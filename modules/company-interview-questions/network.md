# 网络协议

## CQ03 · TCP 建连和断连过程是什么？`CLOSE_WAIT` 为什么堆积？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

TCP 建连使用三次握手：

1. 客户端发送 `SYN`，声明自己的初始序号；
2. 服务端返回 `SYN + ACK`，确认客户端序号并声明服务端序号；
3. 客户端返回 `ACK`，双方确认双向收发能力和序号空间。

断连通常需要两边分别关闭发送方向，所以常见为四个报文：`FIN → ACK → FIN → ACK`。TCP 支持半关闭，一方不再发送后仍可继续接收。

`CLOSE_WAIT` 表示：**本机已经收到对端的 FIN，并向对端确认，但本机应用还没有关闭套接字。** 大量堆积通常说明应用忘记 `close`、异常路径没有释放连接，或线程被阻塞迟迟走不到关闭逻辑。

### 把状态变化串起来

建立连接时，客户端和服务端分别经历：

```text
客户端                                      服务端
CLOSED                                      LISTEN
  | --- SYN, seq=x -----------------------> |
SYN_SENT                                  SYN_RCVD
  | <------ SYN+ACK, seq=y, ack=x+1 -------- |
  | --- ACK, ack=y+1 ---------------------> |
ESTABLISHED                              ESTABLISHED
```

握手不只是“确认网络通”。双方还要同步各自的初始序号，并确认对方已经收到自己的序号。序号空间使 TCP 能够对字节去重、排序和确认。

以客户端主动关闭为例：

```text
客户端                                      服务端
ESTABLISHED                              ESTABLISHED
  | --- FIN ------------------------------> |
FIN_WAIT_1                              CLOSE_WAIT
  | <------ ACK ---------------------------- |
FIN_WAIT_2       服务端应用仍可继续发送       |
  | <------ FIN ---------------------------- |
  | --- ACK ------------------------------> |
TIME_WAIT                                  CLOSED
  |  等待一段时间后
CLOSED
```

“四次挥手”不是硬性规定必须恰好四个独立包。服务端若收到 FIN 后立即关闭，可以把 ACK 和自己的 FIN 合并；双方也可能同时关闭。真正的语义是两个发送方向要分别结束。

### 为什么需要 `TIME_WAIT`

主动关闭方保留 `TIME_WAIT` 主要有两个作用：

1. 如果最后一个 ACK 丢失，对端会重发 FIN，主动关闭方仍能再次回复 ACK；
2. 让旧连接中的延迟报文在网络中消失，避免相同四元组的新连接误收旧报文。

所以少量 `TIME_WAIT` 是正常的协议成本。问题应结合连接创建速率、临时端口耗尽、是否频繁创建短连接以及连接池复用情况判断。

### `TIME_WAIT` 与 `CLOSE_WAIT` 不要混淆

| 状态 | 通常出现在哪一侧 | 主要含义 |
|---|---|---|
| `CLOSE_WAIT` | 被动关闭方 | 等本地应用调用关闭 |
| `TIME_WAIT` | 主动关闭方 | 等待旧报文过期，并能重发最后的 ACK |

排查 `CLOSE_WAIT` 应优先看应用连接生命周期；仅调小系统超时通常治标不治本。

### 一套可执行的排查路径

发现 `CLOSE_WAIT` 持续增长时，可以按下面的证据链排查：

1. 用连接统计确认是哪些本地端口、进程和下游地址；
2. 对照连接数增长时间与发布、流量、超时告警；
3. 抽取线程栈或协程栈，看请求是否卡在业务锁、连接池或下游调用；
4. 审计所有成功、异常、超时和取消路径是否都会释放响应体与 Socket；
5. 检查 HTTP 客户端是否要求消费或关闭响应体后才能归还连接；
6. 修复后观察存量连接是否下降，并增加连接状态和池占用监控。

面试中最好给一个具体例子：代码在成功路径调用 `close()`，但 JSON 解析异常时直接返回，连接就会停在 `CLOSE_WAIT`。正确做法是使用上下文管理器或 `finally` 统一释放。

### 面试中容易说错

- “三次握手是为了防止 SYN 洪泛”：握手首先是协议正确性要求，SYN Flood 是利用了握手状态的攻击；
- “四次挥手是因为 TCP 不可靠”：根因是 TCP 全双工，两个发送方向需要分别关闭；
- “`CLOSE_WAIT` 调小内核超时即可”：这个状态在等本地应用关闭，核心通常是应用生命周期问题；
- “看到 `TIME_WAIT` 就调内核参数”：可能掩盖短连接设计或连接池配置问题。

### 常见追问与回答

**为什么不能只握手两次？**

两次后客户端知道服务端收到了自己的 SYN，但服务端还不知道客户端是否收到服务端的 SYN 和初始序号。第三次 ACK 补上这个确认，也能避免服务端把某些延迟到达的旧 SYN 直接当成完整新连接。

**服务端出现大量 `TIME_WAIT` 一定是故障吗？**

不一定。它说明服务端是主动关闭方。要结合连接速率、端口范围、连接复用和业务关闭策略判断。

**为什么建立连接三次，关闭常见四次？**

服务端收到 SYN 时可以同时确认并发送自己的 SYN；收到 FIN 只代表对端不再发送，本地应用可能还有数据要发，因此 ACK 与本地 FIN 往往分开发送。

**连接断开时进程崩溃了，还会走四次挥手吗？**

不一定。正常 `close` 触发 FIN；异常复位可能发送 RST；主机宕机甚至来不及发送任何报文，只能依靠对端的重传、保活或应用层超时发现。

## CQ04 · QUIC / HTTP/3 相比 HTTP/2 改变了什么？

> 公开记录：字节后端一面公开面经中出现“QUIC 相对于 HTTP/2 的变化”。

### 面试回答

HTTP/2 在一条 TCP 连接上使用二进制分帧和多路复用，解决了 HTTP/1.1 应用层请求排队问题；但 TCP 丢失一个报文时，后续字节必须等待重传，连接上的所有 HTTP/2 流都会受到传输层队头阻塞影响。

HTTP/3 把 HTTP 映射到 QUIC：

- QUIC 基于 UDP，在用户态实现可靠传输；
- 不同 QUIC 流拥有独立的有序交付，单个流丢包不会阻塞其他流；
- TLS 1.3 握手集成进 QUIC，通常减少建连往返；
- 连接通过 Connection ID 标识，客户端网络切换后可迁移连接；
- 协议在用户态演进，部署新拥塞控制和传输特性更灵活。

### 先分清三层问题

| 协议 | 应用层能力 | 可靠传输基础 | 加密 |
|---|---|---|---|
| HTTP/1.1 | 文本报文；常用多连接缓解排队 | TCP | HTTPS 时使用 TLS |
| HTTP/2 | 二进制分帧、流、多路复用、HPACK | TCP 的单一有序字节流 | 通常 TLS |
| HTTP/3 | HTTP 语义运行在 QUIC 流上、QPACK | QUIC 基于 UDP 实现可靠多流传输 | TLS 1.3 集成进 QUIC |

HTTP/2 已经解决了**应用层**的队头阻塞：一个慢响应不会因为请求顺序本身卡住后续响应。但它的多个流仍被编码进同一条 TCP 字节流。只要 TCP 序号中间缺了一段，内核就不能把后续字节交给应用，即使后续字节属于另一个 HTTP/2 流。

QUIC 把可靠有序的范围缩小到单个流。流 A 的包丢失时，流 A 等待重传；已经完整到达的流 B 数据仍可交给 HTTP/3。需要注意：网络拥塞会影响整条连接的拥塞窗口，所以并非“一个流丢包对其他流完全零影响”。

### 用丢包例子理解

假设一个页面同时加载大图片 A 和很小的接口响应 B：

- HTTP/2：A 的某个 TCP 段丢失，B 的后续字节即使先到，也可能被 TCP 有序交付规则挡住；
- HTTP/3：A 与 B 位于不同 QUIC 流，A 等重传时，完整到达的 B 可以先交给应用。

这也是回答“HTTP/3 为什么改善弱网体验”时最关键的因果链，而不是笼统说“UDP 比 TCP 快”。UDP 本身不提供可靠性，QUIC 在 UDP 之上重新实现了确认、重传、拥塞控制和流量控制。

### 建连与连接迁移

传统 TCP 连接通常由源/目的 IP、端口组成的四元组识别。手机从 Wi-Fi 切换到蜂窝网络后，IP 变化通常意味着连接需要重建。QUIC 使用 Connection ID 识别连接，地址变化后可以验证新路径并延续连接状态。

首次访问仍需要完成安全握手；已连接过的客户端可利用会话恢复减少往返。0-RTT 可以更早发送应用数据，但数据可能被重放，因此支付、创建订单等非幂等操作不能仅因为“更快”就直接开放。

### 取舍

HTTP/3 不是“无条件更快”：

- 用户态协议栈和加密带来 CPU 成本；
- 某些网络会限制或降级 UDP；
- 首次连接、短请求和网络质量良好时，收益可能有限；
- 0-RTT 数据存在重放风险，只适合可安全重放的请求。

部署时还要考虑监控与回退：UDP 被网络设备阻断时，客户端通常需要回退到 HTTP/2；排障工具如果只观察 TCP，也会漏掉 QUIC 流量。

### 面试中容易说错

- “HTTP/3 使用 UDP，所以不可靠”：可靠性由 QUIC 提供，不是由 UDP 提供；
- “HTTP/2 没有队头阻塞”：没有 HTTP/1.1 式应用层排队，但仍有 TCP 层队头阻塞；
- “QUIC 完全不需要握手”：仍需建立安全与传输状态，只是流程被整合并支持恢复；
- “0-RTT 没有代价”：它存在重放风险，业务必须判断请求是否可重放。

### 常见追问与回答

**HTTP/2 已经多路复用，为什么仍有队头阻塞？**

应用层流独立，但底层 TCP 只提供一条有序字节流；前面的字节缺失时，后续字节即使已到达也不能交付应用。

**HTTP/3 还需要 TCP 吗？**

不需要。QUIC 自己提供可靠性、拥塞控制、流和连接管理。

**QUIC 为什么选择 UDP，不直接发明新的 IP 协议号？**

UDP 能穿过现有操作系统 API、NAT 和多数网络设备，协议逻辑放在用户态也便于升级。全新的传输层协议往往面临中间设备不识别和内核部署周期长的问题。

**HTTP/3 一定比 HTTP/2 快吗？**

不一定。高质量低延迟网络、连接已复用、请求很短时差距可能很小；UDP 受限、客户端或服务端实现不成熟、CPU 加密成本高时还可能更慢。应以真实网络下的成功率和延迟分位数验证。

### 自测

1. HTTP/2 的“流”为什么仍被 TCP 的字节序约束？
2. QUIC 的多流怎样缩小丢包影响范围？
3. 为什么 0-RTT 更适合幂等请求？

## CQ15 · TCP 如何保证可靠传输？流量控制和拥塞控制有什么区别？

> 来源类型：跨公司公开面经反复出现的 TCP 题族。

### 60 秒面试回答

TCP 的可靠性不是“绝不丢包”，而是把不可靠 IP 之上的字节流变成按序、无重复交付：

- 序号标识字节位置，ACK 确认已经连续收到的数据；
- 校验和发现传输损坏；
- 超时重传和基于重复 ACK 的快速重传恢复丢失；
- 接收端缓存乱序段，重复段不会再次交付应用；
- 滑动窗口允许多个未确认字节同时在途。

流量控制保护接收端，发送上限受接收窗口 `rwnd` 约束；拥塞控制保护网络，发送上限受拥塞窗口 `cwnd` 约束。实际可发送的在途数据受两者较小值限制。算法细节随实现而变，面试时应先讲机制和信号，不把某个算法版本背成所有 TCP 的固定行为。

### 序号、ACK 与重传

TCP 序号按字节计数。若接收端已经连续收到 `[0, 999]`，累计 ACK 通常表达“下一个期望字节是 1000”。后续段先到而中间有洞时，接收端可以缓存乱序数据，但累计 ACK 不会跨过缺口。

发送端主要通过两类证据判断丢失：

1. **重传超时 RTO**：在估计时间内没有得到确认；
2. **重复 ACK / SACK 信息**：表明后续数据到达但前面可能缺段，可以更快重传。

RTO 不能设成固定拍脑袋常量。TCP 根据往返时间样本估计，并对抖动保留安全余量；过短会误重传，过长会让真正丢包恢复太慢。

### `rwnd` 与 `cwnd`

```text
允许在途量 ≤ min(rwnd, cwnd)
```

- `rwnd` 来自接收端通告，表示接收缓冲还能容纳多少；
- `cwnd` 是发送端依据拥塞反馈维护的限制；
- 应用写入速度、发送缓冲和路径带宽也会形成额外瓶颈。

接收窗口为零时，发送端不会永久沉默，而会通过窗口探测避免双方等待。拥塞窗口则通常在新连接或拥塞后保守增长，并在检测到拥塞时收缩；CUBIC、BBR 等具体算法的信号和增长方式不同。

### 为什么“收到 ACK”不等于业务成功

TCP ACK 只证明对端 TCP 栈确认了字节，不证明：

- 服务端应用已经读取；
- 数据已经写入数据库；
- 事务已经提交；
- 用户已经看到结果。

因此支付、下单等业务仍需要应用层请求 ID、幂等键和明确结果查询。连接中断发生在响应返回前时，客户端面对的可能是“请求已成功但响应丢失”的不确定状态。

### 面试中容易说错

- “TCP 不会丢包”：底层会丢，TCP 负责检测和恢复；
- “滑动窗口就是拥塞控制”：它也是可靠传输与流量控制的基础机制；
- “三次重复 ACK 后一定执行同一种快恢复”：具体行为取决于实现和算法；
- “ACK 到了代表数据库已落盘”：TCP 与业务提交是不同层次。

### 常见追问与回答

**粘包是什么，TCP 出错了吗？**

TCP 提供字节流，没有消息边界。“两次 `send` 对应两次 `recv`”本来就没有保证。应用层需要固定长度、分隔符或长度前缀等 framing。

**为什么网络丢包会影响延迟尾部？**

丢包触发重传，若没有足够证据快速重传就要等待 RTO；同一 TCP 连接上的后续字节还可能被前面的缺口阻塞交付。

**SACK 解决什么问题？**

累计 ACK 只能指出连续前缀。SACK 让接收端报告已经收到的非连续区间，发送端可以更准确地只补缺失部分。

### 自测

1. 接收端很慢但网络空闲，主要受 `rwnd` 还是 `cwnd` 限制？
2. 为什么请求超时后直接重试可能重复扣款？
3. TCP 为什么需要应用层消息边界？

## CQ16 · 浏览器访问 HTTPS 地址时发生什么？TLS 1.3 如何验证身份并建立密钥？

> 来源类型：跨面经高频综合网络题。回答以现代 HTTPS 主路径为准，不假设所有连接都从零开始。

### 90 秒面试回答

我会按“名称、连接、安全、HTTP、渲染”五层回答：

1. 浏览器解析 URL，检查缓存、代理、HSTS 和连接复用；
2. 通过 DNS 获得地址，DNS 本身可能命中浏览器、系统或递归解析器缓存；
3. 选择传输：HTTP/1.1 或 HTTP/2 通常在 TCP 上使用 TLS，HTTP/3 使用 QUIC；
4. TLS 握手协商版本、密码套件和应用协议，服务端发送证书链并证明持有私钥；客户端验证域名、有效期、信任链和撤销策略；
5. 双方通过密钥交换派生会话密钥，后续 HTTP 数据使用带认证的加密保护；
6. HTTP 请求经过 CDN、网关和服务端，响应回来后浏览器解析、加载子资源并渲染。

真实路径可能复用现有连接、会话恢复或使用 HTTP/3，因此不能把每次访问都背成固定的“DNS + TCP 三次握手 + 完整 TLS”。

### TLS 1.3 的核心不是“用证书加密全部数据”

证书主要把公钥身份绑定到域名。典型握手中：

```text
ClientHello: 支持版本、随机数、key share、ALPN、SNI...
ServerHello: 选择参数、key share
服务端: EncryptedExtensions、Certificate、CertificateVerify、Finished
客户端: 验证证书和握手签名，发送 Finished
双方: 从 (EC)DHE 共享秘密和握手 transcript 派生流量密钥
```

业务数据用对称加密保护，因为它适合大量数据。证书私钥用于证明服务端身份，不直接拿来加密每一个 HTTP 响应。使用临时 Diffie-Hellman 密钥交换还能提供前向保密：以后服务端长期私钥泄露，也不能直接解开此前记录的会话。

### 客户端验证什么

至少包括：

- 证书链能否连接到受信任根；
- 证书中的名称是否匹配访问域名；
- 证书是否在有效期内、用途是否允许服务器认证；
- 服务端 `CertificateVerify` 是否证明持有对应私钥；
- 整个握手 transcript 的 `Finished` 是否一致。

“网页显示 HTTPS”不代表业务内容可信，也不阻止服务端自己返回恶意数据。TLS 保护通信机密性、完整性和对端身份，不能替代应用鉴权、输入校验和内容安全策略。

### 0-RTT 的边界

会话恢复可以减少握手延迟。TLS 1.3 的 early data 可能被重放，协议层不能保证对每个应用请求恰好执行一次。因此只有业务上可安全重放的操作才适合 0-RTT；支付、创建订单等非幂等操作应拒绝 early data 或使用额外防重放机制。

### 面试中容易说错

- “HTTPS 用服务端公钥加密所有数据”：实际业务流量主要用对称密钥；
- “有证书就一定安全”：还要正确验证域名、链和握手签名；
- “每次请求都要重新 TCP 和 TLS 握手”：连接通常会复用；
- “TLS 1.3 0-RTT 就是零风险”：early data 存在重放边界；
- “DNS 一定先于所有连接”：缓存、预解析和现有连接会改变顺序。

### 常见追问与回答

**中间人为什么不能替换证书？**

攻击者可以发自己的证书，但无法让它同时通过目标域名和受信任链验证，除非信任根、终端或 CA 体系被攻破/错误配置。

**SNI 和 ALPN 分别做什么？**

SNI 告知服务器客户端想访问的主机名，便于同一地址选择证书和虚拟主机；ALPN 在 TLS 握手中协商 HTTP/1.1、HTTP/2 等应用协议。ECH 可进一步保护 ClientHello 中的敏感字段，但部署和协商有额外条件。

**TLS 能防止重放吗？**

正常握手后的记录层有序号和认证保护；TLS 1.3 early data 因会话恢复模型存在专门的重放风险，应用必须按 RFC 给出的边界处理。
