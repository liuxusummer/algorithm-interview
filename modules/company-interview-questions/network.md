# 网络协议

## CQ03 · TCP 建连和断连过程是什么？`CLOSE_WAIT` 为什么堆积？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

TCP 建连使用三次握手：

1. 客户端发送 `SYN`，声明自己的初始序号；
2. 服务端返回 `SYN + ACK`，确认客户端序号并声明服务端序号；
3. 客户端返回 `ACK`，双方确认双向收发能力和序号空间。

断连通常需要两边分别关闭发送方向，所以常见为四个报文：`FIN → ACK → FIN → ACK`。TCP 支持半关闭，一方不再发送后仍可继续接收。

`CLOSE_WAIT` 表示：**本机已经收到对端的 FIN，并向对端确认，但本机应用还没有关闭套接字。** 大量堆积通常说明应用忘记 `close`、异常路径没有释放连接，或线程被阻塞迟迟走不到关闭逻辑。

### `TIME_WAIT` 与 `CLOSE_WAIT` 不要混淆

| 状态 | 通常出现在哪一侧 | 主要含义 |
|---|---|---|
| `CLOSE_WAIT` | 被动关闭方 | 等本地应用调用关闭 |
| `TIME_WAIT` | 主动关闭方 | 等待旧报文过期，并能重发最后的 ACK |

排查 `CLOSE_WAIT` 应优先看应用连接生命周期；仅调小系统超时通常治标不治本。

### 常见追问

**为什么不能只握手两次？**

两次无法让服务端确认客户端已经收到服务端的初始序号，也更难隔离网络中延迟到达的旧连接请求。

**服务端出现大量 `TIME_WAIT` 一定是故障吗？**

不一定。它说明服务端是主动关闭方。要结合连接速率、端口范围、连接复用和业务关闭策略判断。

## CQ04 · QUIC / HTTP/3 相比 HTTP/2 改变了什么？

> 公开记录：字节后端一面公开面经中出现“QUIC 相对于 HTTP/2 的变化”。

### 面试回答

HTTP/2 在一条 TCP 连接上使用二进制分帧和多路复用，解决了 HTTP/1.1 应用层请求排队问题；但 TCP 丢失一个报文时，后续字节必须等待重传，连接上的所有 HTTP/2 流都会受到传输层队头阻塞影响。

HTTP/3 把 HTTP 映射到 QUIC：

- QUIC 基于 UDP，在用户态实现可靠传输；
- 不同 QUIC 流拥有独立的有序交付，单个流丢包不会阻塞其他流；
- TLS 1.3 握手集成进 QUIC，通常减少建连往返；
- 连接通过 Connection ID 标识，客户端网络切换后可迁移连接；
- 协议在用户态演进，部署新拥塞控制和传输特性更灵活。

### 取舍

HTTP/3 不是“无条件更快”：

- 用户态协议栈和加密带来 CPU 成本；
- 某些网络会限制或降级 UDP；
- 首次连接、短请求和网络质量良好时，收益可能有限；
- 0-RTT 数据存在重放风险，只适合可安全重放的请求。

### 常见追问

**HTTP/2 已经多路复用，为什么仍有队头阻塞？**

应用层流独立，但底层 TCP 只提供一条有序字节流；前面的字节缺失时，后续字节即使已到达也不能交付应用。

**HTTP/3 还需要 TCP 吗？**

不需要。QUIC 自己提供可靠性、拥塞控制、流和连接管理。
