# 三轮对抗审查报告

> 审查时间：2026-07-30
>
> 审查范围：语言无关后端核心题、Agent 高频题及 Agent 核心工程专题。
> 不在本轮覆盖声明内：Java/JVM/Spring、Go runtime、C++ 对象模型等语言或框架专属题。

本报告不声称掌握公司的内部题库，也不把公开面经数量解释成真实出题概率。目标是：对公开记录里反复出现、又能区分工程理解深度的题族，至少提供一篇可追问、可验证、有版本边界的系统答案。

## 审查方法

三类证据承担不同职责：

| 证据等级 | 用途 | 典型来源 |
|---|---|---|
| A · 规范与官方文档 | 核验协议、产品语义和版本边界 | RFC、Linux/POSIX、MySQL、Redis、Kafka、OpenTelemetry |
| B · 原始论文与官方工程实践 | 解释设计动机、故障模型和取舍 | Raft、Saga、Spanner、Google SRE、AWS Builders' Library |
| C · 候选人公开记录 | 证明题目公开出现过，观察题族重复 | 牛客等公开面经 |

C 级证据不用于证明技术答案正确；A/B 级资料也不能证明某家公司“必考”。正文必须把两者分开。

## 第一轮：权威性攻击

### 对抗问题

1. 这条结论是协议保证、某个产品实现，还是经验建议？
2. 是否把 MySQL InnoDB、Redis 或某个 TCP 算法的实现说成普遍规律？
3. 是否出现“绝不丢”“一定更快”“完全一致”“恰好一次”等无条件承诺？
4. 故障切换、网络分区、进程暂停和重试时，结论是否仍成立？
5. 技术资料能否直接支持该题的核心机制？

### 本轮修订

- 为 MySQL 题明确 **MySQL 8.4 InnoDB** 边界，区分快照读、锁定读和实际索引锁范围；
- 为 TCP 题区分协议机制与具体拥塞控制实现，不把 ACK 误解释成业务成功；
- 为 Redis 题明确异步复制、lease 过期和故障切换窗口，不承诺“部署副本就零丢失”；
- 为缓存一致性、Outbox 和 MQ 明确“至少一次 + 业务幂等”的现实边界；
- 为 TLS 1.3、CAP、共识和分布式事务补充 RFC、官方文档或原始论文；
- Agent 章节继续以 MCP/A2A 规范、OWASP、NIST、OpenTelemetry 和主流工程团队一手资料为答案依据。

### 第一轮结论

核心答案均能落到 A/B 级资料；公开面经只保留为问题来源。仍需注意：真实系统的配置、版本和业务不变量可能改变答案，读者不能把页面当作无条件操作手册。

## 第二轮：高频覆盖攻击

### 口径

“覆盖率”按**题族**而不是相似问法计数。例如“三次握手”“CLOSE_WAIT”“TIME_WAIT”属于 TCP 连接状态题族；不会为了数字把它们拆成多道薄题。

P0 题族的选择同时满足：

1. 在多条公开后端面试记录中重复出现，或是高频场景题的直接依赖；
2. 能考察因果、边界和故障恢复，不只是 API 记忆；
3. 对不同语言的服务端岗位有迁移价值。

### 有意不纳入 P0 的内容

- JVM GC、Java 内存模型、Spring 事务、Go 调度器：高度依赖岗位语言栈；
- 分库分表、短链、Feed、搜索系统：适合作为后续 P1 场景专题；
- Raft 实现细节、数据库内核源码：适合资深存储/基础架构岗位，不应挤占通用后端主线；
- 只考命令或 API 名称的碎片题：可在具体题目的追问中出现，不单独扩题。

## 第三轮：教学与追问攻击

### 面试官视角

逐题检查是否能继续追问：

- 结论的前提是什么？
- 失败发生在哪个时间窗口？
- 如何用指标、日志、trace、执行计划或状态机验证？
- 方案换来了什么，又牺牲了什么？
- 如果发生重试、超时、切换或并发，是否仍然正确？

新增题目统一包含口述主干、机制拆解、失败边界、常见误区、追问、自测和一手资料。

### 初学者视角

逐题检查是否具备：

1. 开头 60～90 秒主干，先知道面试要回答什么；
2. 流程、表格、SQL、代码或数字例子，避免只堆术语；
3. 明确区分相近概念，例如 `rwnd` / `cwnd`、快照读 / 当前读、熔断 / 限流；
4. 至少一个失败时间线，帮助建立因果模型；
5. 自测题能脱离原文复述，而不是原句填空。

### 第三轮结论

内容已经从“知道名词”提升为“能给结论、解释因果、说出边界、接受追问”。后续新增题若缺少这些层次，应由自动检查和人工审查共同阻止合入。

## 发布前质量门禁

运行：

```bash
pnpm docs:check:interview
pnpm docs:build
```

自动检查验证：

- CQ 编号连续且不重复；
- 每道后端核心题都有面试回答、误区、追问、自测和技术资料；
- README 中的题数与实际题数一致；
- Markdown 内部链接能被 VitePress 构建解析。

自动检查只能验证结构，不能证明答案正确。涉及协议版本、数据库行为或安全建议的实质性修改，仍需重新阅读对应一手资料并进行人工对抗审查。
