# 场景设计与排障

## CQ11 · 如何设计一个可扩展的限流器？

> 来源类型：跨公司公开面经中反复出现的系统设计题，不标注单一公司。

### 面试回答

我会先确认四个条件：按用户、IP、接口还是租户限流；限制平均速率还是同时允许突发；单机还是分布式；超过限制后拒绝、排队还是降级。

### 第一步不是选算法，而是澄清需求

面试官说“设计限流器”时，可以主动确认：

| 问题 | 为什么重要 |
|---|---|
| 限谁 | IP、用户、租户、接口或全局会产生不同 key 数量和公平性 |
| 限什么 | QPS、并发数、带宽或昂贵操作次数不是同一个指标 |
| 允许多大突发 | 决定用窗口还是令牌桶，以及桶容量 |
| 单机还是全球多地域 | 决定一致性、延迟和可用性的取舍 |
| 拒绝还是排队 | 排队可能降低错误率，却把压力转化为延迟和内存 |
| 依赖故障怎么办 | 决定 fail-open、fail-closed 或本地降级 |

例如“每个租户每秒平均 100 次，允许瞬时 200 次；支付接口不能放过超额请求；读接口在 Redis 故障时允许本地近似限流”已经比“做一个 QPS 限流器”清晰得多。

常见算法：

| 算法 | 特点 | 适合 |
|---|---|---|
| 固定窗口 | 实现简单，但窗口边界可能瞬间放过两倍流量 | 粗粒度保护 |
| 滑动日志 | 精确，但记录每个请求，空间成本高 | 低流量且要求精确 |
| 滑动窗口计数 | 用多个小桶近似，成本和精度平衡 | 通用接口限流 |
| 令牌桶 | 按速率补充令牌，允许一定突发 | API 网关常用 |
| 漏桶 | 以稳定速率流出，平滑突发 | 保护处理能力固定的下游 |

### 令牌桶怎样计算

维护三个核心量：

- `rate`：每秒补充多少令牌；
- `capacity`：桶最多保存多少令牌，决定最大突发；
- `tokens` 和 `last_refill`：当前余额和上次计算时间。

请求到来时：

```text
elapsed = now - last_refill
tokens = min(capacity, tokens + elapsed × rate)

if tokens >= cost:
    tokens -= cost
    允许
else:
    拒绝或等待
```

不需要后台任务每毫秒真的放令牌；可以在请求到达时按时间差惰性计算。若不同请求成本不同，例如导出报表比读详情贵，可一次消耗多个令牌。

固定窗口的边界问题也可以用数字解释：限制每分钟 100 次，用户在 `12:00:59` 发 100 次、`12:01:00` 又发 100 次，短短两秒通过 200 次。滑动窗口或令牌桶能更平滑地表达限制。

### 分布式实现

以 Redis 令牌桶或滑动窗口为例：

- key 包含限流维度，如 `tenant:api`；
- 读取状态、计算和更新必须原子执行，可使用 Lua 脚本；
- 设置过期时间，避免无界 key；
- Redis 故障时明确 fail-open 还是 fail-closed；
- 热点 key 需要分片或本地预限流；
- 返回 `429 Too Many Requests`，并在合适时提供重试提示。

### 两层限流更容易扩展

高流量系统常把限流拆成：

```text
实例本地快速限流
    ↓ 过滤明显超额流量
共享存储 / 配额服务
    ↓ 保证租户或全局额度
业务服务
```

本地层延迟低、依赖少，但多个实例的总额度只是近似；共享层更接近全局一致，却增加网络开销和中心热点。可由配额服务按时间段向各实例租赁一批令牌，减少每个请求访问 Redis，但要接受短时间误差并处理实例崩溃后未用完配额。

### 时间、热点和故障

- **时间**：不同机器时钟偏差会影响窗口；可用共享存储时间或允许误差；
- **热点**：全局 key 会集中到一个分片，本地预限流或分层配额能分散压力；
- **存储失败**：支付、库存保护通常偏 fail-closed；普通读接口可本地保守放行；
- **重试风暴**：客户端收到 429 后若立即同时重试，会再次冲击系统，应使用 `Retry-After` 和随机退避；
- **排队上限**：允许等待也要限制队列长度和最长等待时间，防止内存膨胀。

### 验收指标

不能只测“第 101 个请求被拒绝”。还要验证：

1. 稳态通过率是否接近配置速率；
2. 最大突发是否受 `capacity` 限制；
3. 多实例并发时是否超发；
4. 窗口边界和机器时钟偏差；
5. Redis 慢、超时和不可用时的策略；
6. 配置变更能否平滑生效与快速回滚；
7. 被拒绝请求是否有可观察的原因、维度和租户标签。

### 面试中容易说错

- “用 Redis `INCR` 就完成限流”：还要保证过期设置、窗口边界和原子性；
- “分布式限流必须绝对精确”：强一致会提高延迟与可用性成本，很多场景允许小误差；
- “超过限制全部排队”：无界排队会导致延迟雪崩；
- “Redis 故障统一放行”：核心接口和普通读接口的风险不同。

### 常见追问与回答

**Redis 出现网络抖动怎么办？**

核心写接口可选择 fail-closed，保证保护下游；普通读接口可本地限流并 fail-open。选择取决于拒绝合法请求和压垮下游哪个代价更高。

**如何验证限流器？**

测试稳态速率、允许突发量、窗口边界、并发原子性、时钟偏差和依赖故障下的行为。

**如何动态修改租户额度？**

配置要带版本和生效时间，通过配置中心或配额服务分发；实例保留短期缓存，并记录当前版本。降额时要决定立即收紧还是渐进生效，避免现有令牌突然失效导致尖峰拒绝。

**限流和熔断有什么区别？**

限流根据请求量主动控制进入系统的负载；熔断根据下游错误或延迟状态暂时停止调用。二者常配合，但触发信号和保护对象不同。

### 自测

1. 令牌桶的速率和容量分别控制什么？
2. 本地限流与全局限流怎样取舍？
3. 哪些接口适合 fail-open，哪些更适合 fail-closed？

## CQ12 · 一个线上接口突然变慢，如何系统排查？

> 来源类型：跨公司公开面经中的高频工程场景题。

### 面试回答

我不会先猜是数据库，也不会立刻扩容，而是按证据缩小范围：

1. **确认影响面**：哪个接口、地区、租户和版本；P50、P95、P99 从什么时候变化；错误率和吞吐是否同步变化；
2. **检查最近变更**：发布、配置、流量、依赖、数据库结构和基础设施事件，必要时先回滚止损；
3. **沿调用链定位**：用 trace 找出耗时增加的 span，区分应用计算、排队、数据库、缓存、RPC 和第三方依赖；
4. **检查资源饱和**：CPU、内存、GC、线程池、连接池、文件描述符、磁盘 I/O 和网络；
5. **进入具体依赖**：SQL 看执行计划和锁等待，Redis 看慢命令和大 key，MQ 看积压和消费延迟；
6. **验证假设**：一次只改变一个因素，对比修复前后的分位数和错误率；
7. **完成复盘**：补监控、容量阈值、回滚方案、超时预算与故障演练。

### 先定义“慢”，不要只看平均值

先把四个黄金信号拉到同一时间轴：

- **流量**：QPS、并发数、请求大小是否变化；
- **延迟**：P50、P95、P99，排队和执行分别多久；
- **错误**：HTTP 状态、业务错误、超时和取消；
- **饱和度**：CPU、内存、线程池、连接池、磁盘和队列水位。

平均耗时可能正常，但 1% 的请求从 `100ms` 变成 `10s`，用户和上游重试已经会受到严重影响。分位数还应按地区、机房、版本、接口、租户和依赖切分，避免把局部故障平均掉。

### 一条从外到内的证据链

```text
客户端耗时
  = DNS + 建连/TLS + 网关排队
  + 应用线程池等待 + 应用执行
  + 下游 RPC / Redis / SQL
  + 响应传输
```

Trace 能告诉你时间花在哪个 span，但还要与指标和日志交叉验证：

- span 在进入业务代码前很长：看网关、线程池或连接池排队；
- SQL span 很长：看数据库执行计划、锁和资源；
- 多个不相关下游同时变慢：看本机线程池、DNS、网络或共同代理；
- trace 看起来都快、客户端仍慢：看采样缺口、响应传输和客户端网络。

### 用一个案例走完整流程

现象：新版本发布十分钟后，订单接口 P99 从 `300ms` 升到 `4s`，错误率暂时正常。

1. **止血判断**：新旧版本对比，若只有新版本异常且回滚成本低，先回滚；
2. **影响面**：P50 正常、P99 升高，说明是部分请求或资源争用，不是所有执行都变慢；
3. **Trace**：慢请求集中在获取数据库连接之前；
4. **指标**：连接池使用率 100%，数据库 CPU 正常；
5. **日志与变更**：新版本在事务中增加了一个慢 HTTP 调用，持有连接时间变长；
6. **修复**：把远程调用移出数据库事务，设置超时，缩短持有连接时间；
7. **验证**：灰度发布，对比连接等待、事务耗时、P99 和错误率；
8. **预防**：增加连接池等待告警、事务时长监控和相关代码审查规则。

这个例子展示了为什么“数据库连接池满”不等于“数据库容量不够”。扩容连接池可能让更多请求同时压向数据库，只会把排队位置后移。

### 排查要区分相关性与因果

CPU 在接口变慢后上升，不代表 CPU 是根因；可能是上游重试增加导致的结果。验证假设时要寻找时间顺序与可重复证据：

1. 哪个指标最先变化；
2. 是否只发生在某版本、实例或流量标签；
3. 回滚或隔离后是否恢复；
4. 压测或故障注入能否复现；
5. 修复后相关饱和指标是否同步改善。

### 面试表达重点

先讲“止血”，再讲“根因”：

- 止血：回滚、限流、降级、切流、扩容；
- 根因：通过指标、日志、追踪和变更记录形成证据链；
- 修复：不仅恢复服务，还防止同类问题再次发生。

### 面试中容易说错

> “先重启服务看看。”

重启可能暂时恢复，但会破坏现场。除非业务已经不可用且重启是明确的止血手段，否则应先保留线程栈、指标、日志和 trace 证据。

其他常见问题：

- 一上来就说“加索引”，还没证明慢在数据库；
- 只看 CPU 平均值，不看单核、限额、排队和尾延迟；
- 无限加超时时间，导致请求在系统里堆得更久；
- 同时改多个参数，恢复后无法知道哪个假设成立；
- 只恢复服务，不补监控、回滚和演练。

### 常见追问与回答

**平均耗时正常但 P99 上升说明什么？**

少量请求受到锁、GC、冷缓存、慢依赖或热点分片影响。平均值会掩盖尾延迟，应按标签和调用链继续切分。

**所有下游都变慢，问题一定在下游吗？**

不一定。连接池耗尽、线程池排队、DNS 或网络问题可能让多个下游同时表现为慢，需要找共同依赖和最早变慢的环节。

**业务已经大量超时，先保现场还是先重启？**

先以业务恢复为最高优先级，但在不明显拖慢止血的前提下快速保留关键证据，例如指标快照、线程栈、核心日志和部署版本。然后回滚、切流或重启。不能为了完美取证让故障持续，也不能每次无证据重启。

**扩容为什么可能无效甚至更糟？**

瓶颈若在数据库、锁或限额下游，扩应用实例只会增加并发请求，让下游排队和超时更严重。扩容前应确认饱和资源和系统中的实际瓶颈。

**怎样判断是 GC 问题？**

关联停顿时间、堆使用、分配速率与慢请求时间线；观察慢请求是否跨越停顿，线程是否集中等待。不能看到内存高就直接认定 GC，缓存增长和正常堆使用也可能占用内存。

### 一套 90 秒面试表达

> 我先确认影响面和时间点，拉齐流量、延迟分位数、错误率和资源饱和度，并检查发布与配置变更。业务受损严重时先回滚、限流或降级，同时保留指标、线程栈、日志和 trace。随后沿调用链把总耗时拆成网关排队、线程/连接池等待、应用计算和各下游耗时；再进入具体资源验证锁、GC、SQL、缓存或网络假设。我会一次验证一个假设，用版本或实例对照、回滚和压测建立因果。恢复后补监控、容量阈值、超时预算、回滚与故障演练。

### 自测

1. 为什么 P50 正常而 P99 变慢时，要优先寻找局部标签和共享资源？
2. 应用连接池满，但数据库 CPU 很低，可能发生了什么？
3. 为什么“同时把线程池、连接池和超时都调大”不是好的验证方式？

## CQ26 · 如何设计秒杀系统，保证不超卖并扛住突发流量？

> 来源类型：跨公司公开面经高频场景设计题。重点不在背组件，而在容量、不变量和失败恢复。

### 90 秒面试回答

我会先确认商品数、峰值 QPS、活动时长、用户限购、是否允许排队、结果返回时限和库存一致性要求。核心不变量是“成功订单不超过可售库存，同一用户不超过限购数，支付与释放库存可恢复”。

架构上把读流量和写决策分开：CDN/静态页承接读；网关做身份、活动时间、用户级限流和防刷；服务用有界队列或令牌把突发流量整形成系统可处理速率；库存扣减必须在一个权威原子操作中完成，例如数据库条件更新，或 Redis Lua 预扣后通过可靠事件落库。消费者和订单创建按业务请求 ID 幂等，超时未支付订单通过状态机释放预留。数据库唯一约束和库存条件更新负责最终防线，缓存和锁主要用于效率。

### 第一步：做数量级估算

假设：

- 10 万件库存；
- 1000 万用户看到活动；
- 峰值 50 万请求/秒，持续 10 秒；
- 下单核心链路稳定处理 2 万请求/秒。

不能把 50 万 QPS 全部塞进下单线程池和数据库。即使库存只有 10 万，也要尽早过滤：

```text
静态内容/CDN
  ↓
网关：活动校验、身份、防重放、用户/IP/设备限流
  ↓
资格与库存令牌：只放行接近可售规模的请求
  ↓
有界队列：平滑到可消费速率，满时明确拒绝
  ↓
订单状态机 → 支付 → 确认 / 超时释放
```

“上 MQ”不是容量答案。必须给出生产速率、消费速率、最大积压和可接受等待时间：

```text
积压增长速度 = 进入速率 - 消费速率
恢复时间 ≈ 积压量 / (恢复期消费速率 - 恢复期进入速率)
```

### 库存扣减的三种层次

**1. 数据库条件更新**

```sql
UPDATE sku_stock
SET available = available - 1
WHERE sku_id = ?
  AND available > 0;
```

影响行数为 1 才成功。它简单且是最终正确性防线，但单个热门 SKU 可能形成热点行。

**2. Redis Lua 预扣**

脚本原子检查库存、用户限购并预扣，适合高吞吐入口。之后通过可靠事件创建订单并落库。必须处理：

- Redis 成功但事件未可靠产生；
- 重复消费；
- Redis 与数据库数量偏差；
- Redis 故障或切换丢失写；
- 预留超时释放与对账。

**3. 库存分段**

把库存令牌按分片/机房分配可以降低热点，但要处理分片售罄而其他分片有余量、动态再平衡和总量不变量。没有真实热点证据时不要过早增加复杂度。

### 幂等、限购与状态机

建议主键/唯一约束：

```text
unique(activity_id, user_id, purchase_slot)
unique(request_id)
```

订单状态：

```text
CREATING → RESERVED → PAYING → PAID
                └───────────→ EXPIRED → RELEASING → RELEASED
```

每个迁移使用条件更新并记录版本。延迟任务可能重复触发，释放操作也必须幂等；支付成功与超时释放并发时，以状态机和支付权威结果裁决，不能各自无条件修改库存。

### 防刷不能只靠 IP

大规模代理会绕过单 IP 限流，同一 NAT 后也可能有许多真实用户。应组合账户、设备、行为、风险等级、验证码/证明和动态配额。安全策略要在活动前压测，避免风控服务自身成为强依赖。

### 过载和降级

- 队列必须有界，满时快速返回“已售罄/排队中”，不能无限堆积；
- 低优先级推荐、画像、营销逻辑可降级，不阻塞库存主链路；
- 缓存击穿时不能把全部流量回源数据库；
- 预热连接池、脚本、热点数据，但仍要演练冷启动和实例批量重启；
- 监控有效下单率、重复率、库存偏差、排队时长、支付超时和补偿积压，而不只看 QPS。

### 面试中容易说错

- “Redis 单线程所以绝不超卖”：单次脚本原子不等于跨系统流程一致；
- “用分布式锁把请求串行化”：热点锁会把容量问题变成排队和超时；
- “MQ 能无限削峰”：积压受磁盘、保留、消费者恢复时间和业务时限约束；
- “库存扣成负数再补回来”：会破坏成功订单不超过库存的不变量；
- “缓存挂了直接回源数据库”：突发流量可能立即击穿最后防线。

### 常见追问与回答

**Redis 预扣成功但订单创建失败怎么办？**

通过 Outbox/可靠事件保证创建任务可恢复；订单长期未创建则按预留记录释放，并定期对账 Redis、订单和数据库库存。释放也用请求 ID 幂等。

**用户看到超时，但后台下单成功怎么办？**

返回可查询的请求 ID，客户端查询最终状态；不要在超时后无条件重新创建。业务状态必须区分失败和未知。

**怎样证明系统能扛峰值？**

用生产相近数据和依赖进行阶梯压测、突发压测、热点 SKU、实例故障和缓存冷启动演练，验证饱和点、拒绝行为、库存不变量和恢复时间。只测平均 QPS 不够。
