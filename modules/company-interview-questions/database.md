# 数据库

## CQ05 · MySQL 索引为什么使用 B+ 树？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

以 InnoDB 为例，索引采用多路平衡树结构，面试中通常称为 B+ 树。它适合页式存储和范围查询：

1. 内部页主要保存分隔键和子页指针，单页能容纳较多分支，树的高度较低；
2. 查找每经过一层只需读取一个索引页，较高扇出减少随机 I/O；
3. 叶子页按键有序，适合范围扫描和排序；
4. 所有记录都在同一叶子层，查询路径稳定。

InnoDB 聚簇索引的叶子页保存整行记录；二级索引叶子保存索引列和主键值，查询其他列时可能还要根据主键回到聚簇索引，这就是“回表”。

### 为什么不是其他结构

| 结构 | 问题 |
|---|---|
| 二叉搜索树 / 红黑树 | 分支少，数据量大时层数高，不适合减少页 I/O |
| 哈希索引 | 等值查询快，但不天然支持范围、前缀顺序和排序 |
| 跳表 | 可支持范围，但数据库页管理、局部性与成熟实现上 B+ 树更合适 |

### 常见追问

**主键为什么建议短且稳定？**

二级索引叶子保存主键。主键越大，所有二级索引占用越多；频繁变化还会增加页分裂和维护成本。

**联合索引 `(a, b, c)` 为什么强调最左前缀？**

索引先按 `a` 排序，再在相同 `a` 内按 `b` 排序。缺少前导列时，后续列在全局上不再连续有序。

## CQ06 · 一段 SQL 执行缓慢，应该如何排查？

> 公开记录：字节后端一面公开面经。

### 面试回答

我会先判断“慢在哪里”，再决定是否改 SQL 或索引：

1. **确认现象**：是单条 SQL 稳定慢、偶发慢，还是数据库整体慢；记录耗时分位数、调用量和开始时间；
2. **拿到执行计划**：使用 `EXPLAIN`，条件允许时使用 `EXPLAIN ANALYZE` 对比估算行数与实际行数；
3. **看访问路径**：是否全表扫描、扫描行数过大、发生回表、临时表、文件排序或低效连接；
4. **检查索引与统计信息**：过滤列、连接列、排序列是否有合适的联合索引，统计信息是否过旧；
5. **检查等待**：锁等待、磁盘 I/O、CPU 饱和、内存压力、连接池排队和网络延迟；
6. **验证改动**：在接近生产的数据分布上对比执行计划和 P95/P99，不只看一次运行时间。

### 一个关键原则

不要一看到慢 SQL 就“加索引”。索引会增加写放大与存储，低选择性条件也未必值得走索引。应从执行计划证明瓶颈，再做最小改动。

`EXPLAIN ANALYZE` 会实际执行语句。对修改语句或生产大查询使用前，要理解其副作用与成本。

### 常见追问

**有索引为什么没走？**

可能是返回比例太高、隐式类型转换、对索引列使用函数、联合索引前导列缺失、统计信息不准，或优化器判断全表扫描更便宜。

**偶发慢而执行计划正常怎么办？**

重点看锁等待、缓存冷热、检查点或刷盘、连接池排队、主机抖动以及上下游超时，而不是只盯 SQL 文本。
