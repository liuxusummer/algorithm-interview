# 数据库

## CQ05 · MySQL 索引为什么使用 B+ 树？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

以 InnoDB 为例，索引采用多路平衡树结构，面试中通常称为 B+ 树。它适合页式存储和范围查询：

1. 内部页主要保存分隔键和子页指针，单页能容纳较多分支，树的高度较低；
2. 查找每经过一层只需读取一个索引页，较高扇出减少随机 I/O；
3. 叶子页按键有序，适合范围扫描和排序；
4. 所有记录都在同一叶子层，查询路径稳定。

InnoDB 聚簇索引的叶子页保存整行记录；二级索引叶子保存索引列和主键值，查询其他列时可能还要根据主键回到聚簇索引，这就是“回表”。

### 从磁盘页理解为什么是“多叉”

数据库不是每比较一个键就读取一次磁盘，而是以页为单位读写。假设索引页为 `16KB`，内部页中的一条“分隔键 + 子页指针”占几十字节，一个内部页可以指向数百个子页。即使只按 `500` 的扇出粗略估算：

```text
第 1 层：1 个根页
第 2 层：最多约 500 个页
第 3 层：最多约 500 × 500 个叶子页
```

每个叶子页又能保存多条记录，因此几层树就能覆盖很大的数据量。红黑树每个节点通常只有两个子节点，同样数量的数据需要更深的路径；如果节点分散在不同页，会产生更多随机 I/O。

根页和热门内部页还可能常驻 Buffer Pool，所以一次查询不等于树高次物理磁盘读取。面试中应把“树高低”说成减少潜在页访问，而不是机械地说“查一次固定三次磁盘”。

### 聚簇索引和二级索引怎样配合

表：

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  email VARCHAR(128) NOT NULL,
  nickname VARCHAR(64),
  KEY idx_email (email)
);
```

执行：

```sql
SELECT nickname FROM user WHERE email = 'a@example.com';
```

大致经历两棵树：

1. 在 `idx_email` 中找到 `email` 对应的主键 `id`；
2. 再到主键聚簇索引中找到整行并读取 `nickname`。

如果查询只需要 `id`：

```sql
SELECT id FROM user WHERE email = 'a@example.com';
```

二级索引叶子已经包含 `email + id`，可能直接完成查询，这就是覆盖索引的典型场景。是否真的覆盖还应以执行计划为准。

### 范围查询为何自然

叶子页中的键有序，并通过页之间的链式关系支持向后扫描。查询 `WHERE created_at >= ? AND created_at < ? ORDER BY created_at` 时，定位到范围起点后可以沿叶子页顺序读取，不需要逐条重新从根查找。

联合索引 `(tenant_id, created_at)` 先按租户分组，再在同一租户内按时间有序，因此同时给出 `tenant_id` 等值条件和 `created_at` 范围时很合适。只给 `created_at` 时，记录分散在不同租户段中，不能简单利用同样的连续区间。

### 为什么不是其他结构

| 结构 | 问题 |
|---|---|
| 二叉搜索树 / 红黑树 | 分支少，数据量大时层数高，不适合减少页 I/O |
| 哈希索引 | 等值查询快，但不天然支持范围、前缀顺序和排序 |
| 跳表 | 可支持范围，但数据库页管理、局部性与成熟实现上 B+ 树更合适 |

### 面试中容易说错

- “B+ 树查询一定是 O(1)”：它仍是随树高增长的查找，只是扇出高、树很矮；
- “一次查询固定读取三次磁盘”：Buffer Pool、覆盖索引和预读都会改变实际 I/O；
- “索引越多查询越快”：索引增加写入维护、页分裂、缓存占用和优化器选择成本；
- “主键顺序递增绝对最好”：它常有利于减少随机页分裂，但高并发集中写末尾页也可能形成热点。

### 常见追问与回答

**主键为什么建议短且稳定？**

二级索引叶子保存主键。主键越大，所有二级索引占用越多；频繁变化还会增加页分裂和维护成本。

**联合索引 `(a, b, c)` 为什么强调最左前缀？**

索引先按 `a` 排序，再在相同 `a` 内按 `b` 排序。缺少前导列时，后续列在全局上不再连续有序。

**为什么叶子节点还要保存主键，而不是物理行地址？**

InnoDB 二级索引通过主键定位聚簇记录。记录因页分裂或整理移动时，二级索引不必全部更新物理地址；代价是主键会复制进每个二级索引。

**什么时候哈希结构更合适？**

数据完全按等值键访问、不需要范围和排序，并且内存结构或专门引擎能接受其碰撞与扩容成本时，哈希可能更直接。通用关系数据库索引需要兼顾等值、范围、排序和页式存储，因此 B+ 树更通用。

## CQ06 · 一段 SQL 执行缓慢，应该如何排查？

> 公开记录：字节后端一面公开面经。

### 面试回答

我会先判断“慢在哪里”，再决定是否改 SQL 或索引：

1. **确认现象**：是单条 SQL 稳定慢、偶发慢，还是数据库整体慢；记录耗时分位数、调用量和开始时间；
2. **拿到执行计划**：使用 `EXPLAIN`，条件允许时使用 `EXPLAIN ANALYZE` 对比估算行数与实际行数；
3. **看访问路径**：是否全表扫描、扫描行数过大、发生回表、临时表、文件排序或低效连接；
4. **检查索引与统计信息**：过滤列、连接列、排序列是否有合适的联合索引，统计信息是否过旧；
5. **检查等待**：锁等待、磁盘 I/O、CPU 饱和、内存压力、连接池排队和网络延迟；
6. **验证改动**：在接近生产的数据分布上对比执行计划和 P95/P99，不只看一次运行时间。

### 第一步：先把“慢”分型

| 类型 | 典型特征 | 优先方向 |
|---|---|---|
| 稳定慢 | 每次执行都扫描大量行 | SQL、索引、数据模型 |
| 偶发慢 | 大多数快，少数延迟尖峰 | 锁、I/O、缓存冷热、资源抖动 |
| 随数据量变慢 | 数据增长后逐步恶化 | 扫描量、分页方式、索引选择性 |
| 数据库整体慢 | 多条无关 SQL 同时变慢 | CPU、磁盘、连接、Buffer Pool、异常流量 |
| 应用看到慢、数据库执行快 | DB 侧耗时正常 | 连接池等待、网络、序列化、应用排队 |

如果不先分型，很容易拿着一条偶发锁等待的 SQL 去改索引，或者把连接池排队误判为数据库执行慢。

### 第二步：读懂执行计划在说什么

面对执行计划，重点不是背字段，而是回答四个问题：

1. **从哪里开始读数据**：全表、索引范围还是唯一键定位？
2. **预计和实际读取多少行**：估算偏差大可能说明统计信息或数据分布有问题；
3. **在哪一步过滤和连接**：过滤是否太晚，连接顺序是否放大中间结果？
4. **是否有额外工作**：排序、临时表、重复回表、物化等。

例如：

```sql
SELECT id, created_at
FROM orders
WHERE user_id = 42
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;
```

若只有单列索引 `user_id`，数据库先找出该用户的所有订单，再过滤状态并排序。一个更匹配访问路径的候选索引可能是：

```sql
CREATE INDEX idx_user_status_created
ON orders(user_id, status, created_at DESC);
```

它把两个等值条件放在前面，把排序列放后面，可能直接按需要的顺序取前 20 条。但这只是候选方案，仍要验证：

- 用户订单数量和状态分布是否让索引有选择性；
- 查询需要的列是否导致大量回表；
- 新索引给写入和存储带来多少成本；
- 其他查询能否复用，是否与已有索引重复。

### 第三步：把数据库时间和等待时间分开

一次请求的“SQL 耗时”可能包含：

```text
等待应用连接池
  → 网络发送
  → 等待数据库线程 / 锁
  → 真正执行
  → 结果传输
  → 应用反序列化
```

因此要联合应用 trace、连接池指标、数据库执行统计和锁等待信息。数据库慢日志显示 `20ms`，而应用 span 显示 `2s`，就应优先调查那 `1.98s` 花在哪里。

### 常见优化手段与代价

| 手段 | 可能收益 | 代价或风险 |
|---|---|---|
| 联合 / 覆盖索引 | 减少扫描、回表和排序 | 写放大、空间、缓存污染 |
| 改写深分页 | 避免丢弃大量前序行 | 需要稳定排序键和游标协议 |
| 拆大事务 | 缩短持锁时间 | 需要重新保证业务一致性 |
| 分批查询 | 限制单次资源占用 | 往返增多、逻辑更复杂 |
| 缓存热点结果 | 降低数据库压力 | 一致性、穿透与失效问题 |
| 读写分离 | 扩展读吞吐 | 复制延迟、故障切换复杂度 |

### 一个关键原则

不要一看到慢 SQL 就“加索引”。索引会增加写放大与存储，低选择性条件也未必值得走索引。应从执行计划证明瓶颈，再做最小改动。

`EXPLAIN ANALYZE` 会实际执行语句。对修改语句或生产大查询使用前，要理解其副作用与成本。

### 面试中容易说错

- “`type=ALL` 一定不能接受”：小表全扫可能比走索引再回表更便宜；
- “命中索引就不会慢”：索引范围过大、大量回表或锁等待仍会慢；
- “`LIMIT` 一定快”：深分页可能先扫描并丢弃大量记录；
- “平均耗时下降就是优化成功”：还要看 P95/P99、吞吐、CPU、写入成本和回归。

### 常见追问与回答

**有索引为什么没走？**

可能是返回比例太高、隐式类型转换、对索引列使用函数、联合索引前导列缺失、统计信息不准，或优化器判断全表扫描更便宜。

**偶发慢而执行计划正常怎么办？**

重点看锁等待、缓存冷热、检查点或刷盘、连接池排队、主机抖动以及上下游超时，而不是只盯 SQL 文本。

**联合索引的列顺序怎么定？**

先从真实查询的等值、范围、排序、分组和返回列出发，再结合选择性与复用性设计。不能只背“选择性高的放最前”；范围条件之后的列通常难以继续用于缩小同一段扫描，但仍可能用于覆盖或下推过滤。

**线上能直接执行 `EXPLAIN ANALYZE` 吗？**

要谨慎。它会实际执行查询并收集运行信息，可能消耗大量资源或产生锁影响。先确认语句只读、数据规模和环境风险，必要时在只读副本或接近生产的数据环境验证。

### 一套 60 秒面试表达

> 我先区分数据库真慢、连接池等待和偶发锁等待，再看时间范围与影响面。对稳定慢 SQL，我会拿执行计划比较估算行数和实际行数，检查访问路径、扫描量、回表、排序与连接顺序；同时看统计信息和数据分布。对偶发慢，我会关联锁、I/O、CPU、Buffer Pool、连接池和发布事件。优化方案可能是联合索引、改写分页或缩短事务，但每个方案都要用接近生产的数据验证 P95/P99，并评估写放大和回归。
