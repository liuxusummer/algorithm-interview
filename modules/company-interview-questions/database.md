# 数据库

## CQ05 · MySQL 索引为什么使用 B+ 树？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

以 InnoDB 为例，索引采用多路平衡树结构，面试中通常称为 B+ 树。它适合页式存储和范围查询：

1. 内部页主要保存分隔键和子页指针，单页能容纳较多分支，树的高度较低；
2. 查找每经过一层只需读取一个索引页，较高扇出减少随机 I/O；
3. 叶子页按键有序，适合范围扫描和排序；
4. 所有记录都在同一叶子层，查询路径稳定。

InnoDB 聚簇索引的叶子页保存整行记录；二级索引叶子保存索引列和主键值，查询其他列时可能还要根据主键回到聚簇索引，这就是“回表”。

### 从磁盘页理解为什么是“多叉”

数据库不是每比较一个键就读取一次磁盘，而是以页为单位读写。假设索引页为 `16KB`，内部页中的一条“分隔键 + 子页指针”占几十字节，一个内部页可以指向数百个子页。即使只按 `500` 的扇出粗略估算：

```text
第 1 层：1 个根页
第 2 层：最多约 500 个页
第 3 层：最多约 500 × 500 个叶子页
```

每个叶子页又能保存多条记录，因此几层树就能覆盖很大的数据量。红黑树每个节点通常只有两个子节点，同样数量的数据需要更深的路径；如果节点分散在不同页，会产生更多随机 I/O。

根页和热门内部页还可能常驻 Buffer Pool，所以一次查询不等于树高次物理磁盘读取。面试中应把“树高低”说成减少潜在页访问，而不是机械地说“查一次固定三次磁盘”。

### 聚簇索引和二级索引怎样配合

表：

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  email VARCHAR(128) NOT NULL,
  nickname VARCHAR(64),
  KEY idx_email (email)
);
```

执行：

```sql
SELECT nickname FROM user WHERE email = 'a@example.com';
```

大致经历两棵树：

1. 在 `idx_email` 中找到 `email` 对应的主键 `id`；
2. 再到主键聚簇索引中找到整行并读取 `nickname`。

如果查询只需要 `id`：

```sql
SELECT id FROM user WHERE email = 'a@example.com';
```

二级索引叶子已经包含 `email + id`，可能直接完成查询，这就是覆盖索引的典型场景。是否真的覆盖还应以执行计划为准。

### 范围查询为何自然

叶子页中的键有序，并通过页之间的链式关系支持向后扫描。查询 `WHERE created_at >= ? AND created_at < ? ORDER BY created_at` 时，定位到范围起点后可以沿叶子页顺序读取，不需要逐条重新从根查找。

联合索引 `(tenant_id, created_at)` 先按租户分组，再在同一租户内按时间有序，因此同时给出 `tenant_id` 等值条件和 `created_at` 范围时很合适。只给 `created_at` 时，记录分散在不同租户段中，不能简单利用同样的连续区间。

### 为什么不是其他结构

| 结构 | 问题 |
|---|---|
| 二叉搜索树 / 红黑树 | 分支少，数据量大时层数高，不适合减少页 I/O |
| 哈希索引 | 等值查询快，但不天然支持范围、前缀顺序和排序 |
| 跳表 | 可支持范围，但数据库页管理、局部性与成熟实现上 B+ 树更合适 |

### 面试中容易说错

- “B+ 树查询一定是 O(1)”：它仍是随树高增长的查找，只是扇出高、树很矮；
- “一次查询固定读取三次磁盘”：Buffer Pool、覆盖索引和预读都会改变实际 I/O；
- “索引越多查询越快”：索引增加写入维护、页分裂、缓存占用和优化器选择成本；
- “主键顺序递增绝对最好”：它常有利于减少随机页分裂，但高并发集中写末尾页也可能形成热点。

### 常见追问与回答

**主键为什么建议短且稳定？**

二级索引叶子保存主键。主键越大，所有二级索引占用越多；频繁变化还会增加页分裂和维护成本。

**联合索引 `(a, b, c)` 为什么强调最左前缀？**

索引先按 `a` 排序，再在相同 `a` 内按 `b` 排序。缺少前导列时，后续列在全局上不再连续有序。

**为什么叶子节点还要保存主键，而不是物理行地址？**

InnoDB 二级索引通过主键定位聚簇记录。记录因页分裂或整理移动时，二级索引不必全部更新物理地址；代价是主键会复制进每个二级索引。

**什么时候哈希结构更合适？**

数据完全按等值键访问、不需要范围和排序，并且内存结构或专门引擎能接受其碰撞与扩容成本时，哈希可能更直接。通用关系数据库索引需要兼顾等值、范围、排序和页式存储，因此 B+ 树更通用。

## CQ06 · 一段 SQL 执行缓慢，应该如何排查？

> 公开记录：字节后端一面公开面经。

### 面试回答

我会先判断“慢在哪里”，再决定是否改 SQL 或索引：

1. **确认现象**：是单条 SQL 稳定慢、偶发慢，还是数据库整体慢；记录耗时分位数、调用量和开始时间；
2. **拿到执行计划**：使用 `EXPLAIN`，条件允许时使用 `EXPLAIN ANALYZE` 对比估算行数与实际行数；
3. **看访问路径**：是否全表扫描、扫描行数过大、发生回表、临时表、文件排序或低效连接；
4. **检查索引与统计信息**：过滤列、连接列、排序列是否有合适的联合索引，统计信息是否过旧；
5. **检查等待**：锁等待、磁盘 I/O、CPU 饱和、内存压力、连接池排队和网络延迟；
6. **验证改动**：在接近生产的数据分布上对比执行计划和 P95/P99，不只看一次运行时间。

### 第一步：先把“慢”分型

| 类型 | 典型特征 | 优先方向 |
|---|---|---|
| 稳定慢 | 每次执行都扫描大量行 | SQL、索引、数据模型 |
| 偶发慢 | 大多数快，少数延迟尖峰 | 锁、I/O、缓存冷热、资源抖动 |
| 随数据量变慢 | 数据增长后逐步恶化 | 扫描量、分页方式、索引选择性 |
| 数据库整体慢 | 多条无关 SQL 同时变慢 | CPU、磁盘、连接、Buffer Pool、异常流量 |
| 应用看到慢、数据库执行快 | DB 侧耗时正常 | 连接池等待、网络、序列化、应用排队 |

如果不先分型，很容易拿着一条偶发锁等待的 SQL 去改索引，或者把连接池排队误判为数据库执行慢。

### 第二步：读懂执行计划在说什么

面对执行计划，重点不是背字段，而是回答四个问题：

1. **从哪里开始读数据**：全表、索引范围还是唯一键定位？
2. **预计和实际读取多少行**：估算偏差大可能说明统计信息或数据分布有问题；
3. **在哪一步过滤和连接**：过滤是否太晚，连接顺序是否放大中间结果？
4. **是否有额外工作**：排序、临时表、重复回表、物化等。

例如：

```sql
SELECT id, created_at
FROM orders
WHERE user_id = 42
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;
```

若只有单列索引 `user_id`，数据库先找出该用户的所有订单，再过滤状态并排序。一个更匹配访问路径的候选索引可能是：

```sql
CREATE INDEX idx_user_status_created
ON orders(user_id, status, created_at DESC);
```

它把两个等值条件放在前面，把排序列放后面，可能直接按需要的顺序取前 20 条。但这只是候选方案，仍要验证：

- 用户订单数量和状态分布是否让索引有选择性；
- 查询需要的列是否导致大量回表；
- 新索引给写入和存储带来多少成本；
- 其他查询能否复用，是否与已有索引重复。

### 第三步：把数据库时间和等待时间分开

一次请求的“SQL 耗时”可能包含：

```text
等待应用连接池
  → 网络发送
  → 等待数据库线程 / 锁
  → 真正执行
  → 结果传输
  → 应用反序列化
```

因此要联合应用 trace、连接池指标、数据库执行统计和锁等待信息。数据库慢日志显示 `20ms`，而应用 span 显示 `2s`，就应优先调查那 `1.98s` 花在哪里。

### 常见优化手段与代价

| 手段 | 可能收益 | 代价或风险 |
|---|---|---|
| 联合 / 覆盖索引 | 减少扫描、回表和排序 | 写放大、空间、缓存污染 |
| 改写深分页 | 避免丢弃大量前序行 | 需要稳定排序键和游标协议 |
| 拆大事务 | 缩短持锁时间 | 需要重新保证业务一致性 |
| 分批查询 | 限制单次资源占用 | 往返增多、逻辑更复杂 |
| 缓存热点结果 | 降低数据库压力 | 一致性、穿透与失效问题 |
| 读写分离 | 扩展读吞吐 | 复制延迟、故障切换复杂度 |

### 一个关键原则

不要一看到慢 SQL 就“加索引”。索引会增加写放大与存储，低选择性条件也未必值得走索引。应从执行计划证明瓶颈，再做最小改动。

`EXPLAIN ANALYZE` 会实际执行语句。对修改语句或生产大查询使用前，要理解其副作用与成本。

### 面试中容易说错

- “`type=ALL` 一定不能接受”：小表全扫可能比走索引再回表更便宜；
- “命中索引就不会慢”：索引范围过大、大量回表或锁等待仍会慢；
- “`LIMIT` 一定快”：深分页可能先扫描并丢弃大量记录；
- “平均耗时下降就是优化成功”：还要看 P95/P99、吞吐、CPU、写入成本和回归。

### 常见追问与回答

**有索引为什么没走？**

可能是返回比例太高、隐式类型转换、对索引列使用函数、联合索引前导列缺失、统计信息不准，或优化器判断全表扫描更便宜。

**偶发慢而执行计划正常怎么办？**

重点看锁等待、缓存冷热、检查点或刷盘、连接池排队、主机抖动以及上下游超时，而不是只盯 SQL 文本。

**联合索引的列顺序怎么定？**

先从真实查询的等值、范围、排序、分组和返回列出发，再结合选择性与复用性设计。不能只背“选择性高的放最前”；范围条件之后的列通常难以继续用于缩小同一段扫描，但仍可能用于覆盖或下推过滤。

**线上能直接执行 `EXPLAIN ANALYZE` 吗？**

要谨慎。它会实际执行查询并收集运行信息，可能消耗大量资源或产生锁影响。先确认语句只读、数据规模和环境风险，必要时在只读副本或接近生产的数据环境验证。

### 一套 60 秒面试表达

> 我先区分数据库真慢、连接池等待和偶发锁等待，再看时间范围与影响面。对稳定慢 SQL，我会拿执行计划比较估算行数和实际行数，检查访问路径、扫描量、回表、排序与连接顺序；同时看统计信息和数据分布。对偶发慢，我会关联锁、I/O、CPU、Buffer Pool、连接池和发布事件。优化方案可能是联合索引、改写分页或缩短事务，但每个方案都要用接近生产的数据验证 P95/P99，并评估写放大和回归。

2. 为什么“有索引”不等于“扫描行少”？
3. 给深分页接口加索引前还应考虑什么替代方案？

## CQ17 · MySQL 的隔离级别和 MVCC 是怎样工作的？快照读与当前读有什么区别？

> 来源类型：腾讯、字节等公开后端面经反复出现的事务题族。以下以 MySQL 8.4 InnoDB 为边界。

### 60 秒面试回答

SQL 标准从弱到强定义读未提交、读已提交、可重复读和串行化。InnoDB 中，普通 `SELECT` 通常是**一致性非锁定读**：根据 Read View 和 undo 版本判断记录对当前事务是否可见；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 等需要读取最新可用版本并加锁，属于当前读/锁定读。

在读已提交下，每次一致性读通常建立新的快照，所以同一事务两次查询可能看到不同已提交结果；在可重复读下，事务中的一致性读通常复用第一次读取建立的快照。MVCC 主要减少读写互相阻塞，但不会让写写冲突消失，也不替代业务约束。

### 四个隔离级别要回答“允许看到什么”

| 隔离级别 | 可能现象 | InnoDB 一致性读的典型快照边界 |
|---|---|---|
| READ UNCOMMITTED | 可读未提交修改 | 最弱，不用于依赖一致读的业务 |
| READ COMMITTED | 同一行前后可能变化 | 每次一致性读创建新快照 |
| REPEATABLE READ | 同一快照内重复读稳定 | 首次一致性读时建立并复用快照 |
| SERIALIZABLE | 通过更强约束串行化访问 | 普通读也可能转为共享锁读 |

“幻读”要先说明读类型。可重复读下，同一事务的纯快照读在同一 Read View 中不会突然看到后来提交的新行；锁定范围并阻止并发插入则依赖 next-key/gap locking 等锁机制。把所有幻读都归功于 MVCC，或都归功于间隙锁，都不够严谨。

### Read View 如何判断可见性

概念上，每个版本带有创建它的事务信息，并通过 undo 链找到更旧版本。Read View 记录快照建立时的活跃事务边界。读取时：

1. 当前事务自己的修改通常可见；
2. 快照前已经提交的版本可见；
3. 快照建立时仍活跃或之后开始的事务版本不可见；
4. 当前版本不可见时沿 undo 版本链寻找可见版本。

具体字段和判定细节属于实现；面试重点是“快照定义可见集合，undo 保存旧版本”，而不是死背变量名。

### 一个容易答错的例子

事务 A 在可重复读下先执行快照查询，看见余额 100。事务 B 把余额改为 120 并提交。事务 A 再做相同普通查询，通常仍看见 100；但事务 A 若执行 `SELECT ... FOR UPDATE`，读取的是用于加锁和后续修改的当前记录语义，结果可能是 120。

这不代表数据库“自相矛盾”，而是快照读和锁定读的目标不同。业务代码混用两者时必须明确预期。

### MVCC 的成本与边界

- 长事务会让旧版本更久不能清理，增加 undo 压力和读取版本链成本；
- MVCC 不防止两个事务同时基于旧值做出业务决策，余额扣减仍要条件更新或锁；
- 隔离级别不自动保证跨表业务不变量，唯一约束、外键或应用事务仍然重要；
- “一致性”不是单靠数据库隔离级别完成，业务状态机也必须正确。

### 面试中容易说错

- “可重复读完全没有幻读”：要区分快照读、当前读以及混用场景；
- “MVCC 没有锁”：写入和锁定读仍需要锁；
- “一致性由 undo log 保证”：业务一致性是约束、事务机制和应用逻辑共同结果；
- “Read View 在事务开始时一定创建”：通常由第一次一致性读触发，显式一致快照是另一种入口。

### 常见追问与回答

**为什么很多业务选择 READ COMMITTED？**

它减少长期复用旧快照带来的认知负担，某些锁范围也更小，但会允许不可重复读。是否选择应依据事务读写模式、锁冲突和业务约束实测，不能说成所有“大厂默认做法”。

**普通 `SELECT` 会加锁吗？**

InnoDB 的普通一致性读通常不加记录锁；`SERIALIZABLE`、显式锁定读或某些特殊语句需要另说。

**长事务有什么问题？**

除了持锁时间，长时间快照还可能阻碍旧版本清理，放大 undo、存储和恢复压力，并让读到的数据越来越旧。

## CQ18 · InnoDB 有哪些锁？死锁为什么发生，应该怎样处理？

> 来源类型：跨公司公开面经高频数据库并发题。

### 60 秒面试回答

InnoDB 的“行锁”实际锁在索引记录上。根据访问范围和隔离级别，可能使用记录锁、间隙锁或 next-key lock；表级还有意向锁，用于快速协调表锁与行锁。锁住多少内容不仅由 SQL 文本决定，还取决于实际使用的索引和扫描范围。

死锁是事务之间形成循环等待。数据库检测到后会选择一个事务回滚，因此应用必须能够识别死锁错误，在保证幂等和限制次数的前提下重试。预防重点是按一致顺序访问资源、让索引缩小扫描与锁范围、缩短事务，并避免事务内做远程调用。

### 锁的是索引，不是抽象的“这一行”

例如：

```sql
SELECT * FROM orders
WHERE tenant_id = 7 AND status = 'pending'
FOR UPDATE;
```

若存在合适的 `(tenant_id, status, id)` 索引，数据库可以锁定更集中的索引范围；若没有合适索引而必须扫描大量记录，检查和锁定范围可能显著扩大。面试中看到锁冲突，既要看事务顺序，也要看执行计划。

常见概念：

- **record lock**：锁定索引记录；
- **gap lock**：锁定索引记录之间的间隙，重点是阻止插入；
- **next-key lock**：记录锁与前方间隙组合；
- **intention lock**：表级声明事务准备在表内获取哪类行锁；
- **insert intention**：插入前对间隙表达的锁意图，允许不冲突位置并发。

具体加锁行为与隔离级别、唯一索引等条件有关，不能用“一条 update 永远只锁一行”概括。

### 一个典型死锁

```text
事务 A：更新订单 1 → 等待订单 2
事务 B：更新订单 2 → 等待订单 1
```

数据库看到等待图中的环，必须打破它。回滚其中一个事务不是数据库故障，而是并发控制的正常结果。应用若把死锁当成通用 500 且不设计恢复，会把可恢复冲突变成用户错误。

### 正确的处理顺序

1. 从数据库死锁报告拿到两个事务的 SQL、已持有锁和等待锁；
2. 确认实际执行计划与索引范围，不只看业务主键；
3. 统一多资源更新顺序，例如总按订单 ID 递增；
4. 缩短事务，远程调用和用户交互移出事务；
5. 需要重试时使用有限次数、退避和完整事务重放；
6. 用约束或状态机保证重试不会重复产生外部副作用。

降低隔离级别可能减少部分间隙锁，但不是死锁万能药；写写冲突和相反顺序仍会死锁。

### 面试中容易说错

- “InnoDB 行锁直接锁物理行”：它基于索引记录实施；
- “死锁只能重启数据库”：数据库通常会检测并回滚受害者；
- “加索引一定减少锁”：错误索引或低选择性索引仍可能扫描很宽；
- “重试死锁 SQL 即可”：应重放完整事务，让业务条件重新判断。

### 常见追问与回答

**唯一索引等值查询为什么常比范围查询锁得窄？**

当唯一条件精确定位存在记录时，不需要保护一整段可能插入的位置；范围查询为了保持其锁定语义，可能涉及记录和间隙。仍应结合隔离级别和语句类型判断。

**数据库已经自动检测死锁，为什么还要预防？**

检测和回滚有资源成本，频繁死锁会放大尾延迟、重试流量和用户失败率。自动恢复不能替代良好访问顺序。

**怎样区分死锁和长时间锁等待？**

死锁有等待环，系统可以立即选受害者；普通锁等待可能只是前序事务很慢，最终由提交或锁等待超时结束。两者的治理重点不同。

### 自测

1. 为什么缺少合适索引可能放大锁冲突？
2. 死锁重试为什么要重放整个事务？
3. 两个事务更新相同两行时，怎样从设计上破坏等待环？

## CQ19 · 联合索引怎样设计？最左前缀、覆盖索引和深分页分别怎么理解？

> 来源类型：跨面经高频索引设计题，是 CQ05、CQ06 的落地追问。

### 60 秒面试回答

联合索引要从真实查询的过滤、连接、排序和返回列设计，而不是把所有字段拼进去。B+ 树按索引列顺序排序，因此能否高效定位取决于查询是否利用了有序前缀；某列进入范围扫描后，后续列通常难以继续缩小连续扫描区间，但仍可能用于索引条件过滤。

覆盖索引表示查询需要的列都能从索引获得，减少回表，但会增加索引宽度、写放大和缓存压力。深分页的核心问题是数据库仍需找到并跳过前面大量行；若业务允许，优先用基于稳定排序键的 seek/keyset 分页。

### 用查询反推列顺序

```sql
SELECT id, created_at, amount
FROM orders
WHERE tenant_id = ?
  AND status = ?
  AND created_at < ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

候选索引可以从 `(tenant_id, status, created_at, id)` 开始验证：

- 等值条件 `tenant_id`、`status` 放在有序前缀；
- `created_at, id` 与排序及游标方向配合；
- 返回的 `amount` 是否加入覆盖，需要比较读收益和索引体积；
- 数据分布、状态基数和查询组合可能改变最佳方案，最终看执行计划与实际扫描量。

“选择性最高的列永远放第一”不是完整规则。若查询必须按租户隔离并排序，访问模式和排序能力可能比单列选择性更重要。

### 范围条件之后发生什么

索引 `(a, b, c)` 在 `a = ? AND b > ? AND c = ?` 下，可以用 `a` 和 `b` 确定扫描区间，但 `c` 通常不能把这个区间拆成跳跃定位；支持索引条件下推时，它仍可在存储引擎层过滤，减少回表，却不等于减少需要浏览的全部索引项。

因此“范围查询后所有列完全失效”也过度简化。要分别问：

1. 是否用于定位扫描区间；
2. 是否用于索引层过滤；
3. 是否用于覆盖返回列；
4. 是否用于避免排序。

### 深分页为什么慢

```sql
SELECT * FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 100000, 20;
```

数据库通常仍要访问或扫描前 100020 个候选位置，再丢弃前 100000 个。改成 seek 分页：

```sql
SELECT id, created_at, amount
FROM orders
WHERE (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

它从上一页最后一个稳定键继续。代价是不能随意跳到任意页，且排序键必须稳定、唯一或带唯一补充列；并发插入下还要定义用户期望的翻页一致性。

### 面试中容易说错

- “联合索引只要包含字段，顺序无所谓”：顺序决定有序前缀和排序能力；
- “覆盖索引没有代价”：它会放大写入、存储和缓存占用；
- “范围条件后面的列完全没用”：定位、过滤、覆盖与排序要分开讨论；
- “把 `LIMIT offset` 改大连接池就能优化”：根因是扫描和丢弃量。

### 常见追问与回答

**索引越多查询越快吗？**

单个查询可能有更多访问路径，但每个索引都要占空间并在写入时维护。优化器估算也更复杂，应按工作负载保留有价值的索引。

**为什么 `SELECT *` 不利于覆盖索引？**

返回列多，普通二级索引通常无法覆盖，只能频繁回表；把所有列塞入索引又会让索引过宽。接口应明确实际需要的列。

**如何验证新索引？**

用接近生产的数据分布比较执行计划、实际行数、返回行数、排序和回表；同时压测写入成本、Buffer Pool 命中和 P95/P99，而不只测一次热缓存查询。
