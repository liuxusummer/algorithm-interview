# Agent 核心工程体系

这一专题不教某个框架的短期 API，而是回答一个更重要的问题：

> 一个 Agent 为什么能在真实环境中持续、正确、可控地完成任务？

一个能演示的 Agent，通常只需要模型、提示词和几个工具。一个能上线的 Agent，还必须具备状态恢复、权限控制、上下文治理、系统评估、安全防线、完整观测和成本上限。模型决定能力的上限，工程体系决定能力能否稳定兑现。

## 先记住这张全景图

```text
用户 / 上游系统
      │
      ▼
身份认证、租户隔离、配额与风险分级
      │
      ▼
┌──────────────── Agent Runtime / Harness ────────────────┐
│  接收目标 → 加载状态 → 构造上下文 → 模型决策 → 执行动作 │
│      ▲          │            │           │          │   │
│      └── 检查点、暂停/恢复、预算、重试、终止条件 ──────┘   │
└───────────┬─────────────┬──────────────┬──────────────┘
            │             │              │
       工具网关       记忆 / RAG      人工审批
            │
   策略引擎、最小权限、沙箱、出站控制
            │
      内部 API / MCP / 远程 Agent(A2A)

贯穿全链路：评估集 + Trace/Metric/Log + 审计 + 成本核算 + 安全治理
```

这张图里有一条最重要的边界：

- **模型位于决策平面**：理解意图、提出计划、选择候选动作；
- **确定性代码位于控制平面**：鉴权、参数验证、预算、审批、执行、审计和回滚。

不要让模型自己判断“我是否有权限”。模型可以申请动作，控制平面必须独立决定动作是否允许。

## 一套统一的生产心智模型

可以把 Agent 的一次执行抽象为下面的状态转换：

```text
(state, observation, policy, budget)
            │
            ▼
      model proposes action
            │
            ▼
 deterministic validation
            │
     ┌──────┼──────────┐
     ▼      ▼          ▼
  execute  request    reject
           approval
     │      │          │
     └──────┴──────────┘
            │
            ▼
   append event + checkpoint
            │
      continue or stop
```

其中：

- `state` 是可恢复的业务与执行状态；
- `observation` 是这一步新获得的信息；
- `policy` 是独立于模型的权限与安全规则；
- `budget` 同时约束步骤、时间、Token、费用和外部副作用；
- `action` 不是直接执行的命令，而是等待控制平面验证的结构化提案；
- 每次状态变更都应产生可追溯事件，重要节点写入检查点。

### 四个必须分开的概念

| 概念 | 典型内容 | 生命周期 | 常见错误 |
|---|---|---|---|
| 执行状态 | 当前步骤、工具结果、审批状态、剩余预算 | 一次任务，可暂停恢复 | 只存在进程内存里 |
| 推理上下文 | 本轮系统指令、目标、证据、工具描述 | 每次模型调用重新构造 | 把所有历史原样塞入 |
| 长期记忆 | 经确认的偏好、稳定事实、经验摘要 | 跨任务，有过期与删除 | 自动永久保存模型猜测 |
| 外部知识 | 文档、数据库、搜索结果 | 以数据源为准 | 把 RAG 结果当可信指令 |

## 最小生产闭环

一个值得上线试点的 Agent，至少应该形成下面的闭环：

1. **定义任务契约**：成功是什么、失败是什么、允许做什么；
2. **构造最小上下文**：只加入当前决策需要的高信号信息；
3. **生成候选动作**：模型输出受 Schema 约束的动作；
4. **独立执行控制**：鉴权、策略、审批、幂等、超时和隔离；
5. **持久化事件与状态**：任何中断都能判断从哪里继续；
6. **采集完整轨迹**：模型、工具、策略、审批、费用可关联；
7. **离线与在线评估**：质量、安全、时延和成本共同验收；
8. **用失败反哺系统**：线上事故进入回归集、策略和工具设计。

如果缺少第 4～8 步，它通常还是 Demo，而不是生产系统。

## 从 Demo 到生产的成熟度

| 等级 | 能力 | 允许的使用范围 |
|---|---|---|
| L0 单次生成 | 一次模型调用，无工具 | 草稿、建议、低风险文本 |
| L1 受控工具 | 结构化工具、参数验证、只读优先 | 内部只读查询 |
| L2 可恢复执行 | 检查点、幂等、预算、人工审批 | 有限写操作、可回滚任务 |
| L3 可评估上线 | 回归集、轨迹评估、发布门禁、灰度 | 面向真实用户 |
| L4 持续治理 | 威胁建模、红队、审计、SLO、成本归因 | 关键业务规模化运行 |

成熟度不是按框架划分的。使用流行框架不会自动从 L0 变成 L3。

## 面试时如何表达

遇到任何 Agent 系统题，都可以按下面六层展开：

```text
目标与风险
  → 决策边界
  → 状态与数据流
  → 失败模式
  → 控制与恢复
  → 评估、观测和成本
```

例如“设计一个自动处理退款的 Agent”，不要从 Prompt 开始。应先问：

1. 退款金额和账户权限如何分级？
2. 哪些步骤只读，哪些会产生不可逆副作用？
3. 模型负责收集证据，还是可以直接提交退款？
4. 重试会不会重复退款，幂等键如何生成？
5. 什么情况必须人工审批？
6. 如何回放一次错误退款的完整决策链？
7. 上线前用什么数据集证明成功率和安全性？

这样的回答比罗列框架名更能体现生产经验。

## 生产就绪总检查表

### 必须有

- [ ] 任务、工具、租户和用户身份在全链路绑定；
- [ ] 最大步骤、时间、Token、费用和副作用次数都有硬上限；
- [ ] 所有工具都有严格输入 Schema、输出契约和超时；
- [ ] 写操作有幂等键，关键操作可审批或补偿；
- [ ] 状态持久化，进程退出后可以安全恢复；
- [ ] 不可信内容与系统指令、授权信息明确隔离；
- [ ] 离线评估覆盖正常、边界、故障和攻击样本；
- [ ] Trace 能关联模型调用、工具、策略、审批和费用；
- [ ] 机密内容默认不写日志，审计记录防篡改并有保留策略；
- [ ] 有降级、熔断、停止开关和事故响应负责人。

### 应该有

- [ ] 工具按只读、可逆写、高风险写分级；
- [ ] 长期记忆有来源、置信度、TTL、纠错与删除入口；
- [ ] 发布采用版本化评估、灰度和自动回滚；
- [ ] 成本按“成功任务”而不是单次请求核算；
- [ ] MCP / A2A 服务建立信任清单、版本和兼容策略；
- [ ] 线上失败样本经过脱敏后进入回归集。

### 应避免

- [ ] 不要把模型输出直接拼接成 Shell、SQL 或 URL 执行；
- [ ] 不要把工具描述、网页或检索内容视为可信指令；
- [ ] 不要用无限重试掩盖状态与幂等设计缺陷；
- [ ] 不要永久保存全部对话作为“记忆”；
- [ ] 不要只看最终答案而忽略越权、轨迹和成本；
- [ ] 不要因为使用了 MCP 或多 Agent 就默认系统更安全或更强。

## 学习路线

### 面试前快速复习

按这条主线读：

`Runtime → 工具边界 → 上下文 → 评估 → 安全 → 观测 → 协议`

每页优先看：

1. 90 秒面试回答；
2. 架构与关键边界；
3. 失败模式；
4. 最佳实践清单；
5. 追问。

### 准备系统设计面试

先读完七章，再回到 [Agent 开发高频面试题](../agent-development.md)，按 AQ06、AQ08、AQ10 做完整系统设计。专题解决“知识体系”，题目页训练“限时表达与追问”。

## 资料口径与版本

本专题在 **2026-07-29** 按以下优先级核验：

1. 协议、标准和安全组织：MCP、A2A、OpenTelemetry、OWASP；
2. 官方工程复盘与框架文档：Anthropic Engineering、LangGraph；
3. 同行评审论文或系统性研究；
4. 博客和题单只用于发现问题，不作为关键结论的唯一依据。

其中 MCP 以 `2025-11-25` 稳定规范为准；A2A 官方 `latest` 当前指向 `0.3.0`。协议仍会演进，生产实现应固定版本并在升级前做兼容和安全回归。
