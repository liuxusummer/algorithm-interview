# 消息与分布式

## CQ10 · MQ 消息丢失、重复和积压分别怎样处理？

> 公开记录：阿里三面相关公开面经整理。

### 面试回答

我会把消息链路拆成生产、Broker 存储和消费三个阶段：

```text
业务事务 → 生产者 → Broker 接收 / 持久化 / 复制 → 消费者拉取
                                              → 业务副作用 → 确认消费
```

先画链路的意义是：不同位置失败，证据和补救方式不同。“开启持久化”只能覆盖其中一段，不能一次解决全部可靠性问题。

### 1. 防止消息无声丢失

- 生产者使用确认机制，失败重试并记录可追踪的消息 ID；
- Broker 根据业务可靠性要求使用持久化和多副本确认；
- 消费者完成业务事务后再确认消息；
- 对关键业务使用事务消息或 Outbox：业务数据和待发送事件写入同一数据库事务，再由后台可靠投递。

#### 丢失点与防线

| 失败位置 | 例子 | 防线 |
|---|---|---|
| 业务提交了，但消息没发出 | 服务在提交订单后、发送消息前崩溃 | Outbox / 事务消息 |
| 生产者发出，但不知道 Broker 是否收到 | 响应在网络中丢失 | 确认、带同一消息 ID 重试 |
| Broker 单节点故障 | 消息只在内存或单副本 | 持久化、多副本确认 |
| 消费成功但过早确认 | 先 ack，后写数据库时崩溃 | 业务成功后再 ack |
| 消费成功但 ack 丢失 | Broker 再次投递 | 消费幂等 |

Outbox 的基本流程：

```text
数据库事务：
  INSERT orders(...)
  INSERT outbox(event_id, payload, status='NEW')
提交
  ↓
后台投递任务发送 NEW 事件
  ↓
Broker 确认后把事件标记为 SENT
```

它把“业务状态”和“待发送事实”放进同一数据库事务，避免二者只成功一半。后台发送仍可能重复，因此消费者幂等依然需要。

### 2. 接受可能重复，并让消费幂等

网络超时后生产者不知道 Broker 是否写入成功，消费者处理成功但确认丢失时 Broker 也会重投。因此“至少一次”通常意味着可能重复。

消费端使用业务唯一键保证幂等：

- 数据库唯一约束；
- `订单 ID + 事件类型 + 版本` 作为去重键；
- 状态机只允许合法状态转换；
- 去重记录和业务更新放在同一事务中。

仅在 Redis 中写一个“处理过”标记，如果它和数据库更新不在同一原子边界内，仍可能产生不一致。

#### 一个幂等消费例子

处理“订单已支付”事件时，可让 `event_id` 具有唯一约束，并在同一事务中：

1. 插入消费记录；若唯一键已存在，说明处理过，直接返回成功；
2. 检查订单当前状态是否允许从 `PENDING` 变为 `PAID`；
3. 更新订单与相关业务表；
4. 提交事务后再确认消息。

仅用“查询是否处理过，再插入”仍有并发竞态；数据库唯一约束才是最终防线。对外部支付、邮件等无法和本地数据库放入同一事务的副作用，要使用对方提供的幂等键，或通过状态机、补偿和对账收敛。

### 3. 处理积压

1. 先确认生产速率、消费速率和最老消息年龄；
2. 判断是消费者故障、下游变慢、坏消息重试还是突发流量；
3. 暂停非关键生产或限流，隔离毒消息；
4. 在保证分区与顺序约束的前提下扩容消费者；
5. 必要时临时写入转储队列，离线回放；
6. 恢复后补监控、容量水位和自动扩缩容。

#### 先算清楚恢复时间

如果生产速率为每秒 `8,000` 条，消费速率只有每秒 `6,000` 条，积压会以每秒 `2,000` 条增长。扩容后消费达到每秒 `12,000` 条，净消化速度是：

```text
12,000 - 8,000 = 4,000 条/秒
```

积压 `24,000,000` 条至少需要约 `6,000` 秒，也就是 100 分钟，前提是下游数据库能承受扩容后的写入。只看“消费者实例数翻倍”而不算净消化速度和下游容量，容易把积压转化成数据库故障。

#### 顺序性会限制扩容

Kafka 一类分区模型中，同一分区通常由消费组内一个消费者处理。消费者数量超过分区数未必继续提升并行度；若要求同一订单有序，应按订单 ID 分区，但不同订单仍可并行。全局有序意味着接近单通道处理，吞吐代价很大。

### 一句话总结

不要轻易承诺端到端“Exactly Once”。Broker 的幂等生产或事务能力不能自动让数据库副作用只执行一次；业务端仍要设计幂等和补偿。

### 面试中容易说错

- “生产者重试就不会丢”：重试会引入重复，还无法修复业务已提交但尚未调用生产者的窗口；
- “Broker Exactly Once 等于业务 Exactly Once”：外部数据库、HTTP 调用等副作用不自动进入 Broker 事务；
- “先 ack 再处理性能更好”：会把消费进程崩溃转化为静默丢失；
- “积压就无限加消费者”：会受分区数、顺序约束和下游容量限制。

### 常见追问与回答

**如何保证同一订单消息有序？**

按订单 ID 分区，让同一订单进入同一分区并串行处理；全局有序会明显限制并行吞吐。

**失败消息一直重试怎么办？**

指数退避并限制次数，超过阈值进入死信队列，告警后人工或补偿任务处理。

**数据库更新成功，但消费者确认失败怎么办？**

Broker 会再次投递，所以数据库更新必须幂等。用唯一事件 ID、状态机条件更新或版本号让重复处理返回相同结果，然后再次确认。

**死信队列是不是最终解决方案？**

不是。它只是把无法自动处理的消息隔离，避免阻塞主队列。还需要告警、查看原因、修复数据或代码、决定重放或丢弃，并记录审计。

**消息积压时能直接跳过旧消息吗？**

只有业务明确允许丢弃且经过授权才可以。订单、支付等事件通常不能跳过；推荐流、日志等时效型消息可能按过期策略丢弃。要由业务语义决定，而不是运维为了清零指标擅自处理。

## CQ23 · 跨服务事务怎样设计？2PC、TCC、Saga 和 Outbox 怎么选？

> 来源类型：跨公司公开面经高频分布式事务题。术语在不同产品中实现不同，回答以一致性目标和失败恢复为主。

### 90 秒面试回答

我不会先背方案，而会先确认不变量、可接受不一致窗口、参与者是否都可控、是否允许补偿以及故障后怎样恢复。

- **2PC** 由协调者让参与者先准备、再统一提交，适合参与者支持事务协议且需要较强原子性的场景，但准备状态会持有资源，协调和恢复复杂；
- **TCC** 把业务拆成 Try、Confirm、Cancel，资源预留可控，但业务侵入大，Confirm/Cancel 必须幂等并处理空回滚与悬挂；
- **Saga** 把长事务拆成本地事务和补偿步骤，提升可用性与持续时间，代价是中间状态可见且补偿不一定等于物理回滚；
- **Transactional Outbox** 在本地事务中同时写业务数据和事件，异步发布并由消费者幂等处理，适合最终一致的事件驱动链路。

不存在一种方案同时提供零侵入、强一致、高可用和无限扩展。最终选择必须落实到状态机、幂等键、重试、对账和人工修复。

### 先写业务不变量

以订单和库存为例：

```text
不变量：已确认订单数量不能超过可售库存
允许：订单创建后 30 秒内处于待确认
不允许：用户被重复扣款
恢复：超时订单释放预留；支付结果可按请求号查询
```

有了这些边界，才能判断是数据库条件更新、库存预留 + Saga，还是需要更强的单一事务边界。很多“分布式事务问题”最好的答案其实是重新划分服务和数据所有权，避免跨边界强事务。

### 四类方案对照

| 方案 | 一致性形态 | 优点 | 关键代价 |
|---|---|---|---|
| 2PC/XA | 统一提交决策 | 对应用暴露较接近原子事务 | 持锁/资源、协调恢复、参与者限制 |
| TCC | 业务资源预留 | 可明确控制关键资源 | 业务侵入、幂等、空回滚、悬挂 |
| Saga | 本地事务 + 补偿 | 适合长流程、服务自治 | 中间态、补偿语义、并发隔离 |
| Outbox | 本地事务 + 可靠事件 | 消除“数据库成功但消息没发”的窗口 | 重复事件、发布延迟、清理与顺序 |

Outbox 并不产生“恰好一次业务效果”。发布器可能在发送成功但标记前崩溃，从而重复发送；消费者仍要幂等。

### 补偿不是简单反向 SQL

发券的补偿可能是“作废券”，不是删除发券记录；退款是新建退款流水，不是抹掉支付流水。补偿需要保留审计，并处理补偿也失败、只完成部分、外部系统不可用等状态。

推荐显式状态机：

```text
PENDING → RESERVED → CONFIRMED
    └──────────────→ CANCELLING → CANCELLED
                         └──────→ MANUAL_REVIEW
```

每个迁移使用业务 ID + 操作类型去重，并记录版本、原因和最后错误。

### 面试中容易说错

- “2PC 能保证任何故障下都立即可用”：网络分区和恢复阶段会影响可用性；
- “Saga 失败就把前面 SQL 全反向执行”：补偿是业务语义；
- “Outbox 保证消息只发一次”：通常是至少一次发布，消费仍需幂等；
- “最终一致就是不管多久最终会好”：必须有时限、检测和修复路径。

### 常见追问与回答

**怎样处理 TCC 空回滚和悬挂？**

Cancel 先于 Try 到达时要记录已取消，后到的 Try 必须拒绝；Confirm/Cancel 都要按事务分支 ID 幂等，不能重复扣减或释放。

**Saga 编排式和协同式怎么选？**

编排式集中展示流程和恢复状态，适合复杂主链路；协同式降低中心依赖，但事件关系难追踪。无论哪种都要有关联 ID、状态查询和可重放性。

**为什么不把所有数据放回一个数据库事务？**

如果业务边界允许，这通常更简单可靠。只有团队自治、容量、地域或生命周期等约束确实要求拆分时，才承担分布式事务复杂度。

2. Saga 的补偿为什么不等于数据库回滚？
3. TCC 的空回滚和悬挂分别是什么顺序问题？

## CQ24 · 超时、重试、幂等、熔断和限流怎样配合，避免故障放大？

> 来源类型：跨面经高频微服务故障治理题。

### 60 秒面试回答

超时限制单次等待，重试应对暂时故障，幂等降低重复执行风险，熔断避免持续调用明显故障的依赖，限流/并发限制保护容量。它们不是独立开关：

1. 先给整条请求设置 deadline，再给每跳分配预算；
2. 只重试明确可重试且业务幂等的操作；
3. 使用指数退避、随机抖动、次数上限和全局重试预算；
4. 在靠近依赖的一层重试，避免每层三次形成乘法放大；
5. 依赖过载时快速失败、隔离资源并降级，而不是让无限队列吞掉内存和尾延迟。

面试重点是解释失败反馈环：服务变慢 → 超时 → 多层重试 → 流量更高 → 服务更慢。

### deadline 不是每层各自 1 秒

假设用户总预算 800ms：

```text
网关与排队 100ms
服务 A 处理 100ms
依赖 B 最多 450ms
返回与安全余量 150ms
```

下游必须知道剩余 deadline，不能每一跳重新开始完整超时。调用已经没有足够预算时应取消或快速失败，否则完成的结果也来不及返回，消耗会变成浪费。

连接超时、读取超时和总 deadline 也要区分。只设置 socket read timeout 可能不覆盖 DNS、连接池等待、TLS 或客户端排队。

### 重试为什么会形成风暴

如果网关、服务 A、服务 B 都“失败后重试 3 次”，一次用户请求在最坏情况下可能放大为多层尝试的乘积。正确做法：

- 选择一个最了解错误语义的层负责重试；
- 只重试超时、连接重置、限流等经过分类的暂时错误；
- 使用指数退避 + jitter，避免所有客户端同步醒来；
- 设置 retry budget，例如额外尝试量不超过正常请求的一定比例；
- 服务明确返回不可重试、过载和建议等待时间。

### 幂等键要落到状态存储

支付请求携带 `request_id`，服务端保存：

```text
(request_id, operation, request_hash, status, response)
```

重复请求：

- 参数相同且已成功：返回原结果；
- 正在执行：返回处理中或等待同一结果；
- 参数不同：拒绝复用同一幂等键；
- 状态未知：通过权威下游查询或进入人工核对。

只在单机内存放一个去重集合，实例重启或流量换机后就失效；只在入口去重，也无法防止内部消息重复消费。

### 熔断、限流和隔离各自保护什么

- **熔断**：根据近期失败/慢调用快速阻断，给依赖恢复窗口；
- **限流**：控制进入速率，拒绝超出服务能力或租户配额的请求；
- **并发限制**：控制同时在途量，直接约束线程、连接和内存；
- **舱壁隔离**：不同依赖/租户使用独立资源池，避免一个热点耗尽全部容量；
- **降级**：返回较便宜、较旧或功能较少的结果。

半开探测必须受控，不能熔断结束后让所有请求同时冲向刚恢复的依赖。

### 面试中容易说错

- “请求失败都可以重试”：永久错误和非幂等副作用不能盲重试；
- “有熔断就不需要限流”：一个看故障反馈，一个保护容量；
- “timeout 越短越好”：过短会误杀正常请求并制造重试；
- “幂等就是相同请求返回 200”：还要保证副作用最多产生一次可接受效果。

### 常见追问与回答

**读请求一定可以重试吗？**

通常更安全，但仍可能昂贵、触发缓存回填或读到不同版本。需要错误分类、预算和取消机制。

**客户端超时后服务端会自动停止吗？**

不一定。必须把取消/deadline 传递下去，并让数据库和下游调用响应取消；外部副作用已经提交时也不能撤销。

**如何选择超时值？**

以端到端 SLO、下游延迟分位数和故障目标为依据，保留网络与返回预算；分地区、请求类型和依赖设置，而不是复制一个全局常量。

## CQ25 · CAP 到底说了什么？强一致、最终一致和共识是什么关系？

> 来源类型：跨面经高频分布式基础题。这里用可验证语义代替口号。

### 60 秒面试回答

CAP 讨论的是发生网络分区时，一个分布式读写系统不能同时保证线性一致的可用读写和每个请求都得到非错误响应。分区发生时，要么拒绝/等待一部分操作以保持一致性，要么继续服务并允许副本分歧。

它不是平时“从 C、A、P 三选二”的产品标签。没有分区时仍要权衡延迟和一致性；发生分区时，选择也可能按操作、数据和业务动态变化。最终一致只说在没有新更新且通信恢复后副本趋同，不定义收敛时间或用户会看到什么。共识算法则让多个节点在故障模型内对日志顺序或值达成一致，是构建线性一致服务的一类基础机制，但仍需多数派、故障检测和客户端语义配合。

### 用一个分区例子回答

两个机房都持有账户余额副本，网络断开：

- 如果两边都继续接受“扣减 80”，系统可能超支，但请求可继续成功；
- 如果只有能联系多数派的一边处理写，另一边拒绝或等待，可以保护单一顺序，但受影响用户会看到不可用；
- 只允许两边读取旧值是否可接受，要看读操作是否参与业务决策。

因此正确问题是：“这个操作在分区时更怕错误结果，还是更怕拒绝服务？”

### 三个经常混淆的概念

| 概念 | 它保证什么 | 它没有自动保证什么 |
|---|---|---|
| 线性一致性 | 每个操作像在调用与返回之间某个瞬间原子生效 | 跨多个对象的事务、永远可用 |
| 最终一致性 | 停止更新并恢复通信后副本最终趋同 | 读己之写、单调读、收敛时限 |
| 共识 | 节点在故障假设内对值/日志达成一致 | 业务不变量、跨系统副作用恰好一次 |

业务常需要更具体的会话保证，例如 read-your-writes、monotonic reads，不能只写一个“最终一致”就结束设计。

### 多数派为什么有用

在典型共识系统中，提交需要多数节点确认。任意两个多数派必有交集，这为新领导者发现已提交日志提供基础。但这不意味着节点数越多写越快；写路径要等待法定人数，跨地域延迟会直接进入提交延迟。

少数派通常不能继续确认新写，否则可能形成两个独立历史。读取是否必须经过领导者、租约或 ReadIndex 等机制取决于系统实现和所需一致性。

### 面试中容易说错

- “分布式系统只能 CA、CP、AP 三选二”：CAP 的关键条件是网络分区期间；
- “P 可选”：真实网络无法假设永不分区，系统只能决定怎样响应；
- “最终一致就是数据大概一致”：它有收敛前提，但仍太弱，需要补会话语义和时限；
- “用了 Raft 就业务强一致”：共识日志正确不等于跨系统业务不变量自动成立。

### 常见追问与回答

**CP 系统是不是完全不可用？**

不是。通常是无法联系多数派的节点拒绝某些需要一致性的操作；健康多数派仍可服务。可用性还要按操作和故障域描述。

**数据库主从异步复制属于哪类？**

不能只贴 AP 标签。要看写确认条件、故障切换、读路由和分区行为。一个产品可以对不同操作提供不同一致性。

**线性一致等于串行化事务吗？**

不等于。线性一致通常描述单个操作的实时顺序；可串行化描述事务结果等价于某个串行顺序。严格可串行化才同时结合事务串行化和实时顺序。

### 自测

1. CAP 为什么只在网络分区条件下形成尖锐取舍？
2. 最终一致为什么不足以描述用户会不会读到自己的写？
3. 共识日志成功提交后，为什么外部支付副作用仍需幂等？
