# 消息与分布式

## CQ10 · MQ 消息丢失、重复和积压分别怎样处理？

> 公开记录：阿里三面相关公开面经整理。

### 面试回答

我会把消息链路拆成生产、Broker 存储和消费三个阶段：

```text
业务事务 → 生产者 → Broker 接收 / 持久化 / 复制 → 消费者拉取
                                              → 业务副作用 → 确认消费
```

先画链路的意义是：不同位置失败，证据和补救方式不同。“开启持久化”只能覆盖其中一段，不能一次解决全部可靠性问题。

### 1. 防止消息无声丢失

- 生产者使用确认机制，失败重试并记录可追踪的消息 ID；
- Broker 根据业务可靠性要求使用持久化和多副本确认；
- 消费者完成业务事务后再确认消息；
- 对关键业务使用事务消息或 Outbox：业务数据和待发送事件写入同一数据库事务，再由后台可靠投递。

#### 丢失点与防线

| 失败位置 | 例子 | 防线 |
|---|---|---|
| 业务提交了，但消息没发出 | 服务在提交订单后、发送消息前崩溃 | Outbox / 事务消息 |
| 生产者发出，但不知道 Broker 是否收到 | 响应在网络中丢失 | 确认、带同一消息 ID 重试 |
| Broker 单节点故障 | 消息只在内存或单副本 | 持久化、多副本确认 |
| 消费成功但过早确认 | 先 ack，后写数据库时崩溃 | 业务成功后再 ack |
| 消费成功但 ack 丢失 | Broker 再次投递 | 消费幂等 |

Outbox 的基本流程：

```text
数据库事务：
  INSERT orders(...)
  INSERT outbox(event_id, payload, status='NEW')
提交
  ↓
后台投递任务发送 NEW 事件
  ↓
Broker 确认后把事件标记为 SENT
```

它把“业务状态”和“待发送事实”放进同一数据库事务，避免二者只成功一半。后台发送仍可能重复，因此消费者幂等依然需要。

### 2. 接受可能重复，并让消费幂等

网络超时后生产者不知道 Broker 是否写入成功，消费者处理成功但确认丢失时 Broker 也会重投。因此“至少一次”通常意味着可能重复。

消费端使用业务唯一键保证幂等：

- 数据库唯一约束；
- `订单 ID + 事件类型 + 版本` 作为去重键；
- 状态机只允许合法状态转换；
- 去重记录和业务更新放在同一事务中。

仅在 Redis 中写一个“处理过”标记，如果它和数据库更新不在同一原子边界内，仍可能产生不一致。

#### 一个幂等消费例子

处理“订单已支付”事件时，可让 `event_id` 具有唯一约束，并在同一事务中：

1. 插入消费记录；若唯一键已存在，说明处理过，直接返回成功；
2. 检查订单当前状态是否允许从 `PENDING` 变为 `PAID`；
3. 更新订单与相关业务表；
4. 提交事务后再确认消息。

仅用“查询是否处理过，再插入”仍有并发竞态；数据库唯一约束才是最终防线。对外部支付、邮件等无法和本地数据库放入同一事务的副作用，要使用对方提供的幂等键，或通过状态机、补偿和对账收敛。

### 3. 处理积压

1. 先确认生产速率、消费速率和最老消息年龄；
2. 判断是消费者故障、下游变慢、坏消息重试还是突发流量；
3. 暂停非关键生产或限流，隔离毒消息；
4. 在保证分区与顺序约束的前提下扩容消费者；
5. 必要时临时写入转储队列，离线回放；
6. 恢复后补监控、容量水位和自动扩缩容。

#### 先算清楚恢复时间

如果生产速率为每秒 `8,000` 条，消费速率只有每秒 `6,000` 条，积压会以每秒 `2,000` 条增长。扩容后消费达到每秒 `12,000` 条，净消化速度是：

```text
12,000 - 8,000 = 4,000 条/秒
```

积压 `24,000,000` 条至少需要约 `6,000` 秒，也就是 100 分钟，前提是下游数据库能承受扩容后的写入。只看“消费者实例数翻倍”而不算净消化速度和下游容量，容易把积压转化成数据库故障。

#### 顺序性会限制扩容

Kafka 一类分区模型中，同一分区通常由消费组内一个消费者处理。消费者数量超过分区数未必继续提升并行度；若要求同一订单有序，应按订单 ID 分区，但不同订单仍可并行。全局有序意味着接近单通道处理，吞吐代价很大。

### 一句话总结

不要轻易承诺端到端“Exactly Once”。Broker 的幂等生产或事务能力不能自动让数据库副作用只执行一次；业务端仍要设计幂等和补偿。

### 面试中容易说错

- “生产者重试就不会丢”：重试会引入重复，还无法修复业务已提交但尚未调用生产者的窗口；
- “Broker Exactly Once 等于业务 Exactly Once”：外部数据库、HTTP 调用等副作用不自动进入 Broker 事务；
- “先 ack 再处理性能更好”：会把消费进程崩溃转化为静默丢失；
- “积压就无限加消费者”：会受分区数、顺序约束和下游容量限制。

### 常见追问与回答

**如何保证同一订单消息有序？**

按订单 ID 分区，让同一订单进入同一分区并串行处理；全局有序会明显限制并行吞吐。

**失败消息一直重试怎么办？**

指数退避并限制次数，超过阈值进入死信队列，告警后人工或补偿任务处理。

**数据库更新成功，但消费者确认失败怎么办？**

Broker 会再次投递，所以数据库更新必须幂等。用唯一事件 ID、状态机条件更新或版本号让重复处理返回相同结果，然后再次确认。

**死信队列是不是最终解决方案？**

不是。它只是把无法自动处理的消息隔离，避免阻塞主队列。还需要告警、查看原因、修复数据或代码、决定重放或丢弃，并记录审计。

**消息积压时能直接跳过旧消息吗？**

只有业务明确允许丢弃且经过授权才可以。订单、支付等事件通常不能跳过；推荐流、日志等时效型消息可能按过期策略丢弃。要由业务语义决定，而不是运维为了清零指标擅自处理。
