# 操作系统与并发

## CQ01 · 进程、线程和协程有什么区别？谁负责调度？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

**进程是资源隔离的基本容器，线程是操作系统执行和调度的基本单位，协程是运行在线程之上的用户态任务。**

- 进程拥有独立的虚拟地址空间和资源表，进程之间默认不能直接读写彼此内存；
- 同一进程内的线程共享代码、堆和打开的文件，但各自有栈、寄存器与调度状态；
- 协程通常由语言运行时或事件循环调度，切换发生在用户态，适合大量 I/O 等待任务。

以 Python 为例，操作系统调度进程和线程；`asyncio` 事件循环调度 `Task`。协程只有在执行到 `await` 等可让出点时，其他任务才有机会运行。

### 先建立三层运行模型

| 层级 | 谁创建和管理 | 共享什么 | 独有状态 | 切换由谁决定 |
|---|---|---|---|---|
| 进程 | 操作系统 | 显式共享内存、文件等内核资源 | 虚拟地址空间、资源表 | 内核调度器 |
| 线程 | 操作系统或线程库 | 所属进程的堆、代码段、文件描述符 | 栈、寄存器、线程局部存储 | 内核调度器 |
| 协程 / Task | 语言运行时、框架 | 所在线程与进程可访问的数据 | 协程栈帧、局部变量、执行位置 | 事件循环或运行时 |

“线程共享进程内存”既是优势也是风险：线程间传递数据便宜，但访问共享可变状态需要锁、原子操作或无锁结构。进程隔离更强，一个进程越界访问通常不会直接破坏另一个进程，但进程间通信需要管道、Socket、共享内存等额外机制。

### 调度到底怎样发生

操作系统对线程通常采用**抢占式调度**：线程即使没有主动让出，时间片耗尽、更高优先级任务就绪或线程阻塞时，内核也可能切换执行线程。切换需要保存当前寄存器和栈指针，再恢复另一个线程的上下文。

常见协程采用**协作式调度**：运行中的协程执行到 `await`，把“等待的事件”和后续执行位置交给事件循环；事件循环再运行其他已经就绪的任务。I/O 完成后，操作系统通过 I/O 多路复用等机制通知事件循环，原任务重新进入就绪队列。

这解释了两个常见现象：

- 协程等待网络时不会占着线程空转，因此一个线程可以挂起大量连接；
- 协程里若执行长时间 CPU 计算或调用阻塞函数却不 `await`，整个事件循环都会被卡住。

### 用一个 Web 请求理解

假设服务要同时请求用户、订单和库存三个下游：

```python
async def build_page(user_id: int):
    # 三个 I/O 同时发出；等待期间事件循环可以处理其他连接
    user, orders, stock = await asyncio.gather(
        fetch_user(user_id),
        fetch_orders(user_id),
        fetch_stock(user_id),
    )
    return render(user, orders, stock)
```

如果三个请求各需约 `100ms`，串行等待约 `300ms`；并发发出后，理想情况下接近最慢的那一个，即约 `100ms`。这不是让单个 I/O 变快，而是把等待时间重叠起来。

若 `render` 是一个耗时两秒的纯 Python 计算，它不会因写在 `async def` 中就自动并行，应放到进程池、原生扩展或独立计算服务中。

### 不要背成“切换成本固定排序”

一般情况下，进程切换可能涉及地址空间与 TLB 影响，线程切换共享地址空间，协程切换不进入内核，因此常见经验是：

`进程切换 > 线程切换 > 协程切换`

但这不是永远成立的性能公式。实际成本取决于工作集、缓存命中、运行时实现和是否发生系统调用。面试时应说“通常”，不要说“必然”。

### 怎么选择

| 场景 | 优先考虑 | 原因 |
|---|---|---|
| CPU 密集、需要多核并行 | 多进程或明确支持自由线程的运行时 | 隔离好，或让线程真正并行利用多个 CPU 核心 |
| 阻塞 I/O，依赖库是同步接口 | 线程池 | 改造成本低，阻塞不会卡住所有任务 |
| 大量网络 I/O，调用链支持异步 | 协程 | 单线程可管理大量等待中的任务 |
| 需要强故障隔离 | 多进程 | 一个进程崩溃不直接破坏其他进程内存 |

选择前还要看团队约束：如果数据库驱动仍是阻塞接口，强行套 `asyncio` 不能获得完整收益；如果任务需要共享大量内存，多进程复制或 IPC 的代价也可能很高。

### 面试中容易说错

- “进程是调度单位，线程只是资源单位”：现代通用操作系统通常调度线程；
- “协程一定比线程快”：协程主要降低大量等待任务的管理成本，不会自动缩短 CPU 计算；
- “有 GIL 就不需要锁”：GIL 不是业务数据的一致性协议，多步读改写仍可能出现竞态；
- “`async` 就是并行”：并发是任务交错推进，并行是同一时刻在多个计算核心执行。

### 常见追问与回答

**协程能利用多核吗？**

单个事件循环通常运行在一个线程上，不能凭协程本身获得 CPU 并行。可以使用多进程运行多个事件循环。

**Python 线程是不是完全没用？**

不是。在常规启用 GIL 的 CPython 构建中，GIL 主要限制同时执行 Python 字节码的 CPU 并行；线程处理 I/O 等待、调用释放 GIL 的扩展时仍然有价值。CPython 3.13 起还提供可选的 free-threaded 构建，可关闭 GIL 实现真正的多线程并行，但依赖库兼容性和性能仍需验证，不能假设所有线上 Python 都已进入无 GIL 模式。

**协程之间还需要锁吗？**

需要看共享状态。单线程事件循环不会在任意机器指令之间抢占，但一次“读—`await`—写”会在 `await` 处被其他协程插入，仍可能丢失更新。可用 `asyncio.Lock`、消息队列或把状态封装给单一任务处理。

**什么时候线程比协程更合适？**

依赖大量同步阻塞库、并发规模不大、希望以较低改造成本并发执行 I/O 时，线程池往往更务实。不要为了使用协程而把完整调用链重写一遍，却没有测得收益。

## CQ02 · `select`、`poll`、`epoll` 有什么区别？LT 和 ET 呢？

> 公开记录：哔哩哔哩服务端开发暑期实习一面。

### 面试回答

三者都让一个线程等待多个文件描述符的就绪事件，但传递关注集合与返回就绪结果的方式不同：

- `select` 每次调用传入位图集合，返回后需要扫描集合，文件描述符数量还受 `fd_set` 大小限制；
- `poll` 使用数组表达关注集合，消除了 `fd_set` 的固定大小限制，但每次仍要传入并扫描整个数组；
- `epoll` 将关注集合保存在内核中，通过 `epoll_ctl` 增删，`epoll_wait` 主要返回已经就绪的事件，适合连接多、活跃连接占比低的场景。

不要回答“`epoll` 永远是 O(1)”。注册、删除、唤醒、复制就绪事件都存在成本；连接数少或多数连接持续活跃时，优势可能不明显。

### 一次等待调用中发生了什么

假设进程维护 `10,000` 个连接，其中只有 `20` 个刚收到数据：

- `select`：每次把关注集合交给内核，返回后应用还要检查描述集合，找出哪些 fd 就绪；
- `poll`：用 `pollfd` 数组解决位图大小限制，但仍需遍历数组识别就绪项；
- `epoll`：先用 `epoll_ctl` 把关注关系登记到内核，事件发生时把就绪项放入就绪队列，`epoll_wait` 取回这批就绪项。

因此 `epoll` 的优势主要出现在“连接很多、每轮活跃很少、关注集合长期稳定”的负载中。若每轮大多数连接都活跃，应用本来就要处理大量事件，三者差距会缩小。

### 对比维度

| 维度 | `select` | `poll` | `epoll` |
|---|---|---|---|
| 关注集合表达 | 固定大小位图 | 动态数组 | 内核中的兴趣集合 |
| 每轮是否重新传入完整集合 | 是 | 是 | 否，增删时更新 |
| 返回结果 | 修改后的 fd 集合 | 数组中的 `revents` | 就绪事件数组 |
| fd 数量限制 | 受 `FD_SETSIZE` 等限制 | 主要受系统资源限制 | 主要受系统资源限制 |
| 平台 | POSIX 常见 | POSIX 常见 | Linux 特有 |
| 适合场景 | 连接少、兼容性优先 | 中等规模、接口简单 | 大量长连接、活跃比例低 |

### LT 与 ET

| 模式 | 行为 | 编程要求 |
|---|---|---|
| LT，水平触发 | 只要 fd 仍然可读或可写，后续等待还会继续通知 | 容错更高，默认更容易写对 |
| ET，边缘触发 | 状态从未就绪变为就绪时通知 | 必须使用非阻塞 fd，并循环读写到 `EAGAIN` |

ET 如果只读取一次就返回，缓冲区里的剩余数据可能不会再次触发通知，造成连接“看起来卡住”。

ET 的读取逻辑通常要写成：

```python
while True:
    try:
        chunk = sock.recv(65536)
        if not chunk:          # 对端有序关闭
            close_connection()
            break
        consume(chunk)
    except BlockingIOError:    # 已经读空，本轮处理结束
        break
```

这里的关键不是 Python 语法，而是三个约束：fd 必须非阻塞、一次通知后循环处理、以 `EAGAIN` / `EWOULDBLOCK` 作为“本轮读完”的信号。

### 从现象反推问题

| 现象 | 优先检查 |
|---|---|
| ET 模式连接偶尔永久卡住 | 是否只读写一次，没有循环到 `EAGAIN` |
| CPU 空转、`epoll_wait` 不断立即返回 | 是否长期关注总是就绪的可写事件 |
| fd 已关闭却处理到旧事件 | 连接对象是否有代际 ID，关闭与事件处理是否存在竞态 |
| 单个大连接拖慢其他连接 | 每轮是否无限读取，没有设置公平处理预算 |

### 面试中容易说错

- “`epoll` 使用共享内存，所以完全零拷贝”：`epoll_wait` 返回事件仍涉及内核与用户态的数据传递；
- “ET 一定比 LT 快”：ET 可减少重复通知，但代码更复杂，实际收益取决于负载；
- “I/O 多路复用就是异步 I/O”：它通常通知的是“已经就绪”，应用仍需主动执行 `read` / `write`；
- “一个线程只能服务一个连接”：等待可被多路复用，线程只处理当前就绪的连接。

### 常见追问与回答

**`epoll` 为什么适合 C10K？**

重点不是“没有任何扫描”，而是关注集合不必每次从用户态完整传入，应用主要处理就绪连接。

**可写事件为什么要谨慎订阅？**

套接字大部分时间都可写，长期订阅可能造成持续唤醒。通常只在发送缓冲区写满后临时关注可写事件。

**`epoll` 是同步 I/O 还是异步 I/O？**

通常归入同步非阻塞 I/O 多路复用：`epoll_wait` 告诉应用 fd 已就绪，真正的数据复制仍由应用调用 `read` 完成。完成式异步 I/O 则是在操作完成后通知结果，两者语义不同。

**为什么高并发服务仍可能使用多个事件循环线程？**

单个事件循环仍受一个 CPU 核心、回调执行时间和系统调用处理能力限制。常见做法是每个工作线程或进程一个事件循环，再通过端口复用或主线程分发连接。

## CQ13 · 互斥锁、读写锁、信号量和 CAS 怎么选？如何避免死锁？

> 来源类型：跨公司公开面经中反复出现的并发题族。具体 API 随语言变化，正文只讲通用语义。

### 60 秒面试回答

先看要保护的是什么：

- **互斥锁**保护一段临界区，同一时刻只允许一个执行者进入；
- **读写锁**允许多个读者并发，但写者需要独占，适合读多写少且临界区不太短的场景；
- **信号量**表达“最多允许 N 个并发持有者”，常用于连接数、任务并发度等容量控制；
- **CAS**是带条件的原子更新，适合状态很小、竞争可控、重试成本低的场景，不等于所有无锁算法都简单或更快。

死锁通常需要同时满足互斥、持有并等待、不可抢占和循环等待。工程上最有效的办法不是运行时“聪明地解锁”，而是破坏循环等待：规定全局加锁顺序、缩短持锁范围、禁止持锁调用未知代码，并为高风险路径增加超时、线程栈和锁等待观测。

### 从共享状态开始，而不是从 API 名称开始

假设转账需要同时锁定账户 A 和 B。如果两个线程分别先锁 A、先锁 B，就可能形成：

```text
线程 1：持有 A → 等待 B
线程 2：持有 B → 等待 A
```

解决方式是按稳定键排序后加锁：

```python
first_account, second_account = sorted(
    [source_account, target_account],
    key=lambda account: account.account_id,
)

with first_account.lock:
    with second_account.lock:
        transfer(source_account, target_account, amount)
```

排序破坏了循环等待。这里的关键不是 Python 语法，而是所有调用方必须遵守同一锁顺序。

### 四种工具的适用边界

| 工具 | 表达的约束 | 适合 | 主要风险 |
|---|---|---|---|
| 互斥锁 | 同时最多 1 个持有者 | 复合状态、短临界区 | 死锁、锁竞争、优先级反转 |
| 读写锁 | 多读或单写 | 读多写少、读临界区有一定长度 | 写者饥饿、升级死锁 |
| 信号量 | 同时最多 N 个持有者 | 连接池、并发任务上限 | 忘记释放、把限并发误当互斥 |
| CAS / 原子变量 | 值仍等于预期时更新 | 计数器、状态机、无锁结构基础 | ABA、自旋放大、复杂正确性证明 |

读写锁不一定优于互斥锁。读临界区很短、写入并不少或实现需要维护复杂队列时，额外协调成本可能抵消并发收益。CAS 失败意味着状态被别人改过，调用方必须重新读取并验证，不能盲目无限重试。

### 死锁预防、检测与恢复

按优先级回答：

1. **设计期预防**：统一锁顺序；尽量单向依赖；不在锁内进行网络 I/O、阻塞队列操作或回调；
2. **实现期约束**：封装锁的所有权；用结构化释放；限制一次持有的锁数量；
3. **运行期观测**：记录锁等待时间、持锁时间、等待者数量；卡死时抓线程栈或任务栈；
4. **恢复策略**：数据库可选择检测环并回滚一个事务；应用进程若状态已不可知，通常应让请求失败或重启隔离实例，而不是强行释放别人的锁。

锁超时只让失败可控，不会自动保证业务正确。超时后要知道操作是否已经产生副作用，并决定重试、补偿还是返回不确定状态。

### 面试中容易说错

- “CAS 没有锁，所以一定更快”：高竞争下自旋和缓存行抖动可能更差；
- “读写锁适合所有读多写少”：还要看临界区长度、公平性和写者延迟；
- “设置超时就不会死锁”：它只是打断等待，业务状态仍需处理；
- “`volatile` 可以替代锁”：可见性不等于多个读改写步骤的原子性。

### 常见追问与回答

**乐观锁和 CAS 是一回事吗？**

不是。乐观锁是一种冲突处理策略，CAS、数据库版本号条件更新都可以实现它。CAS 是具体的原子原语。

**怎样定位线上死锁？**

先确认是 CPU 忙、自旋、阻塞还是资源池耗尽，再抓多次线程栈，建立“线程持有什么、等待什么”的等待图。数据库则查看死锁日志、锁等待和涉及 SQL。一次线程栈可能只说明暂时等待，连续快照更有证据。

**锁粒度越细越好吗？**

不是。细粒度能降低无关竞争，但会增加锁数量、顺序约束和死锁概率。应以冲突分布和性能数据决定。

## CQ14 · 虚拟内存、页表、缺页异常和 Copy-on-Write 是怎样关联的？

> 来源类型：跨面经高频操作系统基础题。

### 60 秒面试回答

进程使用的是虚拟地址。CPU 的内存管理单元根据页表把虚拟页翻译为物理页，并用 TLB 缓存最近的翻译。页表项不存在、权限不符或页面尚未驻留时会触发页故障；内核判断访问是否合法，合法时建立映射或把页面调入内存，不合法则向进程报告错误。

`fork` 后父子进程最初可以共享只读标记的物理页。任一方写入时产生写保护页故障，内核再复制该页并更新映射，这就是 Copy-on-Write。它推迟并减少复制，但写入密集时仍会产生复制成本。

### 一次内存访问发生什么

```text
虚拟地址
  ↓ 拆成虚拟页号 + 页内偏移
TLB 命中 ───────────────→ 物理页 + 偏移
  │ 未命中
  ↓
查询多级页表
  ├─ 有效映射 → 填充 TLB → 访问内存
  └─ 无映射 / 权限异常 → page fault → 进入内核
```

页故障不是都需要磁盘 I/O：

- 首次访问匿名内存，可能只需分配零页；
- Copy-on-Write 写入，需要复制一个物理页；
- 文件页不在内存，可能需要从存储读取；
- 非法地址或违反权限，访问会失败。

因此不能把 page fault 一律解释成“内存不够开始换页”。

### 为什么要使用多级页表

如果为整个虚拟地址空间建立一个连续大表，大量未使用地址也要占页表空间。多级页表只为实际用到的地址范围分配下级表，以多一次或几次查表换取稀疏空间效率。TLB 又把常用翻译缓存起来，减少每次都遍历页表的成本。

大页可以减少页表层级开销和 TLB 压力，但会增加内部碎片、分配难度和回收代价，并不适合所有工作负载。

### Copy-on-Write 的收益与陷阱

`fork` 后立刻 `exec` 时，绝大多数旧地址空间不会被子进程修改，COW 避免了无意义的全量复制。但如果父进程拥有很大的堆，子进程又写入大量页面，实际复制和内存峰值仍可能很高。

在多线程进程中，`fork` 后子进程只保留调用 `fork` 的线程状态。若其他线程在 `fork` 前持有用户态锁，子进程直接执行复杂逻辑可能遇到无法释放的锁；常见安全路径是尽快 `exec`，并遵守运行时文档约束。

### 面试中容易说错

- “虚拟内存就是磁盘交换区”：虚拟内存首先是地址空间和映射抽象；
- “缺页一定访问磁盘”：匿名页、COW 和权限错误都可能触发页故障；
- “`fork` 会立即复制全部内存”：现代系统通常利用 COW 延迟复制；
- “TLB 是普通数据缓存”：它缓存的是地址翻译。

### 常见追问与回答

**为什么随机访问大数组可能比顺序访问慢？**

除了 CPU cache 局部性，随机访问还可能导致更多 TLB miss 和页表遍历。是否发生磁盘换页要另看内存压力。

**RSS 高是否等于进程独占了这么多物理内存？**

不一定。共享库、共享内存和 COW 页面可能被多个进程映射。分析时还要结合 PSS、共享页和匿名页等指标。

**页故障越少越好吗？**

要区分主缺页、次缺页及其延迟。程序启动或按需映射产生的轻量页故障是正常机制，真正要关注的是它是否造成延迟尖峰和 I/O 压力。
