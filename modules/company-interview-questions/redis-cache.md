# Redis 与缓存

## CQ07 · Redis 为什么快？

> 公开记录：字节后端一面公开面经。

### 面试回答

Redis 快不是单一原因：

1. 主要数据保存在内存，常规请求避免随机磁盘读取；
2. 字符串、哈希、集合、有序集合等结构针对操作语义设计，常用操作复杂度较低；
3. 命令执行路径短，核心命令通常串行执行，避免大量共享数据锁竞争；
4. 使用事件驱动 I/O 管理大量连接；
5. 支持 pipeline，一次网络往返可发送多条命令。

需要加一句边界：Redis 6 之后可使用 I/O 线程处理部分网络读写，因此“Redis 完全是单线程”是不准确的；多数命令的执行仍保持串行语义。

### 一条命令为什么路径短

一次典型请求大致经过：

```text
客户端编码命令
  → 网络到达 Redis
  → 事件循环发现连接可读
  → 解析命令
  → 在内存数据结构上执行
  → 编码响应
  → 网络返回客户端
```

常规 `GET` / `SET` 的数据访问在内存中完成，核心操作通常很短。串行执行让命令之间天然有清晰的先后顺序，避免为每个键操作引入复杂锁竞争。Redis 的高性能来自“单次工作短 + 非阻塞管理大量连接”，不是因为单线程本身神奇。

### 数据结构也决定性能

Redis 不是只保存一个普通哈希表。不同抽象对应不同实现与复杂度：

- String 可表示文本、计数器和二进制数据；
- Hash 适合对象字段的局部读写；
- Set / Sorted Set 支持成员判断、集合运算和按分值排序；
- List / Stream 支持队列或日志式场景。

同一类型也可能根据元素数量和大小选择紧凑编码或常规结构。因此回答复杂度时应针对具体命令和数据规模，不能笼统说“Redis 所有操作都是 O(1)”。

### 网络往返为什么常比命令更贵

假设客户端与 Redis 单次往返是 `1ms`，连续执行 100 个很快的命令：

- 逐条发送并等待响应，理论上仅 RTT 就接近 `100ms`；
- pipeline 一次发送多条命令，再批量读取响应，可显著减少往返等待。

pipeline 不等于事务：它优化网络交互，但不会自动保证这一批命令不被其他客户端命令穿插。需要原子性时要根据场景使用单条原子命令、事务或 Lua 脚本。

### Redis 也会慢

- `KEYS`、超大集合运算或 Lua 长脚本阻塞命令执行；
- 大 key 删除、过期回收和持久化 `fork` 可能造成延迟抖动；
- 网络往返多时，服务端再快也会被 RTT 限制；
- 内存接近上限会触发淘汰或操作系统压力。

### 从延迟尖峰反推原因

| 现象 | 可能原因 | 证据 |
|---|---|---|
| 单个命令稳定慢 | 算法复杂度高、元素太多 | 慢日志、命令统计、大 key |
| 周期性尖峰 | RDB/AOF、过期回收、后台任务 | 延迟监控、持久化指标、系统日志 |
| 服务端耗时低但客户端慢 | RTT、连接池、客户端 GC | trace 分段、网络指标、客户端运行时 |
| CPU 很高 | 热点命令、Lua、序列化、I/O 线程压力 | CPU profile、命令分布 |
| 内存接近上限 | 淘汰、碎片、交换 | `INFO memory`、系统内存和缺页 |

排查时先保留证据，再决定是否删除大 key、拆分数据或调整持久化。直接在生产使用 `KEYS *` 之类的全量命令可能让问题更严重。

### 面试中容易说错

- “Redis 所有操作都是 O(1)”：集合范围操作、排序、删除大对象等可能与元素数量相关；
- “单线程所以没有并发问题”：多条命令组成的业务操作仍可能被其他客户端穿插；
- “pipeline 保证原子性”：它主要减少网络往返；
- “内存数据库绝不会发生磁盘 I/O”：持久化、交换、日志和操作系统行为仍可能涉及磁盘。

### 常见追问与回答

**既然串行执行，为什么吞吐还高？**

内存操作短、避免锁竞争，并通过事件循环和批量网络操作提高整体效率。串行不等于只能维护一个连接。

**如何验证“Redis 慢”？**

看慢日志、延迟监控、命令分布、大 key、CPU、网络、内存和持久化事件，而不是只看平均耗时。

**大 key 为什么危险？**

读取和序列化耗时长，占用网络带宽；删除时可能长时间释放内存；复制和持久化也会放大影响。解决方案通常是拆分、限制单次读取范围、渐进删除并建立大小监控。

**Lua 脚本为什么既有用又危险？**

脚本可把多步读改写放在服务端原子执行并减少 RTT，但长脚本会阻塞其他命令。脚本应短小、有界，并测试最坏输入。

## CQ08 · Redis 如何降低断电后的数据丢失？RDB 和 AOF 怎么选？

> 公开记录：字节后端一面公开面经。

### 面试回答

Redis 提供两类主要持久化机制：

- **RDB**：按时间点生成数据集快照。文件紧凑、备份和全量恢复方便，但故障时可能丢失两次快照之间的数据；
- **AOF**：记录写命令，启动时重放恢复。可通过 `appendfsync always / everysec / no` 在性能和数据损失窗口之间取舍，文件通常更大，需要重写压缩历史。

如果 Redis 只是可重建缓存，可以关闭持久化；如果承担重要数据，常见选择是同时使用 RDB 与 AOF，并结合副本、故障转移和异地备份。持久化解决“重启后恢复”，副本解决“节点故障可用”，二者不是同一个问题。

### RDB 的完整过程

执行后台快照时，主进程通常 `fork` 子进程：

1. `fork` 之后父子进程共享原有内存页；
2. 主进程继续处理请求；
3. 子进程把某个时间点的数据写成临时 RDB 文件；
4. 完成后原子替换旧快照。

主进程在快照期间修改数据时，操作系统通过 Copy-on-Write 复制被修改的内存页。因此快照不是“完全没有运行时成本”：数据集大、写入频繁时，`fork` 延迟和额外内存都可能明显。

### AOF 的写入与重写

AOF 把会改变数据的命令追加到日志。`appendfsync` 控制日志何时要求操作系统刷盘：

| 策略 | 大致语义 | 性能与风险 |
|---|---|---|
| `always` | 每次写命令都同步刷盘 | 数据窗口小，但延迟和吞吐代价最高 |
| `everysec` | 通常每秒刷盘 | 常用折中，极端故障仍可能丢失最近数据 |
| `no` | 交给操作系统决定 | 性能较好，但丢失窗口更不可控 |

AOF 重写不是压缩原日志文本，而是根据当前数据状态生成能重建同样结果的更短命令序列。重写期间的新写入还要被妥善合并，才能在切换文件后不丢变化。

### 恢复时发生什么

- RDB 直接加载紧凑快照，通常恢复较快；
- AOF 需要按顺序重放命令，文件更大时恢复时间可能更长；
- 同时启用时，应以当前 Redis 版本和配置的恢复规则为准，并实际演练；
- 文件存在不代表可恢复，必须定期做校验、异机恢复和故障演练。

### 按业务目标选择

| 场景 | 建议思路 |
|---|---|
| 纯缓存，源数据可重建 | 可不持久化，但要验证回源不会压垮数据库 |
| 可容忍分钟级数据损失 | RDB 快照可能足够，仍需备份与恢复演练 |
| 只能容忍秒级损失 | 常考虑 AOF `everysec`，结合 RDB 与副本 |
| 金融账本、不能丢一笔 | 不应只依赖 Redis；以强持久数据库或日志为事实源 |

### 不能承诺“绝不丢数据”

`everysec` 策略在极端故障时仍可能丢失约一秒数据；副本也可能存在复制延迟。回答时应先明确业务允许的 RPO（最多丢多少数据）和 RTO（多久恢复），再选择配置。

### 面试中容易说错

- “有副本就等于数据不会丢”：异步复制存在延迟，错误删除也会传播；
- “AOF 一定比 RDB 安全”：取决于刷盘策略、文件完整性和恢复流程；
- “RDB 只在子进程工作，对主进程零影响”：`fork`、Copy-on-Write 和 I/O 竞争都会影响主进程；
- “备份成功就算完成”：没有恢复演练的备份无法证明可用。

### 常见追问与回答

**AOF 为什么需要重写？**

同一个键可能经历大量中间写操作，恢复只需要重建最终状态。重写生成更短的等价操作序列。

**RDB 的 `fork` 有什么风险？**

大数据集下创建子进程和写时复制会消耗时间与额外内存，可能带来延迟尖峰。

**主从切换为什么仍可能丢数据？**

主节点已确认给客户端的写入可能尚未复制到被提升的副本。故障切换保证可用性，不自动保证零 RPO；需要结合复制确认策略、业务补偿和事实源设计。

**如何证明恢复方案真的有效？**

定期在隔离环境恢复 RDB/AOF，检查数据完整性与恢复耗时；模拟文件损坏、节点丢失和副本落后，并确认 RPO、RTO 满足目标。

2. AOF `everysec` 的“一秒”为什么不是绝对承诺？
3. 持久化、副本和备份分别解决什么问题？

## CQ09 · 缓存穿透、击穿和雪崩有什么区别？

> 公开记录：字节后端一面公开面经。

### 面试回答

三者按“未命中原因和影响范围”区分：

| 问题 | 典型现象 | 主要方案 |
|---|---|---|
| 穿透 | 请求的数据本来就不存在，每次都绕过缓存访问数据库 | 参数校验、缓存空值、布隆过滤器、防刷限流 |
| 击穿 | 一个热点 key 失效，大量并发同时回源 | 请求合并 / 互斥重建、逻辑过期、热点预热 |
| 雪崩 | 大量 key 同时失效或缓存集群整体不可用 | TTL 加随机抖动、分批预热、多级缓存、限流降级、高可用 |

### 用请求链路区分三者

正常缓存旁路模式：

```text
请求 → 查缓存 ──命中──> 返回
            └─未命中→ 查数据库 → 写缓存 → 返回
```

- **穿透**：数据库里本来就没有。攻击者不断换不存在的 ID，缓存永远难以命中；
- **击穿**：数据库里有，而且是极热点。某一刻热点 key 失效，成千请求同时回源；
- **雪崩**：大量 key 或整个缓存层同时失效，影响面从一个热点扩大到大量请求。

判断题型的核心是：数据是否存在、影响一个 key 还是一批 key、缓存节点是否整体异常。

### 穿透：先挡住“不可能存在”

防护顺序可以是：

1. 参数格式、权限和 ID 范围校验；
2. 布隆过滤器快速拒绝“一定不存在”的 key；
3. 数据库确认不存在后缓存空值，并设置较短 TTL；
4. 对异常来源限流，避免缓存防线被随机 key 绕过。

布隆过滤器有假阳性：它说“可能存在”时仍需访问后端；它说“一定不存在”时才能直接拒绝。数据新增后还要更新过滤器，否则可能误拦真实新数据。

### 击穿：只允许少量请求重建

典型 singleflight 流程：

```text
热点 key 过期
  → 第一个请求获得重建权并查询数据库
  → 其他请求等待、返回旧值或快速失败
  → 重建完成后统一读取新值
```

互斥重建要设置锁租约与等待上限。另一种方案是“逻辑过期”：物理缓存先不删除，发现逻辑时间过期后由一个后台任务刷新，其他请求暂时读取旧值。它用短暂陈旧换稳定延迟，适合允许最终一致的场景。

### 雪崩：保护数据库比缓存命中更重要

TTL 随机抖动只能解决“同一时刻批量过期”。如果 Redis 集群不可达，还需要：

- 本地缓存或静态兜底；
- 回源并发上限与连接池隔离；
- 熔断、限流和非核心功能降级；
- 多可用区部署、故障转移与容量演练；
- 分批预热，避免恢复瞬间再次压垮数据库。

### 缓存与数据库一致性边界

即使不发生穿透、击穿或雪崩，旁路缓存仍可能读到旧数据。常见更新思路是先更新数据库，再删除缓存；若删除失败，需要重试或通过可靠事件补偿。不能把“双写数据库和缓存”简单描述成天然原子。

### 具体回答方式

不要只背三个定义，还要先保护数据库：

1. 设置总回源并发上限；
2. 对热点 key 使用 singleflight 或互斥重建；
3. 缓存空值时设置较短 TTL，避免长期掩盖后来写入的数据；
4. 布隆过滤器只能判断“可能存在 / 一定不存在”，不能替代数据库；
5. 缓存集群不可用时必须有降级和熔断，不能让所有请求无限回源。

### 面试中容易说错

- “缓存空值就解决穿透”：随机 key 会制造大量空值，还需校验、过滤和限流；
- “加随机 TTL 就解决雪崩”：它解决不了节点故障或网络隔离；
- “分布式锁能彻底解决击穿”：锁失败、超时、持有者崩溃和等待队列仍需处理；
- “布隆过滤器没有误判”：它可能把不存在判断为可能存在。

### 常见追问与回答

**互斥锁重建缓存有什么风险？**

锁持有者失败会让其他请求长期等待，因此需要租约、超时和失败兜底；极端热点还要考虑逻辑过期。

**随机 TTL 能彻底解决雪崩吗？**

只能减少同时过期。节点故障、网络隔离或错误发布导致的整体不可用仍需要高可用、限流与降级。

**逻辑过期适合什么场景？**

适合热点数据且业务能容忍短暂旧值的读场景。它不能直接用于余额、库存扣减等要求强一致的决策数据，除非另有权威校验。

**缓存和数据库都失败时怎么办？**

根据业务分级：核心写操作可能 fail-closed；非核心读可以返回本地快照、默认值或明确降级页。关键是预先定义，而不是故障时临时决定。
