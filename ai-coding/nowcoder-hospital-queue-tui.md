# 医院叫号系统（多端 TUI）

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>叫号系统的关键不是打印号码，而是同一患者只能处于一个合法阶段、多诊室并发叫号不能重复领取、优先患者不能让普通队列永久饥饿，并且所有变化都可追溯。</p>
</div>

## 资料边界

公开题单卡片给出的任务是：三个终端通过网络通信共享医院挂号队列。完整角色、优先规则和通信协议未公开。本页重建为挂号端、诊室端和候诊屏训练版，所有扩展规则均属于本站训练设计，不声称复原完整原题。

来源：[牛客 AI Coding 公开题单](https://aicoding.nowcoder.com/questionlist)。

## 训练题目

挂号端创建候诊记录，诊室端叫下一位、开始接诊、完成或过号，候诊屏只读展示当前叫号与等待列表。中心服务维护权威队列，支持多个诊室并发操作以及断线重试。

## 先定义患者状态与角色权限

可采用“等待—已叫号—接诊中—已完成”，并为取消和过号设置明确分支。候诊屏不能推进状态；挂号端不能替诊室完成接诊。过号后是回到队尾、进入独立队列还是必须重新挂号，需要向题目确认。

::: tip Prompt 01｜状态与权限表
```text
请把挂号端、诊室端、候诊屏的命令和患者状态做成权限矩阵。
每个命令写前置状态、成功状态、失败结果和审计字段。
过号后的去向未知，必须标记 UNKNOWN，不要代替医院制定规则。
```
:::

## 并发叫号必须由服务端原子裁决

两个诊室同时请求下一位时，不能都先读取队首再分别更新。服务端要把“选择队首并标记已叫号”视为一次原子命令。返回结果包含患者、诊室和版本，使重复请求能得到相同答案。

::: tip Prompt 02｜并发轨迹
```text
构造诊室 A、B 同时 call-next 的交错时间线。
列出哪些读写必须原子、如何确认每名患者只被一个诊室领取，以及失败重试如何避免跳过下一位。
不要用前端锁或按钮禁用解决服务端竞态。
```
:::

## 优先级必须能解释公平性

如果存在急诊或优先患者，先确认优先级来源、同优先级排序和防饥饿策略。仅用一个优先队列不代表公平。测试应包含持续插入高优先级患者时，普通患者的最大等待行为。

::: tip Prompt 03｜公平性审查
```text
针对普通与优先两类患者，比较绝对优先、配额轮转和等待时间提升三种策略。
说明各自需要的题意授权、不变量和饥饿风险。
若题目未给优先规则，只保留普通 FIFO，不自行扩展。
```
:::

## 显示屏是投影，不是事实源

候诊屏通过轮询或订阅读取服务端状态。消息丢失时应重新获取快照，而不是在本地继续推演。显示内容需要隐私最小化，训练数据可用号码或脱敏标识，不能把真实姓名与诊疗信息写入日志。

::: tip Prompt 04｜只读投影
```text
请设计候诊屏的快照字段、增量事件和重连流程。
区分可公开显示、仅诊室可见和不得记录的字段，并说明版本不连续时如何回退到全量同步。
不提供界面代码。
```
:::

## 审计记录必须与状态变化一致

每次挂号、叫号、过号、开始和完成都记录请求 ID、操作者、前后状态和时间。日志不能在事务提交前就宣称成功。发生争议时，应能从事件还原某个号码为何被某诊室叫走。

::: tip Prompt 05｜审计完整性
```text
审查当前命令结果和审计事件是否一一对应。
构造提交成功但响应丢失、事务回滚、重复请求和越权命令四种情况，说明日志中应出现什么、不应出现什么。
```
:::

## 验收矩阵

- FIFO 队列在没有优先规则时保持稳定顺序。
- 多诊室并发不会叫到同一患者。
- 重复请求不会跳过患者或重复完成。
- 候诊屏断线后以服务端快照收敛。
- 任何患者状态变化都有唯一审计记录。

::: tip Prompt 06｜交付复盘
```text
请按“规则确认—状态机—并发裁决—显示投影—审计证据”整理交付复盘。
指出至少一条 AI 曾擅自补充的医疗业务规则，以及我们为什么撤回它。
```
:::

## 面试复述

突出业务规则未知时的克制、并发 `call-next` 的原子性和患者隐私边界。能说清为什么候诊屏不能成为事实源，比做出更花哨的 TUI 更重要。
