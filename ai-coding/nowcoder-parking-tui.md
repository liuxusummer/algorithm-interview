# 停车场管理系统（多端 TUI）

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>三个终端共享停车记录时，真正的难点不是界面，而是谁拥有权威状态、并发入场如何裁决、重复命令怎样去重，以及终端断线重连后如何恢复一致视图。</p>
</div>

## 资料边界

公开卡片要求实现三个终端通过网络通信共享停车记录的 TUI 系统，考查系统设计、网络通信和状态机。终端名称、协议字段与计费细节未公开，本页重新设计为入口端、出口端和管理端训练版，不声称是完整原题。

来源：[牛客 AI Coding 公开题单](https://aicoding.nowcoder.com/questionlist)。

## 训练题目

入口端登记车辆并分配车位，出口端读取停车记录并完成离场，管理端查看占用情况和异常记录。三个终端只通过中心服务交换消息，不能各自维护互相覆盖的权威数据。交付包含运行说明、失败处理和可复现测试过程。

## 先确定单一事实源

中心服务负责车位和停车会话的权威状态；终端本地只缓存展示数据。若入口端和出口端都能直接修改共享文件，就无法定义冲突顺序，也无法在网络失败时判断哪一份是真的。

::: tip Prompt 01｜架构边界
```text
请根据三个终端的职责画出读写边界。
列出哪些状态只能由中心服务修改，终端允许缓存什么，以及每条命令的请求者、前置条件和返回结果。
不要一开始引入消息队列、微服务或分布式数据库。
```
:::

## 用状态机约束停车会话

训练状态可以是“已创建—已入场—待支付—已离场—已取消”。每个迁移要写前置条件和失败后状态。车位占用与停车会话必须原子更新，否则会出现会话成功但车位仍空闲，或反过来。

::: tip Prompt 02｜状态转换表
```text
为停车会话和车位写联合状态转换表。
覆盖重复入场、未入场先离场、同一车牌同时入场、车位已占用和已离场重复提交。
每行说明成功后的两个对象状态，以及失败时是否允许部分修改。
```
:::

## 网络重试要求命令幂等

出口端可能已提交离场，但在收到响应前断线。重试不能再次计费或释放其他会话。每个有副作用的命令携带稳定请求 ID；服务端记录结果，再次收到同一 ID 返回原结果。

::: tip Prompt 03｜重复命令时间线
```text
构造“服务端已提交、响应丢失、客户端重试”的离场时间线。
请指出幂等键作用域、结果保存时机和并发相同请求的裁决方式。
不要用客户端禁用按钮代替服务端幂等。
```
:::

## TUI 只负责呈现和意图

终端把输入解析成命令，展示服务端确认后的状态。不要在 TUI 中复制计费、车位选择或状态合法性规则。断线时显示最后成功同步时间和离线状态，禁止把本地猜测展示成已确认结果。

::: tip Prompt 04｜终端降级
```text
请为入口、出口和管理端分别设计断线、超时、无效输入和服务端拒绝时的界面反馈。
区分“本地待提交”“服务端已确认”“结果未知”三种状态，不提供 UI 代码。
```
:::

## 先做串行闭环，再测并发

最小闭环是登记一辆车、分配车位、查询、离场、释放车位。随后才加入两车争同一车位、同车重复入场、出口重复离场和服务重启恢复。AI 若直接生成多进程 TUI，调试面会成倍增加。

::: tip Prompt 05｜分阶段计划
```text
把 60 分钟任务拆成最小闭环、异常路径、并发验证和交付清理四阶段。
每阶段给可运行产物、停止条件和可以推迟的内容。
不得把“界面美化”排在状态一致性之前。
```
:::

## 验收矩阵

- 任一车位最多对应一个进行中的会话。
- 任一车牌最多有一个进行中的会话。
- 重复命令返回同一结果，不重复收费或释放。
- 终端断线不改变服务端状态，重连后可重新同步。
- 服务重启后已确认记录仍可解释。

::: tip Prompt 06｜一致性审查
```text
请从并发、重试、崩溃恢复和客户端缓存四个角度审查当前方案。
对每个风险给一条可重复的操作序列和必须检查的不变量。
不建议增加新基础设施，先验证当前单服务设计。
```
:::

## 面试复述

复述顺序是“权威状态—联合状态机—幂等命令—终端降级—并发不变量”。说明自己让 AI 先输出契约和测试轨迹，再分模块实现，避免三个终端各自产生一套冲突规则。
