# 批量任务迁移调度引擎

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>AI 很容易直接说“二分时间，再跑最大匹配”。真正的区分度在于先证明可行性随时间单调，定义某个时刻的边和容量，再让匹配结果同时成为答案与可核验见证。</p>
</div>

## 资料边界

牛客公开题单卡片给出的信息是：旧集群退役时，需要找到最早可迁移时刻和任务到服务器的分配；任务需求与服务器容量随时间线性变化，规模最多约 5,000 个任务。完整输入格式与所有业务规则未公开，因此本页根据公开摘要重新设计训练过程，不声称复原完整原题。

来源：[牛客 AI Coding 公开题单](https://aicoding.nowcoder.com/questionlist)。

## 训练题目

给定一批待迁移任务和候选服务器。任务在时刻 `T` 的资源需求、服务器在时刻 `T` 的可用容量均由题目给定的线性函数确定；兼容性规则决定某任务能否放到某服务器。找出最早存在合法整体分配的时刻，并输出一组可验证的任务—服务器分配。

训练时先向面试官确认四件事：一个服务器能接一个还是多个任务，多维资源是逐维比较还是可折算，时间是整数还是连续值，线性函数是否保证可行性只会从“否”变成“是”。最后一项若不成立，二分答案就没有依据。

## 第一步：把业务名词翻译成判定问题

固定一个候选时刻 `T`，先不求最早，只回答“此时能否完成全部迁移”。如果每台服务器只能接一个任务，可将任务和服务器建成二分图；存在边表示兼容且容量满足。若服务器可接多个任务，问题可能变成带容量匹配或装箱，算法模型会完全改变。

::: tip Prompt 01｜约束澄清
```text
下面只有公开摘要和我整理出的字段，请不要直接给算法。

请把会改变问题模型的歧义列成确认表：时间取值、服务器容量、任务可拆分性、兼容性、输出见证、无解约定。
每一项说明不同答案分别会把问题变成什么模型；未知项必须标记 UNKNOWN。
```
:::

## 第二步：先证明单调性，再谈二分

需要证明：若时刻 `T` 可行，则所有更晚时刻也可行。只有在任务需求不增、服务器容量不减，且兼容关系不随时间恶化时，这个结论才自然成立。若某个线性函数会反向变化，AI 给出的二分模板可能稳定地产生错误答案。

::: tip Prompt 02｜单调性审判
```text
请审查命题“可行(T) => 可行(T+1)”。
分别列出任务需求、服务器容量和兼容关系必须满足的条件，并给出一个最小反例说明任一条件缺失时为何不能二分。
不要写实现；只输出证明骨架、反例和仍需确认的题意。
```
:::

## 第三步：设计可行性判定器

判定器的职责只有三个：计算时刻 `T` 的需求与容量、构建合法边、判断能否覆盖所有任务。不要在判定器里同时更新二分边界。分层后，边界错误、图构建错误和匹配错误才能被独立定位。

::: tip Prompt 03｜判定器契约
```text
为 feasible(T) 写一份接口契约，不提供代码。
契约必须说明输入、输出、无副作用要求、溢出风险、图的节点与边定义，以及成功时如何返回完整匹配见证。
最后给出三个能分别击穿“容量比较”“兼容边”“匹配覆盖率”的最小样例。
```
:::

## 第四步：把复杂度写进设计

5,000 个任务意味着不能默认构造稠密图后反复做昂贵匹配。先估计二分次数、每次建边量和匹配成本，再寻找结构：容量是否可排序、兼容集合是否是区间、服务器是否可分组。优化必须来自题目结构，不能让 AI 凭空声称“用 Hall 定理即可做到线性”。

::: tip Prompt 04｜复杂度预算
```text
规模上限是 5,000。请按“二分次数 × 单次建图 × 单次匹配”给出最坏时间和空间预算。
如果预算超标，只列出需要从题面确认的可利用结构，以及每种结构允许的优化方向。
不要编造题面没有给出的排序性或区间性。
```
:::

## 第五步：用见证审查 AI 结论

仅返回 `true` 不足以证明判定正确。成功时逐项检查每个任务恰好出现一次、服务器占用不超限制、每条分配边确实兼容。最早时刻还要验证 `T` 可行且前一个合法时刻不可行。

::: tip Prompt 05｜最小性与见证审查
```text
我会提供候选时刻 T、匹配结果和 T-1 的失败摘要。
请生成一张验收清单：覆盖性、唯一性、容量、兼容、最早性、整数边界和溢出。
发现证据不足时只指出缺口，不要替我假设结果正确。
```
:::

## 对抗性样例

- 单个任务刚好在边界时刻可放置，暴露 `<` 与 `<=`。
- 每个任务都有候选服务器，但整体无法完美匹配，暴露“局部可选等于全局可行”的误判。
- 多个任务只能争用同一台服务器，检验覆盖性。
- 很晚仍无解，检验上界扩张和无解协议。
- 线性计算接近整数上限，检验中间乘法溢出。

::: tip Prompt 06｜交付前反方评审
```text
请以严格评审者身份攻击当前方案。
优先寻找：未经证明的单调性、把多容量问题误建成普通匹配、只判真不验见证、二分边界遗漏、复杂度估计过于乐观。
每个问题给出一个可执行的验证动作，不写替代实现。
```
:::

## 面试复述

按“先确认模型—证明单调—隔离判定器—输出匹配见证—验证最早性—审查复杂度”复述。必须主动说明：如果服务器可容纳多个任务或可行性不单调，当前方案需要退回重新建模，而不是继续套二分与普通匹配。
