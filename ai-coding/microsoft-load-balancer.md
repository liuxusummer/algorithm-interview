# 最小负载调度器

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>这页不展示最终算法代码，而是训练你如何把自然语言调度规则变成状态不变量，怎样约束 AI 提出方案，以及在 AI 给出“几乎正确”的实现后用反例定位错误。</p>

## 资料边界

一份 Microsoft SDE2 社区面经记录了 AI 辅助现场编码中的负载均衡题。候选人使用 Claude，
面试官关注澄清问题、调试和纠正 AI 输出。原帖没有完整题干，本页依据公开的“双最小堆”线索
设计等价训练题。

来源为[Microsoft AI assisted coding interview experience](https://www.reddit.com/r/leetcode/comments/1sfgtu3/ai_assisted_coding_interview_experience_microsoft/)。

## 训练题目

有多台带权重和编号的服务器，请求按时间到达。空闲服务器中优先选择权重小者，权重相同时选择
编号小者；没有服务器空闲时，请求等待到最早完成时刻；同一时刻完成的服务器要全部释放后再
选择。返回每个请求对应的服务器编号。

## 先问清五个边界

1. 请求是否严格按到达时间给出，多个请求能否同时到达。
2. 服务器在 `开始时间 + 处理时长` 时是否立即可用。
3. 没有空闲服务器时，逻辑时间如何推进。
4. 同时释放多台服务器时，是先全部释放还是遇到第一台就分配。
5. 权重和编号的并列规则是否在所有分支保持一致。

::: tip Prompt 01｜只做规则审查
```text
不要写代码。请把下面的调度题改写成无歧义规则。
[粘贴题目]

输出：
- 状态变量；
- 每个请求到达前必须成立的条件；
- 空闲服务器选择顺序；
- 忙碌服务器释放顺序；
- 时间推进规则；
- 需要向面试官确认的歧义；
- 5 个最小边界样例。

任何题目未说明的行为标为 UNKNOWN，不要自行选择。
```
:::

AI 如果一上来回答“双堆即可”，还不算完成分析。数据结构名称不能替代状态迁移规则。

## 用两个集合描述系统，而不是背模板

每个时刻，服务器只可能处于空闲或忙碌两种状态。

```text
空闲集合：按 权重 → 编号 排序
忙碌集合：按 完成时间 → 权重 → 编号 排序

处理请求前：释放完成时间不晚于当前时刻的全部服务器
若空闲集合为空：跳到最早完成时刻，再释放该时刻的全部服务器
分配后：服务器从空闲集合移动到忙碌集合
```

这里的“全部”是高频错误点。AI 常生成只弹出一个最早完成服务器的流程，普通样例能过，同时
释放时就会违反权重和编号规则。

## 第二轮：让 AI 写不变量，不要写实现

::: tip Prompt 02｜状态不变量
```text
基于已经确认的调度规则，写出处理第 i 个请求之前、释放服务器之后、完成分配之后分别必须成立的
不变量。不要给代码。

对每条不变量说明：
1. 它防止什么错误；
2. 哪个最小样例可以破坏错误实现；
3. 人工走查时需要观察哪些状态。

特别检查：完成时间等于当前时间、空闲集合为空、同一时刻多台完成、相同权重。
```
:::

好的不变量应包含“两个集合互斥且覆盖所有服务器”“忙碌集合中不会残留已到期服务器”“选择前
所有同一最早时刻完成的服务器均已转为空闲”等内容。

## 第三轮：先手算，再允许 AI 提方案

准备三个短轨迹。

- 一台服务器连续处理，验证时间推进。
- 两台相同权重服务器同时释放，验证编号规则。
- 三台不同权重服务器在等待后同时可选，验证必须全部释放。

::: tip Prompt 03｜生成状态表
```text
不要写代码。请对下面输入逐请求生成状态表。

服务器：(编号 0, 权重 3)、(编号 1, 权重 3)、(编号 2, 权重 2)
任务时长：1, 2, 3, 2, 1, 2

每行包含：请求编号、实际开始时间、释放了哪些服务器、分配前空闲集合、选中服务器、完成时间。
每一步引用对应的调度规则。如果存在歧义先停止并提问。
```
:::

人工核对这张表。后续任何实现只要与状态表不一致，就优先检查规则，而不是立刻修改代码。

## 第四轮：让 AI 比较方案，而不是指定答案

::: tip Prompt 04｜方案评审
```text
现在比较三种方案：每次扫描全部服务器、单优先队列、空闲与忙碌两个优先队列。

不要写实现。分别说明：
- 能否直接表达两套排序；
- 每个请求最坏操作次数；
- 时间推进如何处理；
- 最容易写错的边界；
- 在当前约束下推荐哪种，以及为什么。

如果一个方案需要额外假设，请明确列出。
```
:::

这一步让你能解释为何选择数据结构，而不是说“因为这是经典题”。

## AI 给出错误实现后，怎么定位

假设生成结果在常规样例正确，但同时释放样例错误。不要说“请修复 bug”，而要先形成一个可证伪
假设：释放循环可能使用了严格小于，或者只释放了一台服务器。

::: tip 调试 Prompt 01｜只做根因排序
```text
现象：常规样例通过；当两台服务器在时间 5 同时完成时，程序选了先进入忙碌集合的服务器，
而不是权重更小的服务器。

下面给出规则、失败轨迹和相关控制流摘要。
[粘贴信息]

请提出最多三个根因假设，按可能性排序。每个假设给：
- 它如何解释当前现象；
- 需要观察的一个状态；
- 什么结果能证伪它。

先不要给补丁，不要重写数据结构。
```
:::

观察结果返回后，再要求最小修改建议。

::: tip 调试 Prompt 02｜最小修改与回归范围
```text
观察结果：逻辑时间推进到 5 后，只从忙碌集合移动了一台服务器；另一台完成时间也为 5。

请说明最小修复应该维护哪条不变量，并列出修复后必须重跑的 4 类轨迹。
不要修改公开接口，不要提出额外抽象，不要输出整份文件。
```
:::

## 你要主动识别的 AI 常见错误

1. 用 `< 当前时间` 而不是“完成时间不晚于当前时间”。
2. 空闲集合为空时只释放堆顶一台服务器。
3. 时间推进后仍按原始到达时间计算完成时间。
4. 忙碌集合的排序漏掉权重和编号，导致并列行为不稳定。
5. 在两个集合中同时保留同一台服务器的陈旧状态。
6. 复杂度分析只写排序成本，没有计算每台服务器的入堆出堆次数。

::: tip Prompt 05｜逐条审查生成结果
```text
请根据已确认的不变量审查当前实现，但不要改代码。

逐项回答：
- 到期服务器是否全部释放；
- 等待时逻辑时间是否正确推进；
- 完成时间是否基于实际开始时间；
- 两个集合是否互斥；
- 所有并列键是否完整；
- 每个元素最多进出各集合多少次。

每个结论引用对应控制流或状态变化。不能确认时写 UNKNOWN。
```
:::

## 如何证明修复不是碰巧

需要保留四类证据。

- 失败样例修复前后的状态轨迹。
- 等于边界、同时释放和等待推进的独立样例。
- 随机小规模输入与朴素模拟结果的对照。
- 复杂度说明与集合不变量。

这些证据比“测试全绿”的截图更有解释力，因为它们说明你知道错误为什么发生。

## 45 分钟现场节奏

- **0—7 分钟**：澄清规则，写两个集合和五个边界。
- **7—15 分钟**：手算短轨迹，写不变量。
- **15—25 分钟**：让 AI 比较方案，确认最小实现计划。
- **25—35 分钟**：实现并逐轨迹验证。
- **35—41 分钟**：用同时释放、等待和相同权重做对抗测试。
- **41—45 分钟**：解释一处 AI 错误、修复依据、复杂度和剩余风险。

## 面试复述模板

先用两套排序和状态不变量解释方案，再展示一个同时释放的失败轨迹；说明 AI 最初建议哪里“几乎
正确”、你如何用观察证伪并缩小到根因；最后用回归轨迹证明修改没有破坏时间推进。重点始终是
你的判断过程，而不是模型生成了多少代码。
