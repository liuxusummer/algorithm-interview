# 通讯录前缀查询 API 服务

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>“前缀查询”只是表面。真正要先确认号码规范化、重复联系人、更新删除和批量失败语义，再选择 Trie、排序索引或简单扫描。AI 不应在契约尚未确定时先造复杂数据结构。</p>
</div>

## 资料边界

公开卡片要求实现支持单条录入、批量操作和号码前缀计数查询的 HTTP API，考查前缀数据结构与批处理。完整字段、规模和错误协议未公开，本页根据公开摘要重建训练任务，不声称复原完整原题。

来源：[牛客 AI Coding 公开题单](https://aicoding.nowcoder.com/questionlist)。

## 训练题目

服务保存联系人 ID、姓名和号码，提供单条新增、批量新增或删除、按号码前缀统计数量与健康检查。所有查询基于规范化号码；批量命令的原子性和重复请求行为必须在接口文档中明确。

## 号码规范化先于索引

先确认空格、短横线、国家码、前导零和分机如何处理，以及输出保留原值还是规范值。索引必须基于唯一规范；若写入和查询采用不同规则，再正确的 Trie 也会返回错误答案。

::: tip Prompt 01｜规范化决策表
```text
请把号码输入的空白、短横线、括号、国家码、前导零、分机和非法字符整理成决策表。
每项写存储值、索引值、查询值和错误结果。
题目未说明的规则标记 UNKNOWN，不参考现实通讯录自行决定。
```
:::

## 先估算规模，再选索引

小规模可用排序数组加前缀上下界，大规模高频查询可考虑 Trie；更新频繁时要评估删除和节点计数维护。方案比较必须包含内存、构建、单次增删与查询成本，不能只说 Trie 是前缀题标准答案。

::: tip Prompt 02｜结构选择审查
```text
根据联系人数量、号码最大长度、读写比例和内存限制，比较线性扫描、排序索引与 Trie。
列出每种方案的适用前提、增删查复杂度和最难验证的不变量。
缺少规模时给保守方案和需要追问的数据。
```
:::

## 索引与主存储必须同步

新增、删除或批量写入要同时改变联系人仓库和前缀计数。任何一步失败都不能留下孤立记录或脏计数。若采用 Trie，节点计数必须明确代表“经过该前缀的号码数”还是“不同联系人数量”。

::: tip Prompt 03｜索引不变量
```text
请为主存储与前缀索引列出一致性不变量。
覆盖重复号码、同一联系人多个号码、删除不存在记录、更新号码和批量部分失败。
每条不变量给一个独立重算或对账方法。
```
:::

## 批量 API 要先选语义

全有全无适合配置导入，逐项结果适合尽可能接收。两者都要定义重复项、顺序、最大批量、错误位置和重试行为。不要让 AI 默默跳过错误行然后返回整体成功。

::: tip Prompt 04｜批量失败轨迹
```text
对包含“合法、重复、非法、合法”四条记录的批次，分别推演原子模式与逐项模式。
列最终数据、索引计数、响应结构和重试结果。
指出当前契约必须固定的选择，不给实现。
```
:::

## 用慢基线差分验证快索引

在测试规模内，用主存储逐条扫描计算前缀数量，和优化索引结果比较。随机生成增删查询序列并在每一步对账，比只写几个固定前缀更能发现计数没有回退或重复累计。

::: tip Prompt 05｜差分测试
```text
设计“简单扫描真值器 vs 优化索引”的随机操作序列。
列出生成约束、每步比较内容、失败时应保存的最小轨迹，以及如何缩减为可读反例。
不要让两个实现共享同一计数逻辑。
```
:::

## 验收清单

- 写入与查询使用同一规范化版本。
- 空前缀、完整号码、不存在前缀和超长前缀语义明确。
- 批量失败后主存储和索引一致。
- 重复请求不会重复计数。
- 优化索引通过慢基线差分验证。

::: tip Prompt 06｜交付前审查
```text
请从规范化漂移、重复计数、删除回退、批量原子性、并发更新和内存膨胀六个角度攻击当前设计。
每项给一个最小 API 操作序列和应检查的计数，不写实现。
```
:::

## 面试复述

从号码语义开始，再讲索引。最有说服力的证据是使用独立慢基线对随机增删查询序列做差分，而不是只说明自己用了 Trie。
