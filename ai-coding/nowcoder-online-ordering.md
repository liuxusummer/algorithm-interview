# 在线点餐系统 Web 版

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>菜单、购物车和下单很容易被 AI 一次生成，但 VIP 折扣、起送金额与满额免配送的计算顺序往往互相冲突。先做规则决策表和订单价格流水线，再让 AI 修改界面。</p>
</div>

## 资料边界

公开卡片要求实现菜单浏览、购物车和订单提交，并处理 VIP 折扣、起送金额、满额免配送等规则。完整视觉稿、阈值和后端接口未公开。本页采用公开功能重新设计训练过程，不声称复原完整原题。

来源：[牛客 AI Coding 公开题单](https://aicoding.nowcoder.com/questionlist)。

## 训练题目

在现有三层 Web 项目中完成一条可演示链路：浏览菜单、修改购物车、查看价格明细、提交订单、展示结果。菜单价格与优惠资格由服务端权威计算；前端可以即时预览，但下单成功以服务端返回为准。

## 先问清价格规则的顺序

至少确认起送金额看原价还是折后价，免配送门槛看商品金额还是订单总额，VIP 折扣是否包含配送费，以及多个优惠能否叠加。把每条规则写成输入、条件、结果和优先级。

::: tip Prompt 01｜价格决策表
```text
请把 VIP 折扣、起送金额、配送费和满额免配送整理成决策表。
对每条规则列计算基数、执行顺序、边界是否包含等号和冲突时优先级。
未知项标记 UNKNOWN，不要按常见外卖平台规则自行补齐。
```
:::

## 金额计算只能有一个权威实现

前端预览与后端最终计算若各写一套规则，很快会漂移。训练时将价格规则放在可复用领域层或由后端统一返回价格预览；前端展示商品小计、折扣、配送费和应付，而不是自己拼最终金额。

::: tip Prompt 02｜契约与所有权
```text
请为菜单、购物车预览和提交订单列接口契约。
标出每个金额字段由谁计算、客户端能否提交、服务端必须重新校验什么，以及价格变化时返回什么错误。
不要把客户端传来的 total 当成可信事实。
```
:::

## 购物车需要稳定身份和状态

同一菜品数量归并，数量为零时移除；下架或价格变化要在提交时处理。重复点击提交不能创建多份订单。页面刷新后是否恢复购物车属于产品选择，应由题目决定。

::: tip Prompt 03｜购物车状态机
```text
把购物车从空、可编辑、提交中、成功、失败拆成状态和事件。
覆盖重复点击、请求超时、菜品下架、价格变化、数量越界和返回页面。
只给状态转换与交互反馈，不写组件代码。
```
:::

## 先做纵向闭环

先用两道固定菜品跑通“加入—预览—提交—结果”，再增加筛选、样式和持久化。AI 一次生成菜单页、购物车页、订单页和复杂状态库，会把错误分散到过多文件。

::: tip Prompt 04｜最小改动计划
```text
这是现有目录、启动命令和测试入口。
请规划一个最小纵向闭环，列出必须查看和可能修改的文件、每步验收条件及可推迟功能。
在我确认调用链前不要生成代码，也不要引入新的状态管理库。
```
:::

## 边界样例比截图更重要

准备门槛少一分、刚好、加一分；VIP 与非 VIP；配送费免与不免；空购物车；菜品下架；重复提交。页面看起来正确并不能证明金额规则正确。

::: tip Prompt 05｜订单金样
```text
根据规则表生成最小订单金样。
每个样例列商品小计、折扣、配送费、应付和它验证的边界。
预期值必须按规则逐步人工推导，不允许直接复用待测计算函数。
```
:::

## 交付证据

- 一条完整演示路径和一条失败路径。
- 前后端金额字段契约。
- 门槛边界金样全部通过。
- 重复提交只生成一个订单或得到明确幂等结果。
- diff 没有无关框架升级和大范围重构。

::: tip Prompt 06｜交付前审查
```text
请从金额可信性、重复提交、错误恢复和无障碍交互四个角度审查当前交付。
列出证据充分的部分、仍缺测试的部分和必须在 README 声明的限制。
不要用界面截图代替业务验证。
```
:::

## 面试复述

复述从规则表开始，讲清金额权威、前后端契约和门槛金样。最后说明哪些装饰功能被主动推迟，以及为什么这比在 60 分钟内堆更多页面更可靠。
