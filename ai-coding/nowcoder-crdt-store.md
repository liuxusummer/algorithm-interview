# CRDT 数据类型存储

<div class="ai-trend-callout">
  <strong>训练重点</strong>
  <p>CRDT 题最危险的做法是让 AI 凭记忆生成四个类。高质量作答先写清每个类型的状态、更新与合并语义，再用交换、结合、幂等三条性质持续审查。</p>
</div>

## 资料边界

公开卡片要求实现 `G-Counter`、`PN-Counter`、`LWW-Register` 和 `OR-Set` 的 CRDT 存储，考查分布式系统与最终一致性。完整接口和冲突规则未公开，本页据此重建训练任务，不声称是完整原题。

来源：[牛客 AI Coding 公开题单](https://aicoding.nowcoder.com/questionlist)。

## 训练题目

实现四种可在多个副本独立更新、随后反复合并的数据类型。网络允许重复、乱序和延迟投递；合并同一状态多次不能改变结果。训练重点是语义设计、AI 生成结果审查和性质验证，不展示成品实现。

## 先建立语义表

| 类型 | 最小状态 | 本地更新 | 合并直觉 | 最易错点 |
|---|---|---|---|---|
| G-Counter | 每副本递增分量 | 只增本副本 | 逐分量取最大 | 合并时求和导致重复计数 |
| PN-Counter | 正、负两个 G-Counter | 分别递增 | 两部分独立合并 | 负分量符号混乱 |
| LWW-Register | 值、时间、稳定决胜键 | 替换候选 | 选择最大版本 | 同时间戳不确定 |
| OR-Set | 元素的唯一添加标签与删除记录 | add/remove | 集合并集 | 删除旧标签误伤未来重加 |

::: tip Prompt 01｜先写语义，不写类
```text
请把四种 CRDT 分别整理成“状态、查询、更新、合并、冲突决胜”五列表格。
所有假设都要显式说明，尤其是副本 ID、时间戳来源、唯一标签和删除语义。
暂时不要给类定义或方法实现。
```
:::

## 用代数性质约束 AI

状态型 CRDT 的合并需要满足交换律、结合律和幂等律。测试不能只写两个副本合并一次，还要改变顺序、增加重复合并并按不同括号结合。最终查询值一致只是结果，内部状态也应保持可继续合并。

::: tip Prompt 02｜性质测试矩阵
```text
为 merge(a, b) 设计性质测试。
覆盖交换律、结合律、幂等律、本地状态单调增长，以及同一更新被重复传输。
每条性质给最小状态样例和失败时最可能暴露的实现错误，不写测试代码。
```
:::

## LWW 不等于只比较本机时间

如果两个副本时间戳相同，必须有稳定决胜键，否则 `merge(a,b)` 与 `merge(b,a)` 可能返回不同值。还要说明时间戳由调用者提供还是内部生成；在分布式系统里直接信任墙上时钟会带来时钟回拨和偏移风险。

::: tip Prompt 03｜寄存器冲突审查
```text
审查 LWW-Register 的版本比较规则。
请构造：相同时间戳不同值、时钟回拨、重复消息、旧状态晚到四种轨迹。
只判断现有规则是否确定、是否满足交换与幂等；缺少决胜规则时明确拒绝生成实现。
```
:::

## OR-Set 要区分“值”和“这次添加”

删除元素时，删除的是当前观察到的添加标签。并发发生的全新添加标签不应被尚未观察到它的删除操作抹掉。若 AI 只维护普通集合或一个 `removed_values` 集合，就无法正确表达并发重加。

::: tip Prompt 04｜并发轨迹推演
```text
元素 x 在副本 A、B 上经历并发 add、remove、再次 add。
请用事件时间线列出每一步的唯一标签、已观察标签和查询结果。
比较“按值删除”和“按已观察标签删除”的差异，不给实现。
```
:::

## API 与序列化也是语义的一部分

副本 ID、唯一标签和版本决胜键必须能序列化并稳定恢复。反序列化后继续合并，行为应与未重启相同。不要让 AI 把集合转成无序列表后又依赖其顺序，也不要把元组键悄悄转换成不可比较的混合类型。

::: tip Prompt 05｜持久化边界
```text
下面是状态序列化格式草案。
请检查信息是否足以在重启后保持合并语义，重点审查副本身份、唯一标签、时间戳精度、集合顺序和版本兼容。
输出缺失字段、向后兼容风险和恢复后必须重跑的性质测试。
```
:::

## 验证顺序

1. 单副本更新与查询。
2. 两副本不同顺序合并。
3. 三副本不同括号结合。
4. 重复、乱序、延迟消息。
5. 序列化—恢复—继续更新—再次合并。
6. 并发删除与重加。

::: tip Prompt 06｜最终审查
```text
请把当前设计当作会遇到重复和乱序消息的生产组件审查。
逐项回答四个类型是否满足交换、结合、幂等，哪些结论有测试证据，哪些只是推断。
禁止用“最终会一致”代替具体状态轨迹。
```
:::

## 面试复述

先讲“CRDT 的核心是合并代数，不是类的数量”，再用 OR-Set 的唯一标签和 LWW 的稳定决胜规则展示自己纠正 AI 的过程。最后给出性质测试证据，而不是只演示一次正常合并。
