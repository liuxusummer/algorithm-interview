第一部分共 20 题，其中前 15 题为单选题，后 5 题为多选题。下面保留完整题干和全部选项，并在答案之后讲清判断过程。

### 1. 工单摘要如何抑制幻觉

**题目**

后端团队接入大模型生成工单摘要，希望模型不要编造原始工单中没有的信息。更合适的提示约束是？

- A. 提高生成随机性，让模型输出更多候选表达
- B. 限定依据原始工单内容总结，缺失信息标为未提供
- C. 把摘要长度固定得更长，以容纳更多推测细节
- D. 要求模型优先补充背景原因，使摘要看起来更完整

**答案：B**

**逐项解析**

- A 错误。提高随机性通常会增大输出的不确定性，不能解决事实无依据的问题。
- B 正确。它同时限定了事实来源，并为缺失信息提供了合法的回答出口，模型没有必要凭空补全。
- C 错误。输出更长只会提供更多产生无依据细节的机会。
- D 错误。要求“补充”原始工单里不存在的背景，恰好是在鼓励幻觉。

**知识点**

抑制幻觉的基础写法是“**证据边界 + 缺失信息处理 + 输出约束**”。例如：

> 仅依据 `<ticket>` 中的内容总结；没有提及的信息写“未提供”；不要根据常识推断原因；每个结论附上对应原文。

提示词只能降低风险。高风险业务还应配合检索来源记录、置信度阈值、人工复核和离线评测。

### 2. Linux 文件权限

**题目**

Linux 文件权限显示为 `-rw-r-----`。若某用户属于该文件所属组，但不是文件所有者，则该用户对该文件通常具有什么权限？

- A. 仅可读
- B. 无权限
- C. 可执行但缺少读取权限
- D. 可读可写

**答案：A**

**逐项解析**

权限串可以拆为 `- | rw- | r-- | ---`：

- 第一个字符 `-` 表示普通文件；
- `rw-` 是文件所有者权限；
- `r--` 是文件所属组权限；
- `---` 是其他用户权限。

题目中的用户命中“所属组”这一段，因此只有读权限。B、C、D 都与 `r--` 不符。

**知识点**

`r/w/x` 分别对应读、写、执行。数字表示法中 `r=4`、`w=2`、`x=1`，所以该权限也可写成 `640`。目录上的 `x` 不是“执行目录”，而是允许进入并访问其中的目录项。

### 3. RAG 中的过期制度

**题目**

某制度问答系统采用 RAG，但用户发现回答会引用过期制度。检索日志显示 topK 片段相似度较高，但混有旧版本制度。下列改进更能直接缓解该问题的是？

- A. 提高生成 `temperature`，让模型用更丰富表述融合多版制度内容
- B. 缩短最终答案长度，减少暴露过期引用细节的机会
- C. 在召回和重排阶段加入版本、生效时间和来源过滤，再注入命中片段
- D. 继续扩大 topK，使新旧版本都有机会进入上下文，由模型综合判断

**答案：C**

**逐项解析**

- A 错误。温度影响生成随机性，不负责判断制度是否有效。
- B 错误。答案变短并没有移除错误证据。
- C 正确。在证据进入模型前依据元数据过滤，是解决版本污染最直接、可审计的手段。
- D 错误。扩大 topK 会进一步增加冲突片段，反而提高模型选错版本的概率。

**知识点**

RAG 不应只做向量相似度检索。生产系统常见流程是：

1. 按租户、权限、来源、版本、生效时间做硬过滤；
2. 在合格候选中做向量召回；
3. 用重排模型进一步排序；
4. 把来源、版本和引用位置一并交给生成模型。

“语义相似”不等于“业务上有效”，时效性与权限通常必须作为结构化条件处理。

### 4. 不可重复读

**题目**

事务 T1 第一次读取某行余额为 100。事务 T2 随后提交更新，把该余额改为 120。T1 在同一事务内再次读取同一行得到 120。该现象更贴近哪类并发读问题？

- A. 幻读：条件范围内行集合变化
- B. 死锁：事务之间形成循环等待
- C. 不可重复读：同一行两次读取变化
- D. 脏读：读取其他事务未提交数据

**答案：C**

**逐项解析**

T1 两次读取的是同一行，而这一行的值从 100 变为 120，符合不可重复读。T2 已经提交，因此不是读取未提交数据的脏读；题目也没有出现范围查询结果行数变化，所以不是幻读；更不存在相互等待，不能称为死锁。

**知识点**

- **脏读**：读到了其他事务尚未提交的数据；
- **不可重复读**：同一事务内，同一行前后读取的值不同；
- **幻读**：同一范围条件前后查询得到的行集合不同；
- **死锁**：多个事务形成循环等待，谁都不能继续。

做题时先看“是否提交”，再看变化的是“行的值”还是“行的集合”。

### 5. 活动选择的贪心策略

**题目**

给定若干活动的开始和结束时间，希望选出数量最多的互不重叠活动。下列贪心策略通常可用于该问题并可通过交换论证证明正确的是？

- A. 每次选择开始时间最早的可选活动
- B. 每次选择与其他活动重叠最多的活动
- C. 每次选择持续时间最长的可选活动
- D. 每次选择结束时间最早的可选活动

**答案：D**

**逐项解析**

选择结束时间最早的活动，会给后续活动留下尽可能大的时间范围。A 只保证开始得早，可能结束得很晚；B 和 C 更可能占用大量时间，都不能保证最优。

**知识点**

交换论证的核心是：设某个最优解的第一个活动为 $x$，贪心选择为 $g$，且 $g$ 最早结束。因为 $end(g)\le end(x)$，把最优解中的 $x$ 换成 $g$ 不会影响后续活动，仍然是最优解。于是可以递归处理剩余活动。

### 6. 稳定排序

**题目**

某列表中存在多个排序键相同的记录，业务要求排序后这些记录仍保持原来的相对先后顺序。下列算法性质最贴近该要求的是？

- A. 稳定排序
- B. 外部排序
- C. 分治排序
- D. 原地排序

**答案：A**

**逐项解析**

“相等关键字的相对顺序不变”就是稳定排序的定义。外部排序描述数据是否主要在外存中处理，分治描述算法思想，原地排序描述额外空间使用，它们都不能单独保证稳定性。

**知识点**

归并排序、插入排序和冒泡排序通常可以稳定实现；堆排序和常规快速排序通常不稳定。稳定性在多关键字排序中特别有用：先按次关键字稳定排序，再按主关键字稳定排序，可以保留次关键字次序。

### 7. Precision 与 Recall

**题目**

某风控场景更关注减少误拦正常用户。验证集上模型 M1 的 TP=80、FP=20、FN=40，模型 M2 的 TP=70、FP=10、FN=50。若主要按“被判高风险的请求中确实高风险的比例”取舍，下列判断更合理的是？

- A. 选 M2：`Recall=70/(70+50)`，高于 M1 的 Recall
- B. 选 M2：`Precision=70/(70+10)`，高于 M1 的 Precision
- C. 选 M1：FP=20、FN=40，误拦更少且覆盖更高
- D. 选 M1：`Precision=80/(80+20)`，`Recall=80/(80+140)`

**答案：B**

**逐项解析**

题干中的“被判高风险的请求中确实高风险的比例”正是精确率：

$$
Precision=\frac{TP}{TP+FP}
$$

M1 的精确率为 $80/(80+20)=0.8$，M2 的精确率为 $70/(70+10)=0.875$，因此选 M2。

- A 错误：M2 的召回率 $70/120$ 低于 M1 的 $80/120$。
- C 错误：M2 的 FP 更少，才更符合减少误拦的目标。
- D 错误：Recall 的分母应为 $TP+FN$，不是 $80+140$。

**知识点**

- Precision 回答“判为正的有多少是真的”，关注误报；
- Recall 回答“真实为正的有多少被找出”，关注漏报；
- $F_1$ 是二者的调和平均，但业务若明确偏向一侧，就不应机械追求 $F_1$。

### 8. 用 shell 统计状态码

**题目**

某日志文件 `app.log` 中每行仅包含一个三位 HTTP 状态码且无其他内容。希望统计状态码 500 出现的行数，下列命令更符合该目标的是？

- A. `grep '500' app.log | wc -l`
- B. `grep -v '500' app.log | wc -c`
- C. `wc -l app.log | grep '500'`
- D. `cat app.log > grep '500' | wc`

**答案：A**

**逐项解析**

A 先筛出包含 `500` 的行，再用 `wc -l` 统计行数。B 的 `-v` 表示反向匹配，而且 `wc -c` 统计字节；C 先得到总行数再搜索数字 500，语义不对；D 的重定向和管道组合也不成立。

**知识点**

题目已经保证每行只有三位状态码，所以 A 足够。实际日志格式更复杂时，应使用精确匹配，例如：

```bash
grep -c '^500$' app.log
```

也可以用 `awk '$1 == 500 { count++ } END { print count }' app.log` 按字段处理。

### 9. 同一进程中的线程资源

**题目**

某后端服务把一个耗时任务拆成多个线程在同一进程内执行。下列关于这些线程与进程资源关系的说法较合理的是？

- A. 线程切换时会重新创建进程页表，因此开销通常高于进程切换
- B. 同进程线程共享同一地址空间，但各自有栈和调度上下文
- C. 多个线程并发执行时不涉及同步问题，因为它们共享同一份内存
- D. 线程拥有独立地址空间，线程间传递对象需要经过内核网络栈

**答案：B**

**逐项解析**

同一进程内的线程共享代码段、数据段、堆和文件描述符等资源，但各自拥有栈、寄存器、程序计数器和线程局部存储。共享内存正是竞争条件产生的原因，所以 C 错误。线程通常不拥有独立地址空间，也不需要通过网络栈传递普通内存对象，因此 D 错误。A 把线程切换与地址空间切换混为一谈。

**知识点**

线程比进程更轻量，但“轻量”不等于“无同步成本”。对共享可变状态仍要使用锁、原子变量、无锁结构或消息传递，并尽量缩短临界区。

### 10. 可恢复缺页异常

**题目**

某进程执行一条访存指令时发生可恢复缺页异常。内核完成页表更新并装入目标页后，若该处理器支持精确异常，用户态执行流通常如何恢复？

- A. 重启当前进程，从 `main` 函数入口重新执行
- B. 恢复到触发缺页的访存指令，由该指令重新执行
- C. 从异常处理程序入口继续执行原用户逻辑
- D. 跳过触发缺页的访存指令，从下一条指令继续执行

**答案：B**

**逐项解析**

缺页发生时，访存指令还没有成功完成。内核把页面装入并更新页表后，会恢复用户态上下文，让同一条故障指令重新执行。直接跳过会丢失这次读写；从 `main` 重启代价和语义都不正确；异常处理入口属于内核执行流程，不是用户程序的继续位置。

**知识点**

精确异常要求处理器能明确指出故障指令，并保证更早指令已完成、更晚指令尚未产生可见影响。这使操作系统可以修复页表后安全重试。

### 11. 支付回调的幂等性

**题目**

某支付回调接口可能因网络抖动被调用方重试。为了避免同一业务事件被重复处理，服务端设计中最关键的是？

- A. 要求客户端把超时时间调得更短，让失败更快暴露
- B. 在响应体中返回更详细日志，由调用方自行排查
- C. 按事件唯一编号做幂等校验，重复请求返回已处理结果
- D. 把接口从 HTTPS 改成 HTTP，降低 TLS 握手开销

**答案：C**

**逐项解析**

网络重试无法彻底避免，服务端必须假设同一事件可能到达多次。使用支付流水号或事件 ID 建立唯一约束，首次请求原子地完成业务处理并记录结果，后续重复请求直接复用结果，才能从业务层消除重复副作用。其他选项都没有解决“同一事件处理多次”的核心问题。

**知识点**

幂等设计通常包含：

1. 客户端或上游提供稳定的幂等键；
2. 数据库建立唯一索引，避免并发穿透；
3. 业务写入与幂等记录放在同一事务；
4. 重复请求返回一致结果，而不是仅返回“重复调用”错误。

### 12. 联合索引的最左前缀

**题目**

MySQL 表 `orders` 上有联合索引 `(user_id, status, create_time)`。下列查询条件最符合该索引最左前缀使用方式的是？

- A. `WHERE user_id = 1001 AND status = 1`
- B. `WHERE status = 1 ORDER BY user_id`
- C. `WHERE create_time > '2026-01-01'`
- D. `WHERE status = 1 AND create_time > '2026-01-01'`

**答案：A**

**逐项解析**

索引按 `user_id → status → create_time` 排列。A 从首列开始连续使用了两列，可以有效定位。B、C、D 都跳过了首列 `user_id`，通常不能利用这棵 B+ 树完成有效的前缀定位。

**知识点**

“最左前缀”不是要求 SQL 条件书写顺序与索引一致，而是要求查询约束能从索引首列连续匹配。遇到范围条件后，后续列通常不能继续用于缩小索引扫描范围，但仍可能用于索引下推或覆盖查询，需结合执行计划判断。

### 13. 二叉树节点计数

**题目**

一棵非空二叉树共有 29 个结点，其中度为 1 的结点有 6 个。按二叉树结点度数关系推断，该树中度为 2 的结点数为？

- A. 12
- B. 13
- C. 11
- D. 10

**答案：C**

**解析**

设度为 0、1、2 的结点数分别为 $n_0,n_1,n_2$。非空二叉树满足：

$$
n_0=n_2+1
$$

又因为：

$$
n_0+n_1+n_2=29,\qquad n_1=6
$$

代入得：

$$
(n_2+1)+6+n_2=29
$$

所以 $2n_2=22$，即 $n_2=11$。

**知识点**

这个关系可以从边数推出：一棵有 $n$ 个结点的树有 $n-1$ 条边；另一方面，所有结点的孩子数之和为 $n_1+2n_2$。因此

$$
n_0+n_1+n_2-1=n_1+2n_2
$$

整理后就是 $n_0=n_2+1$。

### 14. Function Calling 的安全边界

**题目**

某后端系统让大模型根据用户请求调用“查询订单”工具。关于 Function Calling 的执行边界，下列说法较合理的是？

- A. 模型输出调用请求，后端校验参数并执行工具
- B. 后端只校验参数格式，把用户身份和资源权限判断留到工具返回后再处理
- C. 模型生成结构化调用结果后直接写入业务数据库，不经过后端执行层
- D. 工具接口只写自然语言用途说明，参数约束由模型根据上下文临场补齐

**答案：A**

**逐项解析**

模型输出的函数名和参数只是一个**不可信的调用提议**。后端必须校验函数白名单、参数结构、用户身份、资源权限和业务约束，再决定是否执行。B 把鉴权放到了数据可能已经泄露之后；C 让模型绕过业务执行层；D 缺少机器可验证的参数契约，都不安全。

**知识点**

一个可靠的工具调用链路通常是：

```text
用户请求 → 模型提出调用 → JSON Schema 校验
         → 身份鉴权/资源授权 → 业务规则校验
         → 后端执行 → 结果脱敏 → 模型组织答案
```

提示词不能替代后端权限控制。模型和其输出都应被视为不可信输入。

### 15. 栈的操作顺序

**题目**

某服务按顺序接收操作：`push(4)`、`push(7)`、`pop`、`push(2)`、`push(9)`、`pop`、`pop`。若底层结构是栈，则三次 `pop` 得到的元素顺序为？

- A. 7、2、9
- B. 9、2、7
- C. 4、7、2
- D. 7、9、2

**答案：D**

**解析**

按后进先出逐步模拟：

| 操作 | 栈内容（右侧为栈顶） | 弹出 |
|---|---|---|
| `push(4)` | `[4]` | — |
| `push(7)` | `[4, 7]` | — |
| `pop` | `[4]` | 7 |
| `push(2)` | `[4, 2]` | — |
| `push(9)` | `[4, 2, 9]` | — |
| `pop` | `[4, 2]` | 9 |
| `pop` | `[4]` | 2 |

因此三次弹出依次得到 7、9、2。

**知识点**

栈是 LIFO（Last In, First Out，后进先出）结构。遇到混合操作题时，逐步画出栈状态比凭直觉倒推更可靠。

### 16. 大模型客服的幻觉与越权控制（多选）

**题目**

某后端团队建设大模型客服系统。为了降低幻觉和越权工具调用风险，下列设计较合理的有哪些？

- A. 允许模型在资料不足时根据常识补全具体制度条款，提高回答完整度
- B. 对低置信度或资料冲突的请求进入人工复核或返回无法判断
- C. 对工具调用参数做白名单校验和权限校验，再由后端执行
- D. 弱化检索片段来源和版本记录，把事实校验主要交给模型最终回答

**答案：B、C**

**逐项解析**

- A 错误。具体制度属于必须有来源的事实，用常识补全会制造幻觉。
- B 正确。为不确定请求提供降级出口，可以避免模型被迫硬答。
- C 正确。白名单、参数校验、鉴权和后端执行共同构成防越权边界。
- D 错误。来源与版本记录是事实可核验、可追溯的依据，不应弱化。

**知识点**

大模型安全不能只靠一句“不要越权”。至少要有三层控制：

1. **知识层**：可靠检索、版本过滤、引用溯源；
2. **决策层**：置信度阈值、冲突检测、拒答与人工复核；
3. **执行层**：工具白名单、参数校验、最小权限、审计与幂等。

### 17. 推荐模型上线评估（多选）

**题目**

某推荐服务上线新模型前，需要评估其离线效果和线上风险。下列做法较合理的有哪些？

- A. 上线前保留灰度或 A/B 实验方案，观察真实用户反馈
- B. 若训练集准确率很高，就可省略线上监控和回滚预案
- C. 关注与业务目标一致的指标，而不是只看训练损失
- D. 用独立验证集评估模型效果，避免只看训练集表现

**答案：A、C、D**

**逐项解析**

- A 正确。灰度和 A/B 实验能限制影响范围，并用真实流量验证效果。
- B 错误。训练集高分可能来自过拟合，且不能替代线上监控与回滚能力。
- C 正确。训练损失是代理指标，最终取舍应看点击、转化、留存、投诉率等业务目标。
- D 正确。独立验证集用于估计泛化能力，避免被训练集表现误导。

**知识点**

一个完整的上线闭环是“离线验证 → 小流量灰度/A-B → 线上指标与护栏监控 → 可快速回滚 → 复盘迭代”。效果指标之外，还要设置延迟、错误率、资源成本和负向反馈等安全护栏。

### 18. 联合索引与覆盖索引（多选）

**题目**

某订单表常用查询为：

```sql
WHERE user_id = ?
  AND status = ?
ORDER BY create_time DESC
LIMIT 20
```

关于索引执行代价的判断，正确的有哪些？

- A. 把 `create_time` 放在联合索引首列，仍能稳定利用 `user_id` 和 `status` 的等值过滤前缀
- B. 覆盖索引能否减少回表，还取决于 `SELECT` 列是否都在索引中
- C. 若只有单列索引 `status`，低选择性状态列过滤效果可能较弱
- D. 联合索引 `(user_id, status, create_time)` 有机会同时支持过滤和排序

**答案：B、C、D**

**逐项解析**

- A 错误。若 `create_time` 位于首列，查询没有对它提供可定位的等值前缀，后面的 `user_id` 和 `status` 不能稳定用于索引定位。
- B 正确。只有查询所需列都能从索引叶子节点取得时，才可能成为覆盖索引并避免回表。
- C 正确。状态列通常只有少量取值，单列索引筛完仍可能留下大量行，优化器甚至可能选择全表扫描。
- D 正确。前两列等值定位后，第三列 `create_time` 在索引中天然有序，可按倒序读取前 20 条，减少 `filesort`。

**知识点**

联合索引设计常用经验是“等值过滤列在前，范围或排序列在后”，但最终还要考虑选择性、查询列、更新成本和实际执行计划。用 `EXPLAIN ANALYZE` 验证，比只背口诀更可靠。

### 19. TCP 可靠传输（多选）

**题目**

关于 TCP 在后端服务通信中的可靠传输机制，下列说法正确的有哪些？

- A. TCP 会保留应用层消息边界，使接收端每次 `read` 都对应一次 `send`
- B. TCP 通过应用层 JSON 字段校验来恢复丢失报文内容
- C. TCP 的重传机制可在部分报文丢失时补发未确认的数据
- D. TCP 通过序号和确认机制支持按字节流确认数据接收进度

**答案：C、D**

**逐项解析**

- A 错误。TCP 是面向字节流的，不保留应用层消息边界，接收端可能发生粘包或拆包。
- B 错误。可靠性由传输层的序号、确认、重传和校验等机制提供，与应用层是否使用 JSON 无关。
- C 正确。发送方可在超时或收到重复 ACK 等情况下重传未确认数据。
- D 正确。TCP 按字节编号，ACK 表示接收方期望收到的下一个字节序号，可用于累计确认接收进度。

**知识点**

TCP 只提供有序可靠的字节流，不提供“消息”概念。应用层仍需自行设计报文边界，例如固定长度、分隔符、长度字段或 TLV，并同时处理超时、半包、粘包和连接中断。

### 20. 共享计数器与任务队列（多选）

**题目**

某后端服务中多个线程会同时更新共享计数器和任务队列。下列做法中，有助于降低并发错误风险的有哪些？

- A. 在临界区中执行长时间网络请求，以减少锁释放次数
- B. 把只读配置发布为不可变对象，减少共享状态修改
- C. 把共享队列的入队和出队操作纳入一致的同步协议
- D. 用互斥锁保护共享计数器的读改写临界区

**答案：B、C、D**

**逐项解析**

- A 错误。持锁执行慢 I/O 会拉长临界区，增加竞争、超时乃至锁雪崩风险。
- B 正确。不可变对象天然易于安全共享，能从源头减少写竞争。
- C 正确。入队和出队必须遵循同一套同步协议；一端加锁、另一端不加锁仍会破坏队列不变量。
- D 正确。`count += 1` 是读、改、写的复合操作，并非天然原子，需要互斥锁或合适的原子变量保护。

**知识点**

并发控制的目标不只是“加锁”，而是维护共享对象的不变量：

- 尽量减少共享可变状态；
- 临界区只包含必要的内存操作，不放慢 I/O；
- 对同一共享结构采用一致的锁或无锁协议；
- 明确锁顺序，避免死锁；
- 优先使用经过验证的线程安全队列和并发容器。

### 本节复习路线

这 20 题可以归纳为四条主线：

1. **后端运行时**：文件权限、线程资源、缺页恢复、TCP 字节流；
2. **数据正确性**：事务隔离、联合索引、幂等键、并发同步；
3. **算法基础**：稳定排序、区间贪心、栈模拟、二叉树计数；
4. **大模型工程**：证据边界、RAG 版本过滤、工具鉴权、模型上线评估。

最容易丢分的地方不是术语本身，而是系统边界。例如 Function Calling 的安全边界在服务端校验、授权和审计；支付回调的幂等边界在可持久化的业务唯一键；RAG 的事实边界在进入模型前就应通过元数据过滤确定。

## 02 · 余数游走 {#problem-02}

### 题目描述

给定长度为 $n$ 的整数序列 $a_1,a_2,\ldots,a_n$ 和正整数模数 $M$。序列首尾相接，视为一个环。

对于起点 $s$，从 $a_s$ 开始沿环依次取数，最多取 $n$ 个。走出第 $t$ 步后的余数轨迹值定义为

$$
S_t=\left(\sum_{i=0}^{t-1}a_{(s+i-1)\bmod n+1}\right)\bmod M,\qquad t\ge 1.
$$

余数采用标准非负表示，落在 $[0,M-1]$。轨迹不包含尚未取元素时的初始余数 $0$。

只要下一步得到的余数与轨迹中已有余数重复，游走就停止；若一直没有重复，则取满 $n$ 步后停止。记从起点 $s$ 出发能取到的最大步数为 $L_s$，求

$$
\sum_{s=1}^{n}L_s.
$$

输入包含 $T$ 组测试数据，其中 $1\le T\le 10^5$。每组输入满足 $1\le n,M\le 2\times10^5$，随后给出 $n$ 个整数，且 $-10^9\le a_i\le10^9$。保证所有测试数据的 $n$ 之和不超过 $2\times10^5$。

### 样例

**输入**

```text
2
5 3
1 2 2 1 2
4 5
5 0 5 0
```

**输出**

```text
11
4
```

第一组从位置 1 出发时，余数依次为 `1, 0, 2`，下一步再次得到 `0`，所以 $L_1=3$；其余四个起点的长度均为 2，总和为 11。

第二组每个元素对 5 的余数都是 0。任一起点第一步得到 0，第二步会重复，因此每个起点的长度都是 1。

### 解题思路

#### 1. 破环成链

把数组在逻辑上复制一遍。起点只有 $n$ 个，每个起点最多走 $n$ 步，因此只需覆盖 $2n-1$ 个元素。

定义前缀余数

$$
P_0=0,\qquad
P_i=(P_{i-1}+a_{(i-1)\bmod n+1})\bmod M.
$$

代码计算 $P_0,P_1,\ldots,P_{2n-1}$。

#### 2. 消去与起点有关的常数

从位置 $s$ 出发，走 $t$ 步后的余数是

$$
S_t=(P_{s+t-1}-P_{s-1})\bmod M.
$$

固定 $s$ 后，所有轨迹值都减去了同一个 $P_{s-1}$。模 $M$ 意义下减去同一个常数是双射，因此

$$
S_x=S_y
\iff
P_{s+x-1}=P_{s+y-1}.
$$

所以，从起点 $s$ 能合法走 $L$ 步，等价于

$$
P_s,P_{s+1},\ldots,P_{s+L-1}
$$

两两不同。问题已经变成：对前缀余数数组中的每个左端点，求长度不超过 $n$ 的最长无重复窗口。

#### 3. 双指针扫描所有起点

维护窗口 `[left, right]` 和集合 `seen`：

1. 下一个前缀余数未在集合中，且窗口长度还不到 $n$，就继续扩展右端；
2. 停止扩展时，窗口长度就是当前起点的答案；
3. 左端右移前，从集合中删除离开的余数。

左端右移只会放宽限制，所以右端不需要回退。每个位置最多入窗、出窗各一次。

### 正确性证明

固定起点 $s$ 时，第 $t$ 步轨迹值为 $(P_{s+t-1}-P_{s-1})\bmod M$。因为对所有步数都减去了相同常数，两个轨迹值相等当且仅当对应的两个前缀余数相等，所以 $L_s$ 正好等于从 $P_s$ 开始的最长无重复窗口长度，且长度上限为 $n$。

处理某个 `left` 时，`seen` 恰好保存 `prefix[left..right]`，其中元素两两不同。扩展循环只在下一个余数未出现且窗口未达到长度上限时继续，所以停止时窗口已是该左端点的最长合法窗口。删除左端元素后，不变量对下一个左端点继续成立。由此每个 $L_s$ 都被准确计算一次。

### Python 3 ACM 实现

```python
import sys

input = sys.stdin.readline


def total_walk_length(n, modulus, values):
    prefix = [0] * (2 * n)
    current = 0

    # P[1..2n-1] 足以覆盖全部起点，每个起点最多向后走 n 步。
    for i in range(1, 2 * n):
        current = (current + values[(i - 1) % n]) % modulus
        prefix[i] = current

    seen = set()
    right = 0
    total = 0

    for left in range(1, n + 1):
        limit = left + n - 1

        # seen 始终对应 prefix[left..right]，窗口内余数互不相同。
        while right < limit and prefix[right + 1] not in seen:
            right += 1
            seen.add(prefix[right])

        total += right - left + 1

        # 左端点准备右移；right 始终单调向右。
        seen.remove(prefix[left])

    return total


def solve():
    test_count = int(input())
    answers = []

    for _ in range(test_count):
        n, modulus = map(int, input().split())
        values = list(map(int, input().split()))
        answers.append(str(total_walk_length(n, modulus, values)))

    print("\n".join(answers))


solve()
```

### 复杂度分析

- **时间复杂度**：期望 $O(n)$。前缀余数线性生成，双指针中每个位置至多进出集合一次。
- **空间复杂度**：$O(n)$。

### 易错点

- 轨迹不包含“还没走”的初始余数 0，所以窗口从 $P_s$ 开始，不能把 $P_{s-1}$ 放入集合。
- 环形展开需要算到 $P_{2n-1}$；长度为 `2 * n` 的前缀数组正好够用。
- Python 的 `%` 自动得到非负余数；其他语言处理负数时需要再次加模。
- 总答案最大为 $n^2=4\times10^{10}$，固定宽度语言必须使用 64 位整数。

## 03 · 汽车洗车计算器 {#problem-03}

这是一道提示词工程题。提交物不是传统算法函数，而是一段 Prompt：模型接收一行自然语言洗车场景，严格按规则计算，并且只输出 JSON。

### 计费规则

1. 车型基础价：小型车 38 元、SUV 58 元、MPV 78 元；
2. 普通洗不加价；精洗按基础价的 180% 向上取整；打蜡按基础价的 250% 向上取整；
3. 会员在洗车类型加价后打 85 折并向下取整，该结果记为 `wash_cost`；
4. 内饰清洁每次 28 元，发动机清洗每次 45 元；
5. 节假日时，对 `wash_cost + 附加费` 乘 120% 并向上取整；
6. 室内停车 15 元，露天停车 0 元；停车费不参与节假日加成；
7. 最终输出 `total_bill`、`wash_cost` 和 `car_type`。

### 样例

**输入 1**

```text
张先生不是会员，非节假日，小型车普通洗，不加附加项目，露天停车。
```

**输出 1**

```json
{"total_bill":38,"wash_cost":38,"car_type":"小型车"}
```

**输入 2**

```text
李先生是会员，节假日，SUV精洗，加内饰清洁，室内停车。
```

**输出 2**

```json
{"total_bill":156,"wash_cost":89,"car_type":"SUV"}
```

第二个样例的计算顺序是：

1. SUV 精洗：$\lceil58\times1.8\rceil=105$；
2. 会员折扣：$\lfloor105\times0.85\rfloor=89$，所以 `wash_cost=89`；
3. 加内饰清洁后为 $89+28=117$；
4. 节假日加成：$\lceil117\times1.2\rceil=141$；
5. 最后加室内停车费 15 元，总价为 156 元。

### 为什么这道题容易错

困难不在算术，而在把自然语言规则写成**不可交换的流水线**。例如先打会员折扣再计算精洗，和先计算精洗再打折，可能得到不同整数；停车费若提前加入，也会被错误地收取节假日加成。

一个可靠 Prompt 至少要固定四件事：

- **角色**：模型是规则执行器，不是自由发挥的客服；
- **计算顺序**：每一步的输入、输出和取整方向都明确；
- **输出契约**：只允许一个 JSON 对象，字段名和类型固定；
- **反例约束**：明确“不是会员”“非节假日”不能因为包含关键词而被识别为肯定条件。

### 推荐 Prompt

```text
# 角色
你是洗车费用规则引擎。你的任务是从用户的一行中文描述中提取条件，
严格按下面的顺序计算费用，不补充题目之外的规则。

# 规则与顺序
1. 车型基础价：小型车=38，SUV=58，MPV=78。
2. 洗车类型：
   - 普通洗：基础价不变；
   - 精洗：ceil(基础价 × 18 / 10)；
   - 打蜡：ceil(基础价 × 25 / 10)。
3. 会员折扣：
   - 是会员：floor(第 2 步结果 × 85 / 100)；
   - 不是会员或非会员：不打折。
   第 3 步结果就是 wash_cost。
4. 附加费：每次内饰清洁 28，每次发动机清洗 45。
5. 节假日：
   - 节假日：ceil((wash_cost + 附加费) × 12 / 10)；
   - 非节假日：wash_cost + 附加费。
6. 停车费最后加入：室内停车=15，露天停车=0。
   停车费绝不参与节假日加成。
7. 第 6 步结果是 total_bill。

# 解析约束
- “不是会员”“非会员”必须识别为否定，不能仅因出现“会员”二字判为会员。
- “非节假日”必须识别为否定，不能仅因出现“节假日”三字判为节假日。
- car_type 只能是“小型车”“SUV”“MPV”之一。
- 所有取整必须在规则指定的步骤立即完成，再进入下一步。

# 输出要求
只输出合法 JSON，不输出 Markdown、解释、前后缀或额外字段：
{"total_bill":整数,"wash_cost":整数,"car_type":"车型"}

# 示例
输入：张先生不是会员，非节假日，小型车普通洗，不加附加项目，露天停车。
输出：{"total_bill":38,"wash_cost":38,"car_type":"小型车"}

输入：李先生是会员，节假日，SUV精洗，加内饰清洁，室内停车。
输出：{"total_bill":156,"wash_cost":89,"car_type":"SUV"}

# 现在处理
{{USER_INPUT}}
```

### Python 3 本地校验器

Prompt 的真实评测对象是大模型。为了在提交前校验计费顺序，下面额外给出一个针对题目固定词表的 Python 标准输入/输出参考程序。它不是用字符串规则替代大模型，而是充当确定性的“计费真值引擎”。

```python
import json
import sys


def ceil_div(value, divisor):
    return (value + divisor - 1) // divisor


def calculate(text):
    if "SUV" in text:
        car_type = "SUV"
    elif "MPV" in text:
        car_type = "MPV"
    else:
        car_type = "小型车"

    base_price = {
        "小型车": 38,
        "SUV": 58,
        "MPV": 78,
    }[car_type]

    # 用整数分子做乘法，避免浮点误差影响取整。
    if "精洗" in text:
        wash_price = ceil_div(base_price * 18, 10)
    elif "打蜡" in text:
        wash_price = ceil_div(base_price * 25, 10)
    else:
        wash_price = base_price

    is_member = (
        "会员" in text
        and "不是会员" not in text
        and "非会员" not in text
    )
    if is_member:
        wash_price = wash_price * 85 // 100

    # wash_cost 必须在附加费和节假日加成之前保存。
    wash_cost = wash_price

    addon_cost = 0
    if "内饰清洁" in text and "不加内饰清洁" not in text:
        addon_cost += 28
    if "发动机清洗" in text and "不加发动机清洗" not in text:
        addon_cost += 45

    subtotal = wash_cost + addon_cost
    is_holiday = "节假日" in text and "非节假日" not in text
    if is_holiday:
        subtotal = ceil_div(subtotal * 12, 10)

    parking_cost = 15 if "室内停车" in text else 0
    return {
        "total_bill": subtotal + parking_cost,
        "wash_cost": wash_cost,
        "car_type": car_type,
    }


def solve():
    description = sys.stdin.read().strip()
    result = calculate(description)
    print(
        json.dumps(
            result,
            ensure_ascii=False,
            separators=(",", ":"),
        )
    )


solve()
```

- 是否先完成车型加价，再做会员折扣；
- `wash_cost` 是否排除了附加费、节假日加成和停车费；

- 否定表达是否优先于关键词子串匹配；

## 04 · 分期借贷还款引擎 {#problem-04}

第四题是一道 AI Coding 工程题。公开资料可以确认：考生会拿到一份 README，需要完成一个以 HTTP JSON 提供服务的信贷领域项目，而不是提交单个算法函数。

### 可以确认的需求范围

系统需要管理：

- 信贷产品、借款人和贷款；
- 还款计划与账务流水；
- 等额本息、等额本金、先息后本三种还款方式；
- 放款、提前还款、逾期罚息、风险冻结、批量还款；
- 展期、减免、坏账核销、核销后回收与冲正。

同时必须满足以下工程约束：

- 金额精确到分，不能使用二进制浮点数直接记账；
- 日期按自然月推进，并支持可控制的虚拟时钟；
- 贷款与账务状态只能按合法路径流转；
- 每笔账务必须保持零和；
- 冲正遵循后进先出；
- 失败操作不能留下部分修改。

这些约束说明，评测重点不是“接口数量”，而是数据在长业务链路中始终保持一致。

### 先复述需求，再开始写代码

拿到陌生工程仓库后，第一条 AI 指令不应是“帮我全部实现”，而应要求它先完成仓库审计：

```text
阅读 README、目录、数据模型、路由、测试和 TODO。
先不要修改代码，输出：
1. 项目目标与运行方式；
2. 已实现、未实现和疑似错误的功能；
3. 核心实体、状态与数据不变量；
4. 每个公开接口的输入、输出和错误语义；
5. 按依赖关系排序的最小实现计划；
6. 当前信息不足、必须回到 README 核对的歧义。
所有结论都要标注对应文件或测试依据，不要臆造接口。
```

这一步能防止 AI 在没读懂现有骨架时重写项目，也能尽早发现 README 与代码之间的缺口。

### 领域模型应该围绕不变量组织

推荐至少拆出五类核心对象：

| 对象 | 关键字段 | 主要职责 |
|---|---|---|
| `Product` | 利率、期限、还款方式、罚息规则 | 描述合同模板 |
| `Borrower` | 身份、风险状态 | 决定能否新增或继续放款 |
| `Loan` | 本金、余额、状态、起息日 | 贷款聚合根，保护状态流转 |
| `Installment` | 期次、到期日、本金、利息、已还金额 | 表达计划与实际还款差异 |
| `LedgerTransaction` | 业务键、时间、分录、冲正关系 | 保存不可变账务事实 |

金额统一使用整数“分”：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class LedgerLine:
    account: str
    delta_cents: int


def validate_balanced(lines):
    if not lines:
        raise ValueError("账务分录不能为空")
    if sum(line.delta_cents for line in lines) != 0:
        raise ValueError("同一事务的账务分录必须零和")
```

如果原仓库规定使用 `Decimal`，也要在系统边界统一量化到两位小数；不要让 `float` 混入持久化模型。

### 三种还款方式的建模重点

1. **等额本金**：每期本金大体相同，利息按剩余本金计算，因此月供逐期下降；
2. **等额本息**：理论月供固定，但分到“分”后必然产生尾差，最后一期要吸收误差并确保本金余额归零；
3. **先息后本**：中间期只还利息，最后一期归还全部本金。

无论使用哪种方式，都应满足：

$$
\sum_{i=1}^{m} principal_i=loan\_principal
$$

且任一期的本金、利息和剩余余额均不能为负。不要在每个接口里重复计算计划；应由一个纯函数生成计划，再由服务层持久化。

::: info 日期与舍入必须服从原 README
“自然月如何处理 1 月 31 日”“利息采用四舍五入还是其他舍入”“提前还款当天是否计息”等细节会改变最终金额。公开截图没有给出这些规则，实际作答时必须以题目 README 和现有测试为准。
:::

### 状态机与原子性

状态迁移应集中在领域层。例如贷款被冻结后能否还款、核销后能否直接恢复，都必须由明确的迁移表控制，不能散落在路由的多个 `if` 中。

一次还款通常同时修改：

- 贷款剩余本金；
- 对应期次的已还本金、利息与罚息；
- 贷款状态；
- 账务流水；
- 幂等请求记录。

这些修改必须处于同一个数据库事务中。推荐顺序是：

1. 校验请求和幂等键；
2. 锁定贷款聚合或使用乐观版本号；
3. 计算本次资金分配；
4. 生成零和账务分录；
5. 校验所有领域不变量；
6. 一次性提交；
7. 提交失败则整体回滚。

“先更新余额，再尝试写流水”的实现一旦中途失败，就会产生无法审计的脏数据。

### 冲正为什么要用追加记录

账务流水应尽量不可变。冲正不是删除旧记录，而是追加金额相反的新事务，并引用被冲正的事务。

若同一笔业务发生多次可冲正操作，LIFO 约束意味着只能先冲销最后一笔尚未被冲正的事务。这样任意时刻都能从流水重放出当前余额，也保留了完整审计链。

```python
def reverse_lines(original_lines):
    # 冲正分录逐项取反，总和仍然为 0。
    reversed_lines = [
        LedgerLine(
            account=line.account,
            delta_cents=-line.delta_cents,
        )
        for line in original_lines
    ]
    validate_balanced(reversed_lines)
    return reversed_lines
```

### HTTP 层只做协议适配

原题接口路径和 JSON 字段应严格沿用 README。无论具体框架如何，HTTP 层都只负责：

- 解析并校验 JSON；
- 把业务异常映射成稳定的状态码和错误体；
- 把幂等键、操作者和虚拟时间传给服务层；
- 序列化领域结果。

金额计算、状态迁移和账务分配不应写在路由函数里。这样单元测试可以直接验证领域规则，不必为每个边界都启动 HTTP 服务。

| 计划 | 三种还款方式、最后一期 | 本金之和等于借款本金，余额最终为 0 |

### 推荐的 AI Coding 节奏

1. **仓库审计**：读完 README、测试和 TODO，输出证据化清单；
